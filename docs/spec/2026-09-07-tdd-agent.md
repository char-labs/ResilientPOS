# PR spec: TDD 주도 스킬과 에이전트

## 목적
비즈니스·도메인·Controller 개발을 테스트부터 진행하도록 저장소 전용 스킬과 Claude/Codex 에이전트를 제공한다.

## 범위
- Repository 자체 테스트를 제외하고 도메인/비즈니스 단위 테스트, 필요한 비즈니스 통합 테스트, REST Docs 기반 Controller 테스트 기준을 정한다.
- Fixture Monkey를 fixture 생성 도구로 선택하고 의도에 중요한 값과 문서 예시는 고정한다.
- 공통 TDD 스킬과 Claude/Codex 진입점, TDD 작업을 수행하는 에이전트를 설치한다.
- 루트 지침에는 조건부 실행 안내만 추가하고 상세 정책은 wiki로 분리한다.
- RED/GREEN/REFACTOR 실행 근거를 PR spec에 남기도록 템플릿을 보완한다.

## 제외
Repository CRUD/query/JPA 매핑 전용 테스트, 업무 기능/샘플 API 구현, 테스트 라이브러리 의존성 설치, GitHub workflow, 원격 push/PR 생성, 별도 plan 문서.
REST Docs와 Fixture Monkey 의존성은 최초 적용 기능 PR에서 버전 호환성을 검증하고 추가한다.

## 인수 조건
- 개발 요청 시 TDD 에이전트가 spec의 한 동작을 테스트로 바꾸고, 의도한 assertion 실패를 확인한 뒤 최소 구현과 리팩터링을 순차 수행한다.
- 환경/컴파일 오류나 실행하지 않은 테스트를 RED/GREEN 증거로 기록하지 않는다.
- Repository 테스트와 문서 전용 작업에 업무 TDD를 강제하지 않는다.
- Controller는 MockMvc와 REST Docs로 HTTP 계약을 검증하고 스니펫을 생성한다. 단순 Controller 메서드 호출을 HTTP 계약 테스트로 취급하지 않는다.
- fixture의 경계값/예상값/HTTP 문서 예시는 명시적으로 고정한다.
- 도구별 에이전트는 공통 스킬을 참조하며 지원하지 않는 환경에서는 주 에이전트가 같은 절차를 수행한다.

## 검증
스킬 frontmatter와 에이전트 설정 문법, 참조 경로, 공통 지침의 범위, 로컬 PR 검사를 확인한다.
독립 에이전트에게 현실적인 테스트 설계 시나리오를 주고 스킬 적용 전후의 판단을 검토한다. 이번에는 앱 코드/의존성을 바꾸지 않으므로 Gradle 테스트 실행을 주장하지 않는다.

## Wiki 영향
테스트 전략 페이지를 추가하고 개발 규칙, 현재 상태, wiki 인덱스, 변경 기록을 갱신한다. 제품 기능 요구사항은 바꾸지 않는다.

## 분할 계획
기존 하네스 브랜치 chore/development-harness의 d203398 위에 쌓는 별도 PR 단위다. 예상 12개 파일/350줄 이내. 실제 라이브러리 도입과 최초 테스트 구현은 후속 기능 PR로 분리한다.

## 결과

- 공통/Codex 스킬 및 Claude 진입점의 공식 quick_validate 통과. 검증용 PyYAML은 /tmp에만 설치했다.
- Claude plugin validate .claude/agents 통과. Codex TOML 필수 필드/문법, 공통 스킬 참조와 wiki 링크 검증 통과.
- python3 scripts/check_pr.py --base d203398 --worktree 및 git diff --check 통과.
- 독립 에이전트의 적용 전 시나리오 3개와 적용 후 시나리오 4개를 검토했다. 컴파일 오류/직접 Controller 호출/랜덤 문서값/Repository 테스트 제외/실제 롤백/기존 통과 테스트 구분이 모두 일관됐다. 적용 전에도 적절히 판단했으므로 스킬로 성능이 개선됐다고 주장하지 않는다.
- 실제 Claude/Codex 새 세션에서 자동 선택과 업무 RED/GREEN 실행은 미검증이다. 앱 코드와 의존성을 바꾸지 않았으므로 Gradle 테스트는 실행하지 않았다.
