# PR spec: 크기 게이트의 경계를 테스트로 고정하고 분할 규칙의 순환을 끊는다

## 목적
[pr-size-by-lines-only](2026-09-22-pr-size-by-lines-only.md)가 남긴 결함을 닫는다. multi-review에서 Claude와 Codex가 독립적으로 같은 것을 짚었고 전부 실측으로 확인했다.

**하네스 테스트가 새 경계를 고정하지 못한다.** 세 가지 변형을 넣고 스위트를 돌리니 모두 115개가 통과했다.

| 변형 | 결과 |
|---|---|
| 경고 임계 900 → 100 | 115개 통과 |
| 실패 임계 1400 → 1000 (메시지는 그대로) | 115개 통과 |
| 통계 줄에서 파일 수 삭제 | 115개 통과 |

원인은 셋이다. `test_size_and_warning`이 900줄을 쓰지만 spec 19줄과 구현 1줄이 더해져 검사기가 보는 값은 920줄이라 경계에서 20줄 떨어진 곳을 찍는다. 첫 단언이 경고 목록이 비지 않았는지만 보아 크기와 무관한 경고로도 통과한다. 둘째 단언이 임계값이 아니라 메시지 문자열을 본다. 그래서 앞 spec의 "하네스 테스트가 새 경계를 고정한다"는 서술은 사실이 아니었다.

**통계 줄의 파일 수에는 아무 테스트가 없다.** 스위트 전체에서 `check()`의 셋째 반환값을 읽는 테스트가 하나도 없다. "판정하지 않고 통계로만 출력한다"가 앞 PR의 핵심 계약인데 그 계약만 무방비였다.

**분할 규칙 두 줄이 서로를 되돌린다.** "경고가 나오면 남은 범위를 후속 PR로 이동한다"와 "같은 파일의 연속 작업은 1400줄 안이면 합친다"가 함께 있다. 1200줄 합본을 만들면 900줄 경고가 뜨고 앞 줄이 남은 범위를 후속 PR로 밀어내는데, 그 후속은 의존하므로 스택이 되어 새 절이 피하려던 결과로 돌아온다.

## 범위
**경계를 상수로 하나만 두고 테스트가 그 상수를 읽는다.** `WARN_LINES = 900`, `FAIL_LINES = 1400`을 `check_pr.py`에 두고 조건과 메시지가 모두 그 값을 쓴다. 지금은 같은 숫자가 조건과 메시지에 따로 적혀 있어 조건만 바꿔도 메시지 단언이 통과한다.

**테스트가 경계의 양쪽을 찍는다.** 고정 오버헤드를 통계 줄에서 읽어 빼고 실제 입력을 `WARN_LINES - 1`·`WARN_LINES`·`FAIL_LINES`·`FAIL_LINES + 1`로 맞춘다. 각 경우에 오류 목록과 경고 목록을 둘 다 단언한다. 메시지 문자열의 숫자에 기대지 않는다.

**통계 줄의 파일 수에 테스트를 둔다.** 파일 수가 f-string에서 사라지면 실패해야 한다.

**규칙의 순환을 끊는다.** [개발 워크플로](../wiki/development-workflow.md)에서 경고를 명령이 아니라 신호로 고쳐 쓴다. 쪼갤 수 없는 한 목표면 실패 한도까지 그대로 낸다. 작업 선택 순서에는 **앞 PR 머지를 기다린다**를 넣는다. 1인 저장소에서 가장 싼 선택인데 지금 빠져 있다.

**겹침 판정에서 `docs/spec/**`를 뺀다.** PR마다 자기 spec을 그 아래 쓰므로 그대로 두면 "경로가 겹치지 않는다"가 거의 항상 거짓이 되어 1단계가 사문이 된다.

**과한 단정 둘을 사실에 맞춘다.** 경로가 겹치지 않는 것은 문자열 비교일 뿐이라 의미적 독립의 증거가 아니다. squash 머지가 반드시 `CONFLICTING`을 만든다고 단정한 것도 두 번의 관측이지 보편 법칙이 아니다.

**앞 spec의 사실과 다른 서술을 고친다.** "하네스 테스트가 새 경계를 고정한다"는 틀렸다. 「제외」가 볼트 스킬 본문을 제외한다고 적고 「결과」가 그것을 고쳤다고 적어 서로 어긋난다. 막힌 시점의 파일 수는 25개가 아니라 26개다(상한이 25).

**1400의 근거와 재검토 조건을 적는다.** 지금은 숫자만 있다. 합산 1027줄을 수용하고 여유를 둔 값이라는 것과, 그 구간을 실제로 리뷰해 본 적이 없다는 것을 함께 남긴다.

**파일 수 상한을 없애면서 열린 경로를 한계로 적는다.** 빈 파일은 0줄로 세므로 몇 개를 넣어도 게이트에 걸리지 않는다. 한 줄 수정은 2줄로 세므로 1400줄이 한 줄씩 고친 약 700개 파일을 허용한다. 실측했다.

계약: 판정 기준은 그대로다. 상수로 빼는 것은 값이 아니라 표현만 바꾼다. 저장 형식도 API도 건드리지 않는다.

복구: 해당 없음.

관측성: 해당 없음.

## 제외
- 한도 값 자체의 변경. 900과 1400을 그대로 둔다.
- 파일 수를 경고로 되살리는 것. 리뷰어가 선택지로 제시했지만 "파일 수는 참고 수치로만 출력한다"가 앞 PR에서 정한 것이라 뒤집지 않는다. 대신 그 결정이 여는 경로를 문서에 적는다.
- `HarnessTest` 상속 구조 정리. 하위 클래스 넷이 상속해 같은 15개가 다섯 번 실행되어 실행 수 115 중 60이 중복이다. 고유 테스트는 55개다. 목표가 달라 나눈다.
- `check_pr.py`의 rename 미인식. 이동을 삭제와 삽입으로 세어 줄 수가 두 배가 되지만, 앞 PR의 근거였던 25개/361줄은 그 계산으로 나온 검사기 자신의 값이라 근거가 흔들리지 않는다. 실측해 확인했다.
- 원문 보관 경로의 파일 수 한도 테스트. 선존재 공백이고 이 PR의 목표 밖이다.

## 인수 조건
1. 경고 임계를 바꾸면 테스트가 실패한다.
2. 실패 임계를 바꾸고 메시지를 그대로 두어도 테스트가 실패한다.
3. 통계 줄에서 파일 수를 지우면 테스트가 실패한다.
4. 실제 입력이 899줄이면 오류도 경고도 없다.
5. 실제 입력이 900줄과 1400줄이면 경고만 있고 오류가 없다.
6. 실제 입력이 1401줄이면 오류가 있다.
7. 기존 검사가 그대로 동작한다.

## 검증
- `python3 scripts/test_check_pr.py` — 전부 통과.
- 인수 조건 1~3은 해당 변형을 실제로 넣어 스위트가 **실패하는 것**을 관측한다. 통과만 보면 아무것도 증명하지 못한다.
- `python3 scripts/check_pr.py --base origin/main --worktree` — PASS.

## TDD 검증 기록
RED를 변형 주입으로 관측한다. 세 변형 각각에서 바꾸기 전 스위트는 전부 통과했고, 고친 뒤에는 실패해야 한다.

| 동작 / 테스트 이름 | RED 명령·실패 이유 | GREEN 명령·결과 | 리팩터링 후 회귀 명령·결과 |
|---|---|---|---|
| 경고 임계를 바꾸면 잡힌다 | 임계를 100으로 바꿔도 `python3 scripts/test_check_pr.py` 115개 통과 | 경계 테스트를 고친 뒤 같은 변형에서 실패 | 변형을 되돌리고 전부 통과 |
| 실패 임계를 바꾸면 잡힌다 | 임계를 1000으로 바꿔도 통과 | 같은 변형에서 실패 | 같음 |
| 통계 줄의 파일 수가 사라지면 잡힌다 | f-string에서 지워도 통과 | 같은 변형에서 실패 | 같음 |
