# PR spec: 오프라인 결제 시연용 단말 화면을 정적 페이지로 둔다

## 목적
단말 네트워크가 끊겨도 주문과 결제 요청을 받고, 재연결 뒤 서버에 빠짐없이 반영되는 것을 눈으로 시연할 화면이 없다. 지금은 `POST /v1/terminals/{terminalId}/sync`를 직접 호출해야만 확인할 수 있다.

기대 결과:
- 브라우저에서 `http://localhost:8080/terminal/index.html`을 열면 결제 단말 모양의 주문·결제 화면이 뜬다.
- 화면에서 결제하면 `CREATE_ORDER`와 `REQUEST_CHECKOUT` operation이 단말 저장소(localStorage)에 먼저 쌓이고, 연결되어 있으면 sync 배치로 전송된다.
- 네트워크가 끊긴 동안의 결제도 같은 방식으로 쌓였다가 재연결 뒤 순번대로 전송된다.

## 범위
- `src/main/resources/static/terminal/index.html` 한 파일. 빌드 도구와 외부 라이브러리를 쓰지 않는다. Spring Boot의 기본 정적 리소스 제공으로 서빙하므로 서버 코드와 설정은 바꾸지 않는다.
- 화면 구성은 토스 포스(선불형 주문 홈)의 공개 화면 캡처를 참고했다. 상단 바, 분류 탭, 상품 격자, 주문서 패널, 결제 버튼, 고객 결제 안내 화면, 현황 화면이다. 로고와 상표는 쓰지 않는다.
- 단말 식별자(`terminalId`, `storeId`)는 브라우저마다 처음 열 때 UUID로 만들어 localStorage에 둔다. 순번은 1부터 단조 증가한다.
- 전송 규칙은 기존 sync 계약을 그대로 따른다. `APPLIED`와 `DUPLICATE`는 대기열에서 지우고, `REJECTED`는 지우고 주문을 거절로 표시하고, `GAP`은 남겨 다시 보낸다. `CONFLICT`는 지우고 주문을 충돌로 표시한다.
- 고객 화면(키오스크)을 같은 파일에 둔다(범위 조정, 2026-10-05 추가). 상단 바의 키오스크 토글이나 주소의 `?kiosk`로 들어가며, 고정 크기 대신 화면 폭을 따르는 반응형 배치다(820px 이하에서는 담은 메뉴가 아래에 붙는다). 고객이 메뉴를 담고 결제하는 흐름이고 대기열과 sync는 직원 화면과 같은 것을 쓴다.
- 디자인은 Toss Design System `DESIGN.md`를 따른다(범위 조정, 2026-10-05 추가). 그 문서가 값을 명시한 것만 그대로 쓰고, 명시하지 않은 것은 확장으로 표시한다.
  - 따른 것: 색상 semantic token 10개(foreground, body, muted, border, canvas, surface, primary, primary-hover, weak 배경·전경, danger), 글꼴 순서(Toss Product Sans 우선, 시스템 글꼴 대체. 글꼴 파일은 재배포 권리가 확인되지 않아 싣지 않는다), 본문 16px와 줄 높이 24px, TDS Mobile Button 크기 눈금(xlarge 56px·16px·17px/600, medium 38px·10px, small 32px·8px)과 상태(disabled, pressed, hover, keyboard focus, 동기화 버튼의 loading과 폭 유지), 그림자 없음, 간격 눈금(4·6·8·16·24·32), 결과와 다음 행동을 밝히는 문구.
  - 확장(문서가 값을 주지 않은 것): 상단 바와 작업 영역 색, 상품 타일 색과 크기, 옵션 버튼(52px), 분류 탭, 매장·포장 선택, 수량 조절, 상태 배지 색, 알림(toast), 결제 안내 화면 배치, 카드 모서리 반경. TDS가 공개한 43개 컴포넌트 가운데 값이 측정된 것은 Button·Badge·TextField·Agreement 넷뿐이어서 나머지는 포스 화면 캡처를 근거로 구성했다.
  - 따르지 않은 것: `color.muted`를 가격 같은 보조 글자에 쓰지 않고 빈 상태 안내에만 쓴다. 흰 배경에서 대비가 낮아 읽기 어렵기 때문이고 보조 글자는 `color.body`를 쓴다.
- 결제 화면에 결제 방법 선택과 페이스페이 흐름을 둔다(범위 조정, 2026-10-05 추가). 결제를 누르면 금액과 함께 `페이스페이`와 `카드 · 휴대폰` 두 가지를 고르고, 페이스페이는 얼굴 인식 화면을 거쳐 결제 요청을 접수한다. 직원 화면과 고객 화면이 같은 결제 화면을 쓴다.
  - 얼굴 인식은 흉내다. 카메라를 쓰지 않고 얼굴 정보를 다루지 않으며 1.5초 뒤 결과를 낸다. 시연 제어 막대에서 인식 성공과 실패를 고른다.
  - 인식에 실패하면 결제되지 않았다고 알리고 다시 시도와 카드 결제를 권한다. 인식 도중 취소하면 주문을 만들지 않는다.
  - 오프라인에서는 페이스페이를 고를 수 없다. 얼굴 대조는 서버가 해야 한다고 가정했기 때문이다(실제 단말의 동작은 확인하지 못했다). 인식 도중 끊기면 실패로 안내하고 카드 결제만 권한다. 카드 결제는 오프라인에서도 단말에 저장한다.
  - 결제 수단은 단말의 결제 내역에만 남긴다. sync 계약에는 수단 필드가 없어 서버로 보내지 않는다.
- 고객 화면은 세로형 결제 단말 모양으로 그린다(범위 조정, 2026-10-05 추가). 사용자가 준 자료(아래 참고 자료)의 실제 단말 화면을 따랐다. 800×1280 비율을 480×768 논리 크기로 그리고 창 크기에 맞춰 축소·확대한다. 화면 폭을 따라 배치가 바뀌던 이전 방식은 없앴다. 상단 바(뒤로, 직원 부르기, English, 처음으로), 결제할 금액, "카드를 넣거나 선택하세요", 결제 수단 타일(얼굴결제·QR 결제·현금·계좌이체), 아래쪽 카드 투입 안내로 구성한다. QR 결제·현금·계좌이체는 자리만 있다.
- 페이스페이 화면 세 가지를 실제 단말 사진의 구성에 맞춘다(범위 조정, 2026-10-05 추가). 근거는 아래 참고 자료의 아이샵케어 글에 실린 단말 사진이다.
  - 결제 화면: 페이스페이를 맨 위의 넓은 타일로 가장 먼저 두고, 그 아래에 삼성페이·애플페이 안내 줄, 다시 그 아래에 작은 타일 세 개(QR 결제, 현금, 계좌이체)를 둔다. 이전에는 페이스페이가 다른 타일과 같은 크기였다.
  - 얼굴 확인 화면: 어두운 전체 화면에 큰 원형 테두리를 두고 그 안에 "얼굴 확인 중"을 적는다. 이전에는 흰 배경이었다. 실제 단말은 원 안에 카메라 영상을 보이지만 이 화면은 카메라를 쓰지 않아 직접 그린 도형을 둔다.
  - 대기 화면: 옅은 파란 면에 얼굴 표시와 안내 문구를 둔다. 실제 단말의 대기 화면에 있는 캐시백 홍보 문구, 결제하기 버튼, 로고는 넣지 않았다. 결제는 포스가 시작하므로 버튼이 필요 없다.
  - 실제 단말이 얼굴 확인 화면 아래에 보이는 개인정보 수집 동의 안내는 넣지 않았다. 얼굴 정보를 다루지 않는 시연이라 동의를 받을 대상이 없다.
- 고객 단말을 2세대 단말(프론트 2)의 전면 구성에 맞춘다(범위 조정, 2026-10-05 추가). 근거는 아래 참고 자료의 제작기 글에 실린 제품 사진과 도해다.
  - 조사한 사실: 화면은 7인치 1280×800으로 1세대와 같다. 화면 위에 검은 띠가 있고 그 왼쪽에 비접촉 결제 표시, 오른쪽에 카메라 2개가 있다. 비접촉 결제 자리는 1세대의 오른쪽 옆면에서 전면 위쪽으로 옮겨졌다. IC 카드 투입구는 화면 아래 전면에 있고 긁는 방식의 리더는 오른쪽 옆면에 붙는다. 얼굴 확인 화면은 카메라 영상 둘레에 파란 호 모양의 테두리를 두른다.
  - 단말 틀: 화면(464×768 논리 크기) 위에 검은 띠, 아래에 투입구가 있는 턱을 그려 전체를 480×880으로 한다. 지금 쓸 수 있는 자리를 밝힌다. 결제 화면에서는 비접촉 결제 표시가, 얼굴 확인 중에는 카메라 2개가 켜진다.
  - 문구: 삼성페이·애플페이 안내를 1세대 기준의 "오른쪽 옆면"에서 "화면 위쪽 표시"로 바꾼다. 얼굴 확인 안내는 "화면 위 카메라를 바라봐 주세요"로 바꾼다.
  - 얼굴 확인 화면의 테두리를 깜빡이는 원에서 도는 호로 바꾼다.
  - 넣지 않은 것: 긁는 방식의 옆면 리더, 검은색 본체 색상, 리더 교체 구조. 화면 흐름과 관계가 없다.
- 사용 가이드 204쪽과 제품 페이지를 분석해 화면을 실제 구성에 맞춘다(범위 조정, 2026-10-05 추가). 근거는 아래 참고 자료의 사용 가이드와 사용자가 준 단말 사진이다.
  - 고객 결제 화면: 옅은 회색 면 위에 흰 타일을 쌓는다. 위에서부터 삼성페이·애플페이·NFC 큰 타일, 2×2 타일(얼굴결제, QR 간편결제, 현금, 계좌이체), 선불권·포인트·쿠폰 사용 버튼, "카드는 여기에"와 투입 표시다. 이전의 "페이스페이 넓은 타일" 구성은 사용자가 준 사진과 달라 바꿨다.
  - 포스의 결제하기 화면을 더한다. 결제를 누르면 총 결제금액, 분할 결제, 쿠폰·포인트 사용, 결제 방법 타일(신용카드, 현금, QR결제, 계좌이체, 전화승인), 오른쪽 주문내역이 있는 화면으로 간다. 연결된 고객 단말에는 같은 금액의 결제 화면이 함께 뜬다. 이전의 결제 대기 창은 없앴다.
  - 현금 결제를 더한다. 포스의 현금 타일은 고객 화면을 거치지 않고 바로 접수하고 수단을 `CASH`로 남긴다.
  - 현황을 주문 목록과 주문 상세로 다시 만든다. 오른쪽에 진행·완료 목록(주문 출처 표시, 주문 이름, 경과 시간, 완료 버튼), 왼쪽에 결제 정보 카드와 품목 카드를 둔다. 전송 상태(대기 건수, 확정 순번, 지금 동기화)는 목록 아래와 주문 상세의 "서버 전송" 줄로 옮겼다. 상단 현황 탭에 진행 건수를 붙인다.
  - 단말 기록에 주문번호(1부터 증가), 주문 출처(포스·키오스크), 매장·포장, 품목, 조리 완료 여부를 더한다. sync 계약에는 이 필드가 없어 서버로 보내지 않는다. 이 변경 이전에 만든 주문은 번호와 품목 없이 보인다.
  - 키오스크를 실제 흐름으로 다시 만든다. 첫 화면(주문하기), 매장·포장 선택(먹고가요, 포장해요), 메뉴(분류 탭, 2단 카드, 인기·신규 배지, 하단 확인하기), 주문 확인("이대로 주문할까요?", 수량 조절, 메뉴 더 추가), 결제 수단(카드, 삼성·애플페이, QR 간편결제), 카드 투입 안내, 주문번호 안내(4초 뒤 닫힘) 순서다. 상품 사진 자리에는 색 면과 글자를 둔다.
  - 넣지 않은 것: 상품 상세와 옵션 선택, 포인트 적립·사용 화면, 고객 호출 방식 입력, 분할결제·할인 등록 모달, 결제내역·시재·설정 화면, 후불형(테이블 홈)·도소매(바코드)·서비스업(예약) 화면, 터미널(카드단말기) 화면. 가이드에서 구성은 파악했으나 이번 시연의 흐름(주문, 결제, 오프라인 전송)에 필요하지 않다.
- 포스와 고객 단말을 서로 다른 포트에서 띄워 주고받게 한다(범위 조정, 2026-10-05 추가).
  - 같은 파일을 두 포트로 서빙하고 주소의 `role=terminal`로 역할을 가른다. 포스 화면의 `고객 단말 창 열기`가 자기 포트에 1을 더한 주소로 단말 창을 연다. 다른 주소는 `terminal` 파라미터로 준다.
  - 포스가 주문·대기열·sync를 모두 맡는다. 단말은 결제 화면만 그리고 저장소를 쓰지 않는다.
  - 두 창은 `postMessage`로만 주고받고 양쪽 모두 상대 origin과 창을 확인한다. 포스는 그릴 때마다 상태(연결 여부, 키오스크 여부, 결제 요청, 결제 결과)를 통째로 보내고, 단말은 `paid`·`cancel`·`done`만 보낸다.
  - 포스에서 결제를 누르면 포스에는 결제 대기 창이, 단말에는 결제 화면이 뜬다. 어느 쪽에서든 취소할 수 있고 취소하면 주문을 만들지 않는다.
  - 키오스크를 켜면 단말에 주문 화면이 뜬다. 단말은 상품 코드와 수량만 보내고 포스가 자기 메뉴에서 이름과 가격을 다시 읽는다. 모르는 상품이나 범위 밖 수량이 하나라도 있으면 그 주문을 받지 않는다.
  - 단말 창이 연결되지 않았으면 이전처럼 포스 화면이 고객 화면으로 바뀐다.
  - 한계: 같은 브라우저의 두 창만 이어진다. 기기 두 대로 시연하려면 서버를 거치는 중계가 필요하다. 포스를 새로 고치면 연결이 끊기므로 `고객 단말 창 열기`를 다시 누른다.
- 시연 제어 막대(단말 화면 밖)에 네트워크 강제 차단 스위치를 둔다. 브라우저의 실제 오프라인 상태와 요청 실패도 같은 경로로 처리한다.
- 서버 없이 파일로 열거나 주소에 `?mock`을 붙이면 서버 응답을 흉내 낸다.

## 제외
- 실제 얼굴 인식과 페이스페이 승인 연동. 화면 흐름만 재현한다.
- 실제 카드 승인. 토스페이먼츠 개발자 키 연동은 후속 작업이다. 이 화면의 결제는 결제 요청 접수까지다.

## 후속 작업
이 PR에 담지 않고 넘기는 일이다. 백엔드 변경은 모두 별도 컨텍스트라 각각 새 spec과 새 PR로 다룬다. 근거는 사용 가이드 204쪽 분석과 저장소 조사(모듈 구성, 공개 HTTP 입구, 제품 기획서의 비목표)다.

결정이 먼저 필요한 것:
1. 수단별 오프라인 결제의 의미. 지금은 오프라인에서 결제 요청을 쌓았다가 재연결 뒤 서버가 승인을 요청한다. 실물 카드는 고객이 떠난 뒤 승인할 수 없고 기획서는 카드 번호를 저장하지 않는다고 정했다. 현금은 단말에서 확정된 사실이라 오프라인에서 받아도 된다. 카드는 오프라인에서 막을지, 단말이 받은 승인 결과를 사실로 기록할지 정해야 한다.
2. 토스페이먼츠 연동의 범위. 토스페이먼츠는 온라인 결제 대행 API라 서버 쪽 승인 요청·조회·취소는 붙일 수 있지만 카드를 읽는 단말 결제는 이 경로로 시연할 수 없다.
3. 고객관리(고객, 포인트, 스탬프, 쿠폰, 선불권, 예약)를 범위에 넣을지. 기획서는 CRM을 비목표로 둔다. 넣으면 쿠폰·포인트·선불권이 결제 승인 전에 금액을 깎고 취소 때 되돌려야 해서 주문·결제 설계가 함께 바뀐다.

백엔드 후속(위 결정 뒤):
- 결제 수단과 단말 승인 결과를 받는 경로. 지금 게이트웨이 포트는 결제 식별자와 금액만 받는다. 이 화면이 현금으로 기록해도 서버는 똑같이 승인을 요청한다.
- 분할결제. 가이드는 한 주문에 결제 여러 건과 남은 금액을 다루는데 현재 모델은 한 checkout에 진행 중인 승인 시도가 하나다.
- 주문 속성: 주문 출처(포스·키오스크·배달·테이블주문), 주문번호, 매장·포장, 옵션, 할인. 지금은 단말의 로컬 기록에만 있다.
- 상품과 가격의 소유. 서버가 단말이 보낸 단가를 그대로 받는다. `store`가 상품을 가져야 검증할 수 있다.
- 조회와 취소 입구. 공개 HTTP 입구가 주문 생성, checkout, sync 셋뿐이라 현황의 서버 쪽 상태와 결제 취소를 보여줄 수 없다.

이 화면의 후속:
- 단말 인증 반영. 열린 PR 81번(단말 토큰 인증)이 머지되면 sync 입구가 인증을 요구해 이 화면의 실서버 전송이 거절된다. 화면이 단말 토큰을 받아 요청에 싣도록 고쳐야 한다. 그 전까지는 모의 모드(`?mock`)로만 시연할 수 있다.
- 키오스크의 독립. 지금은 키오스크 주문이 포스를 거쳐 포스의 단말 식별자로 접수돼, 포스가 꺼지면 키오스크도 주문을 받지 못한다. 실제 제품에는 포스 없이 쓰는 단독 키오스크가 있다. 키오스크가 자기 단말 식별자와 대기열을 갖게 한다.
- 기기 두 대 시연. 포스와 단말의 연결이 같은 브라우저의 두 창에 묶여 있다. 서버를 거치는 중계가 필요하다.
- 만들지 않은 화면: 상품 상세와 옵션 선택, 포인트 적립·사용, 고객 호출 방식 입력, 분할결제·할인 등록, 결제내역, 시재, 설정, 테이블 홈(후불형), 바코드(도소매), 예약(서비스업), 터미널(카드단말기).
- 디자인 다듬기와 실제 기기에서의 확인. 지금까지는 자동화 브라우저로만 확인했다.
- 단말 저장소. 지금은 localStorage다. 기획서는 로컬 DB를 말한다.
