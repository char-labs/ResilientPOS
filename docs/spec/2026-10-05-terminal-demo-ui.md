# PR spec: 오프라인 결제 시연용 단말 화면을 정적 페이지로 둔다

## 목적
단말 네트워크가 끊겨도 주문과 결제 요청을 받고, 재연결 뒤 서버에 빠짐없이 반영되는 것을 눈으로 시연할 화면이 없다. 지금은 `POST /v1/terminals/{terminalId}/sync`를 직접 호출해야만 확인할 수 있다.

기대 결과:
- `demo` 프로필로 띄운 애플리케이션에서 `http://localhost:8080/terminal/index.html`을 열면 포스 화면이 뜨고, 다른 포트에서 연 고객 단말 화면과 주고받는다.
- 화면에서 결제하면 `CREATE_ORDER`와 `REQUEST_CHECKOUT` operation이 단말 저장소(localStorage)에 먼저 쌓이고, 연결되어 있으면 sync 배치로 전송된다.
- 네트워크가 끊긴 동안의 결제도 같은 방식으로 쌓였다가 재연결 뒤 순번대로 전송된다.

## 범위
이 절은 최종 상태다. 범위가 바뀐 경위는 결과 절 첫머리에 있다.

**파일과 서빙**
- 화면은 `src/main/resources/static/terminal/index.html` 한 파일이다. 빌드 도구와 외부 라이브러리를 쓰지 않는다.
- 정적 파일 서빙은 기본값에서 끄고(`spring.web.resources.add-mappings: false`) `demo` 프로필에서만 켠다. 이 화면은 인증 없이 열리고 sync endpoint를 부르므로 운영 jar에 실려도 기본 프로필에서는 404다. `DemoPageExposureTest`가 두 프로필의 동작을 지킨다. 서버의 업무 코드는 바꾸지 않는다.
- 한 파일이 주소의 `role` 값에 따라 포스와 고객 단말 두 역할로 동작한다. `?mock`을 붙이거나 파일로 열면 서버 응답을 흉내 낸다.

**포스 화면(가로형 1280×800)**
- 주문 홈: 상단 바(키오스크 토글, 주문 홈·현황 전환, 네트워크 상태), 분류 탭, 상품 타일, 주문서 패널, 결제 버튼.
- 결제하기: 총 결제금액, 결제 방법 타일(신용카드, 현금, QR결제, 계좌이체, 전화승인), 주문내역. 현금은 포스에서 바로 접수하고 수단을 `CASH`로 남긴다. 신용카드는 고객 단말에서 받는다.
- 현황: 진행·완료 목록(주문 출처, 주문 이름, 경과 시간, 전송 상태 배지, 완료 버튼)과 주문 상세(결제 정보, 품목). 목록 아래에 전송 대기 건수, 확정 순번, 지금 동기화 버튼을 둔다. 전송이 막히면 그 자리와 상단 바에 사유를 보인다.

**고객 단말 화면(세로형, 화면 464×768에 단말 전면 틀을 더해 480×880)**
- 단말 틀: 2세대 단말의 전면 구성을 따른다. 화면 위 검은 띠에 비접촉 결제 표시와 카메라 2개, 화면 아래에 IC 카드 투입구가 있다. 결제 화면에서는 비접촉 표시가, 얼굴 확인 중에는 카메라가 켜진다.
- 대면 결제: 결제할 금액, "카드를 넣거나 선택하세요", 삼성페이·애플페이·NFC 타일, 2×2 타일(얼굴결제, QR 간편결제, 현금, 계좌이체), 선불권·포인트·쿠폰 사용 버튼, "카드는 여기에"와 투입 표시.
- 얼굴결제: 어두운 화면의 얼굴 확인, 실패 안내, 결과. 얼굴 인식은 흉내다. 카메라를 쓰지 않고 얼굴 정보를 다루지 않으며 1.5초 뒤 결과를 낸다. 오프라인에서는 고를 수 없다(얼굴 대조는 서버가 해야 한다고 가정했고 실제 단말의 동작은 확인하지 못했다).
- 키오스크: 첫 화면, 매장·포장 선택, 메뉴(분류 탭, 2단 카드, 배지), 주문 확인, 결제 수단(카드, 삼성·애플페이, QR 간편결제), 카드 투입 안내, 주문번호 안내(4초 뒤 닫힘). 결제가 아직 확인되지 않았으면 "준비 완료" 대신 "주문을 접수했습니다"라고 보인다.
- 대기 화면과 연결 안내 화면.

**포스와 단말의 연결**
- 같은 파일을 두 포트로 서빙한다. 포스의 `고객 단말 창 열기`가 자기 포트에 1을 더한 주소로 단말 창을 연다. 다른 주소는 `terminal` 파라미터로 준다.
- 포스가 주문·대기열·sync를 모두 맡는다. 단말은 화면만 그리고 저장소를 쓰지 않는다.
- 두 창은 `postMessage`로만 주고받는다. 양쪽 모두 상대 origin과 창을 확인하고, 주소로 받은 상대 주소는 같은 호스트·같은 프로토콜의 절대 주소일 때만 쓴다.
- 포스는 그릴 때마다 상태(네트워크, 키오스크 여부, 얼굴 인식 시연 결과, 결제 요청, 결제 결과)를 통째로 보내고 주문을 받지 못하면 `rejected`를 보낸다. 단말은 `hello`·`paid`·`cancel`·`done`을 보낸다.
- 단말은 받은 상태를 정해진 모양과 타입으로만 받는다(금액은 숫자, 주문번호는 정수, 상태와 수단은 허용 목록).
- 키오스크 주문은 단말이 상품 코드와 수량만 보내고 포스가 자기 메뉴에서 이름과 가격을 다시 읽는다. 모르는 상품이나 범위 밖 수량이 하나라도 있으면 받지 않는다.
- 단말은 포스가 받았다고 답한 뒤에만 장바구니를 비운다. 거절되거나 5초 안에 답이 없으면 접수되지 않았다고 알리고 담은 메뉴를 남긴다.
- 단말 창이 연결되지 않았으면 포스 화면이 고객 화면으로 바뀐다.

**대기열과 전송**
- 단말 식별자(`terminalId`, `storeId`)는 브라우저마다 처음 열 때 UUID로 만들어 localStorage에 둔다. 순번은 1부터 단조 증가한다.
- 결제하면 `CREATE_ORDER`와 `REQUEST_CHECKOUT`을 저장소에 먼저 쓴다. 저장에 실패하면 메모리의 대기열·순번·주문 기록을 되돌리고 결제를 완료로 보이지 않는다.
- 전송 규칙은 기존 sync 계약을 따른다. `APPLIED`와 `DUPLICATE`는 대기열에서 지우고, `REJECTED`는 지우고 주문을 거절로 표시하고, `GAP`은 남겨 다시 보낸다. `CONFLICT`는 지우고 주문을 충돌로 표시한다. 한 번에 50개씩 보내고 실패하면 5초마다 다시 보낸다.
- 같은 주소의 다른 탭이 저장하면 그 내용을 따른다. 두 탭이 각자 순번을 매기지 않게 하려는 것이다.
- 단말 기록에 주문번호, 주문 출처(포스·키오스크), 매장·포장, 결제 수단, 품목, 조리 완료 여부를 남긴다. sync 계약에 없는 필드라 서버로 보내지 않는다. 확정된 주문 기록은 200건까지만 둔다.

**시연 제어(단말 화면 밖의 막대)**
- 네트워크 강제 차단, 고객 단말 창 열기, 키오스크 켜기, 얼굴 인식 성공·실패 선택, 단말 초기화(두 번 눌러야 하고 4초 뒤 풀린다).
- 브라우저의 실제 오프라인 상태와 요청 실패도 강제 차단과 같은 경로로 처리한다.

**디자인 기준**
- 사용자가 준 Toss Design System `DESIGN.md`를 따른다. 그 문서가 값을 명시한 것만 그대로 쓰고 나머지는 확장으로 표시한다.
- 따른 것: 색상 token(foreground, body, muted, border, surface, primary, primary-hover, weak 배경·전경, danger), 글꼴 순서(Toss Product Sans 우선, 시스템 글꼴 대체. 글꼴 파일은 재배포 권리가 확인되지 않아 싣지 않는다), 본문 16px와 줄 높이 24px, TDS Mobile Button 크기 눈금과 상태, 그림자 없음, 결과와 다음 행동을 밝히는 문구.
- 간격은 4·6·8·16·24·32 눈금을 기본으로 한다. 결제하기 화면의 좌우 여백(56px)과 배지·알림의 1~2px 안쪽 여백은 눈금 밖이다.
- 확장: 상단 바와 작업 영역 색, 상품 타일, 분류 탭, 수량 조절, 상태 배지 색, 알림, 고객 화면의 배치. 그 문서가 값을 측정한 컴포넌트는 Button·Badge·TextField·Agreement 넷뿐이어서 나머지는 공개 화면 캡처와 사용 가이드를 근거로 구성했다.
- 따르지 않은 것: `color.muted`는 흰 배경에서 대비가 낮아 빈 상태 안내에만 쓰고 보조 글자는 `color.body`를 쓴다.
- 로고, 상표, 상품 사진, 홍보 문구는 쓰지 않는다. 아이콘은 직접 그린 도형이다.

**접근성**
- 화면을 다시 그려도 키보드 포커스, 스크롤 위치, 알림 영역을 유지한다. 터치 영역은 40px 이상이다(현황의 동기화 버튼만 TDS medium 규격인 38px이다).

## 제외
- 실제 얼굴 인식과 페이스페이 승인 연동. 화면 흐름만 재현한다.
- 실제 카드 승인. 토스페이먼츠 개발자 키 연동은 후속 작업이다. 이 화면의 결제는 결제 요청 접수까지다.
- 자리만 있는 기능: 할인, 분할 결제, 옵션, 메모, QR 결제, 계좌이체, 전화승인, 고객 화면의 현금, 쿠폰·포인트·선불권, 영수증, 직원 부르기, 언어 전환. 누르면 범위 밖이라고 알린다.
- 만들지 않은 화면: 상품 상세와 옵션 선택, 포인트 적립·사용, 고객 호출 방식 입력, 분할결제·할인 등록, 결제내역, 시재, 설정, 테이블 홈(후불형), 바코드(도소매), 예약(서비스업), 터미널(카드단말기).
- 단말 인증 연동. main에는 단말 토큰 인증(PR 81번)이 들어왔고 이 화면은 토큰을 싣지 않는다. 그래서 실서버 전송은 401로 거절되고 화면은 전송이 멈췄다고 알린다. 시연은 모의 모드(`?mock`)로 한다.
- 시각 디자인 다듬기. 후속 작업이다.
- Service Worker를 통한 오프라인 페이지 로딩. 페이지를 연 뒤에 끊기는 상황만 시연한다.

## 후속 작업
이 PR에 담지 않고 넘기는 일이다. 백엔드 변경은 모두 별도 컨텍스트라 각각 새 spec과 새 PR로 다룬다. 근거는 사용 가이드 204쪽 분석과 저장소 조사(모듈 구성, 공개 HTTP 입구, 제품 기획서의 비목표)다.

결정이 먼저 필요한 것:
1. 수단별 오프라인 결제의 의미. 지금은 오프라인에서 결제 요청을 쌓았다가 재연결 뒤 서버가 승인을 요청한다. 실물 카드는 고객이 떠난 뒤 승인할 수 없고 기획서는 카드 번호를 저장하지 않는다고 정했다. 현금은 단말에서 확정된 사실이라 오프라인에서 받아도 된다. 카드는 오프라인에서 막을지, 단말이 받은 승인 결과를 사실로 기록할지 정해야 한다.
2. 토스페이먼츠 연동의 범위. 토스페이먼츠는 온라인 결제 대행 API라 서버 쪽 승인 요청·조회·취소는 붙일 수 있지만 카드를 읽는 단말 결제는 이 경로로 시연할 수 없다.
3. 고객관리(고객, 포인트, 스탬프, 쿠폰, 선불권, 예약)를 범위에 넣을지. 기획서는 CRM을 비목표로 둔다. 넣으면 쿠폰·포인트·선불권이 결제 승인 전에 금액을 깎고 취소 때 되돌려야 해서 주문·결제 설계가 함께 바뀐다.

백엔드 후속(위 결정 뒤):
- 결제 수단과 단말 승인 결과를 받는 경로. 지금 게이트웨이 포트는 결제 식별자와 금액만 받는다. 이 화면이 현금으로 기록해도 서버는 똑같이 승인을 요청한다.
- 분할결제. 가이드는 한 주문에 결제 여러 건과 남은 금액을 다루는데 현재 모델은 한 checkout에 진행 중인 승인 시도가 하나다.
- 주문 속성: 주문 출처(포스·키오스크·배달·테이블주문), 주문번호, 매장·포장, 옵션, 할인. 지금은 단말의 로컬 기록에만 있다.
- 상품과 가격의 소유. 서버가 단말이 보낸 단가를 그대로 받는다. `store`가 상품을 가져야 검증할 수 있다.
- 조회와 취소 입구. 공개 HTTP 입구가 주문 생성, checkout, sync 셋뿐이라 현황의 서버 쪽 상태와 결제 취소를 보여줄 수 없다.

이 화면의 후속:
- 단말 인증 반영. PR 81번이 머지돼 sync 입구가 `Authorization: Bearer` 토큰을 요구한다. 이 화면의 실서버 전송은 지금 401로 거절된다. 단말을 등록해 토큰을 받는 HTTP 입구가 없어 화면만 고쳐서는 풀 수 없다. 시연용 단말을 등록하고 토큰을 화면에 넘기는 방법(시드 데이터, 등록 입구, `demo` 프로필 전용 설정 중 하나)을 정한 뒤 화면이 토큰을 싣게 한다. 그 전까지는 모의 모드(`?mock`)로만 시연할 수 있다.
- 키오스크의 독립. 지금은 키오스크 주문이 포스를 거쳐 포스의 단말 식별자로 접수돼, 포스가 꺼지면 키오스크도 주문을 받지 못한다. 실제 제품에는 포스 없이 쓰는 단독 키오스크가 있다. 키오스크가 자기 단말 식별자와 대기열을 갖게 한다.
- 기기 두 대 시연. 포스와 단말의 연결이 같은 브라우저의 두 창에 묶여 있다. 서버를 거치는 중계가 필요하다.
- 만들지 않은 화면: 상품 상세와 옵션 선택, 포인트 적립·사용, 고객 호출 방식 입력, 분할결제·할인 등록, 결제내역, 시재, 설정, 테이블 홈(후불형), 바코드(도소매), 예약(서비스업), 터미널(카드단말기).
- 디자인 다듬기와 실제 기기에서의 확인. 지금까지는 자동화 브라우저로만 확인했다.
- 단말 저장소. 지금은 localStorage다. 기획서는 로컬 DB를 말한다.
- 화면이 인라인 스크립트라 엄격한 CSP를 걸 수 없다. 인증이 들어올 때 이 경로를 허용할지 막을지도 함께 정한다.
- 주소로 받는 상대 주소를 같은 호스트로만 제한했다. 같은 호스트의 다른 포트에서 도는 서비스는 여전히 상대가 될 수 있다.
