# PR spec: Spring Boot를 4.1.2로 올리고 BOM 버전 재정의를 지운다

## 목적
[dependency-cves](2026-10-06-dependency-cves.md)(PR #85)는 Boot 4.1.1 BOM의 취약한 전이 의존성 셋을 `build.gradle.kts`의 `extra` 속성으로 덮어썼고, "세 줄 모두 Boot 4.1.2 이상으로 올리는 PR에서 지운다"는 다시 볼 조건을 남겼다. Boot 4.1.2 GA가 2026-10-22에 나왔다(GitHub release v4.1.2, Maven Central `spring-boot-dependencies` maven-metadata.xml에 4.1.2, 2026-10-23 확인). 이 PR은 Boot를 4.1.2로 올리고, 새 BOM이 CVE 수정 버전 이상을 담는 재정의를 지워 버전 결정을 BOM에 돌려준다.

## 범위
**결정 1: Boot 플러그인을 4.1.2로 올린다.** `id("org.springframework.boot") version "4.1.1"`을 4.1.2로 바꾼다. dependency-management 플러그인(1.1.7)과 Modulith BOM(2.1.1, PR #94가 2.1.2로 올린다)은 건드리지 않는다.

**결정 2: 재정의를 BOM과 비교해 고쳐진 것만 지운다.** `spring-boot-dependencies` 4.1.2 pom(2026-10-23 Maven Central)의 속성과 #85 주석의 수정 버전을 비교했다.

| 속성 | #85 재정의 | 4.1.1 BOM | 4.1.2 BOM | CVE 수정 버전 | 판정 |
|---|---|---|---|---|---|
| `tomcat.version` | 11.0.26 | 11.0.24 | 11.0.27 | 11.0.25 | 지운다. BOM이 재정의보다 높다 |
| `jackson-bom.version` | 3.1.7 | 3.1.5 | 3.1.7 | 3.1.7 | 지운다 |
| `kafka.version` | 4.2.2 | 4.2.1 | 4.2.2 | `lz4-java` 1.11.1(`kafka-clients` 4.2.2는 1.11.2) | 지운다 |

- 셋 다 수정 버전 이상이라 남길 줄이 없다. 재정의 셋과 묶음 주석, 그 뒤 빈 줄(23~31행)을 지운다. `dependencies {`(32행)와 Modulith BOM 줄(33행)은 손대지 않는다. PR #94의 hunk가 33행이라 겹치지 않게 하려는 것이다.
- 지운 뒤 기대하는 runtimeClasspath는 `tomcat-embed-core` 11.0.27, `jackson-core`·`jackson-databind` 3.1.7, `kafka-clients` 4.2.2, `lz4-java` 1.11.2다. Tomcat만 11.0.26에서 11.0.27로 바뀌고 나머지는 지금과 같다.
- (개발 중 범위 조정) runtimeClasspath를 OSV로 조회하자 `lz4-java` 1.11.2에 #85 머지 뒤(2026-10-07) 공개된 CVE 3건이 나왔다. 바꾸기 전 빌드에도 같은 3건이 있어 이 PR이 들인 것이 아니다. 고친 1.11.4를 쓰는 `kafka-clients` 4.2.x 배포판이 아직 없다(4.2.2가 최신이다. apache/kafka의 KAFKA-21174는 trunk(#23609)와 4.3 브랜치(#23767)에만 머지됐고 4.2 브랜치의 `gradle/dependencies.gradle`은 1.11.2다). 사용자와 대조해 이 PR에서는 고정하지 않고 기록만 남기기로 했다. 근거와 노출 범위는 결과 절에 적는다.

**결정 3: Kafka 작업 규칙을 적용한다.** `kafka-clients`는 4.2.2 그대로지만 Spring Kafka가 4.1.1에서 4.1.2로, `spring-boot-kafka`가 4.1.2로 바뀐다. 그래서 릴리스 노트와 sources jar로 대조하고, 기동 로그의 클라이언트 설정 값을 비교하고, Modulith·Kafka 키워드 문서를 갱신 규칙대로 고친다.

- 기준값: 바꾸기 전 빌드(Boot 4.1.1 + 재정의 셋)로 `KafkaRetryIntegrationTest`·`KafkaEventDeliveryIntegrationTest`·`EventPublicationResubmitterIntegrationTest`·`EventPublicationResubmitSelectedIntegrationTest`를 돌려 결과 XML을 보관했다(4개 클래스 통과). 바꾼 뒤 같은 테스트의 `ProducerConfig`·`ConsumerConfig`·`AdminClientConfig values`를 같은 방식(#85와 같이 `client.id`·`group.id`·`bootstrap.servers`·`group.instance.id` 제외)으로 뽑아 비교한다.
- 공식 근거: [Spring for Apache Kafka v4.1.2 release](https://github.com/spring-projects/spring-kafka/releases/tag/v4.1.2), Boot 4.1.2 release의 "Upgrade to Spring Kafka 4.1.2"(spring-boot#51965), `spring-kafka`·`spring-boot-kafka` 4.1.1·4.1.2 sources jar 비교(주석·빈 줄을 뺀 코드 비교, 2026-10-23).

**4.1.1에서 4.1.2로 바뀐 것 중 이 저장소에 닿는 것.** 출처는 각 프로젝트의 GitHub release와 milestone, BOM pom 비교다.

| 대상 | 버전 | 이 저장소에 닿는 변경과 판단 |
|---|---|---|
| Spring Kafka | 4.1.1 → 4.1.2 | #4818(gh-4780): 기본 `BackOff`가 재시도 0이면 `setBackOffFunction`을 부르지 않던 버그 수정. #4760(gh-4754): `ExponentialBackOffWithMaxRetries(0)`이 한 번 재시도하던 버그 수정. `kafkaErrorHandler`는 `ExponentialBackOffWithMaxRetries(max-retries)`를 기본으로 두고, 원인 체인에 커넥션 획득 실패(`CannotCreateTransactionException`·`DataAccessResourceFailureException`)가 있으면 함수로 무제한 `ExponentialBackOff`를 고른다. 기본값 `max-retries=5`에서는 첫 `nextBackOff()`가 시작 간격이라 두 버전이 같다. `resilientpos.kafka.retry.max-retries`를 0 이하로 둘 때만 달라진다. (1) 경합 실패는 4.1.1이 한 번 더 시도했고 4.1.2는 바로 DLT로 보낸다. (2) 첫 실패가 커넥션 획득 실패면 두 버전 모두 무제한 대기다(4.1.1은 재시도가 남아 함수가 불렸고 4.1.2는 #4818로 불린다). (3) 처리 도중 연결이 끊겨 `JpaSystemException`·`TransactionSystemException`으로 온 실패는 경합으로 분류된다. 4.1.1은 #4760 버그로 한 번 더 시도했고 그 시도에서 커넥션 획득이 실패하면 예외가 바뀌어 무제한 대기로 넘어갔다. 4.1.2는 바로 DLT로 보낸다. 그래서 0 이하로 두면 `KafkaConfiguration` KDoc이 막으려던 "DB 장애 동안 DLT에 쌓임"이 생긴다. 기본값이 아니고 배포 설정에서도 쓰지 않아 코드는 바꾸지 않고, 키워드 문서의 `BackOff` 항목에 적는다 |
| Spring Kafka | 〃 | #4757: 예외 분류 캐시(`ExceptionMatcher`)가 `HashMap`에서 `ConcurrentHashMap`으로 바뀌었다. `kafkaErrorHandler` 빈 하나를 listener 다섯 개의 consumer 스레드가 함께 쓰고 분류 결과를 캐시에 넣으므로 이 저장소 경로에 닿는 개선이다. 코드 변경은 없다 |
| Spring Kafka | 〃 | #4683(gh-4622): stop이나 다른 스레드의 ack가 남긴 wakeup이 다음 `commitSync`를 중단시키고 그 offset을 다시 커밋하지 않던 버그 수정(`commitIfNecessary`가 한 번 다시 커밋). 이 저장소는 ack 모드가 기본값(BATCH)이고 stop 말고 wakeup을 부르는 경로가 없다. 앞 batch의 offset은 poll 루프 맨 앞(`doProcessCommits`)에서 커밋되고 stop 경쟁이면 poll 결과를 버리고 돌아가므로 닿는 경우가 드물다. 닿아도 재시작 뒤 같은 레코드가 다시 오는 것이고 consumer는 멱등이라 계약은 같다 |
| Spring Kafka | 〃 | #4830: `KafkaTemplate.receive`가 없는 offset에서 다른 offset 레코드를 돌려주던 버그 수정. DLT 재투입(`DeadLetterReader`)은 `KafkaTemplate.receive`를 쓰지 않고 자기 consumer로 읽은 뒤 offset을 직접 비교하므로 닿지 않는다. #4826: `KafkaAdmin`이 토픽 설정 변경을 한 번에 모아 보내고 오류 문구가 바뀐다. DLT의 `retention.ms=-1` 맞춤 동작은 같다 |
| Spring Kafka | 〃 | 그 밖(share consumer, `@RetryableTopic`, batch·async·suspend listener, `ReplyingKafkaTemplate`, Streams, 헤더 매퍼의 multi-value·역직렬화 예외 헤더)은 이 저장소가 쓰지 않는다. listener는 다섯 개 모두 레코드 단위 동기 `@KafkaListener`다 |
| spring-boot-kafka | 4.1.1 → 4.1.2 | 코드 변경은 `KafkaProperties`의 `@SuppressWarnings` 한 줄뿐이다. 클라이언트 설정 값이 바뀔 이유가 없고 결정 3의 비교로 확인한다 |
| Spring Framework | 7.0.9 → 7.0.10 | #37207: `@Scheduled` 작업을 취소할 때 쓰는 키를 프록시가 아닌 대상 빈(`ultimateSingletonTarget`)으로 바꿔 빈 소멸 때 작업이 취소되게 했다. 실행은 여전히 프록시를 거친다(`EventPublicationResubmitter` 등 `@Scheduled` 빈). #37406: 일시 정지된 executor가 늦은 종료에서 스레드를 놓던 문제 수정(테스트 컨텍스트 재사용, PR #110). #37300: non-suspend Kotlin 함수의 `MethodParameter`에서 Kotlin reflection을 쓰지 않는다. `submit(Callable)`의 타입 파라미터에 `@Nullable` 경계가 붙었다. 모두 동작 계약을 바꾸지 않고 전체 테스트로 확인한다 |
| Spring Security | 7.1.1 → 7.1.2 | 닿는 것이 없다. `BearerTokenAuthentication`(opaque token)·OAuth2 client·reactive 수정이 대부분이고, 운영자 체인은 JWT(`JwtAuthenticationToken`)다. password encoder 검증의 spring-core 의존 제거는 내부 변경이다. "Downgrade to Jackson 3.1"은 Security 자체 빌드의 Jackson 선언이고 이 저장소의 Jackson은 BOM이 3.1.7로 정한다 |
| Boot OAuth2 resource server | 4.1.1 → 4.1.2 | #52260: issuer 검증기 조건이 `issuer-uri != null`에서 값이 있을 때로 바뀌었다. `AdminSecurityFilterChain`이 `issuer-uri`가 비면 기동을 멈추므로 닿지 않는다. #51630(`authorities-claim-delimiter` 단독 설정)·#51562(`authorities-claim-expressions` setter 이름)은 쓰지 않는 속성이다 |
| Spring Data Redis | 4.1.1 → 4.1.2 | Stream `TrimOptions.equals` 수정과 reactive `HSTRLEN` 추가뿐이다. 이 저장소는 Stream과 reactive Redis를 쓰지 않는다. Lettuce(7.5.2)와 Spring Session(4.1.1)은 그대로다 |
| Spring Data JPA·Hibernate | 4.1.1 → 4.1.2, Hibernate 7.4.5 → 7.4.13 | HQL `%` 연산자·JPQL escape 리터럴 수정과 Hibernate 패치 여덟 개 올림이다. Kotlin JDSL이 만든 JPQL도 Hibernate가 파싱하므로 쿼리 형태로 영향을 배제하지 않고, 조회·낙관적 잠금·INSERT 횟수·soft delete를 다루는 전체 테스트로 확인한다. 볼트 rule `domain-modeling-kotlin.md` §5의 "Hibernate 7.4.5는 DB가 만든 값을 읽느라 갱신 행 수 검사를 건너뛴다"는 7.4.13에서 다시 확인하지 않았다. 그 rule은 DB가 만드는 시각 값을 쓰지 않는다는 금지라 버전과 관계없이 그대로다 |
| Testcontainers | 2.0.5 그대로 | testRuntimeClasspath에서 변경 없음. Kafka 브로커 이미지(`apache/kafka:4.1.0`)도 그대로다 |
| 그 밖 | Micrometer 1.17.2, PostgreSQL JDBC 42.7.14, Netty 4.2.19, Jackson 2 BOM 2.21.7 | 패치 올림이다. 전체 테스트로 확인한다 |

**결정 4: 현재 버전을 적은 문서를 고친다.** `README.md` 기술 스택 표의 Boot 버전, `docs/wiki/event-contract.md`의 "Boot 4.1.1은 Jackson 3 기본값을 그대로 쓴다"를 4.1.2로 바꾼다. 뒤 문장은 `EventContractCompatibilityTest`가 4.1.2에서 통과하는 것으로 확인한다. 다른 문서의 "4.1.1 소스로 확인" 같은 인용은 확인 당시 버전이라 그대로 둔다.

## 제외
- Spring Boot 4.2.x와 Jackson 3.2.x·Kafka 4.3.x 같은 마이너 올림.
- Spring Modulith 2.1.2 올림. PR #94가 한다.
- Kafka 브로커 이미지(`apache/kafka:4.1.0`) 변경.
- `max-retries`를 0 이하로 둘 때의 동작 고정 테스트와 값 검사. 기본값이 아니고 배포 설정에서도 쓰지 않는다. 4.1.2에서는 처리 도중 연결이 끊긴 실패가 바로 DLT로 가므로 키워드 문서에 적어 두고, 0 이하를 막는 검사가 필요해지면 그 값을 쓰려는 PR에서 정한다.
- `lz4-java` 1.11.4 고정. Boot BOM이 `lz4-java`를 관리하지 않아 `extra` 속성이 아니라 Gradle constraint가 필요하고, `kafka-clients` 4.2.2와 1.11.4는 Kafka가 검증한 조합이 아니다. Boot BOM이 1.11.4 이상을 쓰는 `kafka-clients`를 가져오면 그 Boot 패치로 올리는 PR에서 다시 본다. Kafka 4.2 브랜치에는 아직 수정이 없어 Boot 4.1.x 패치로 언제 풀릴지 알 수 없다. 그 전에 고정이 필요해지면 따로 정한다.
- 의존성 취약점 자동 검사(OSV·Dependabot) 도입.

## 인수 조건
- `build.gradle.kts`의 Boot 플러그인이 4.1.2이고 `extra["tomcat.version"]`·`extra["jackson-bom.version"]`·`extra["kafka.version"]`과 그 주석이 없다. 다른 줄은 바뀌지 않는다.
- `./gradlew dependencyInsight --configuration runtimeClasspath`가 `tomcat-embed-core` 11.0.27, `jackson-core`·`jackson-databind` 3.1.7, `kafka-clients` 4.2.2, `lz4-java` 1.11.2를 보이고, 그 버전이 4.1.2 BOM 값(또는 BOM이 관리하는 `kafka-clients`가 요청한 값)과 같다. (개발 중 고침) 처음에는 "selected by rule"이 없어야 한다고 적었지만 이 표시는 dependency-management 플러그인이 BOM 버전을 resolution rule로 적용할 때마다 붙어 재정의 여부를 가리지 못한다.
- runtimeClasspath 좌표를 `https://api.osv.dev/v1/querybatch`로 조회해 #85의 CVE 11건이 다시 나오지 않는다. 다른 취약점이 나오면 좌표와 ID를 결과에 적고 이 PR에서 고칠지 판단한다.
- 바꾸기 전후 runtimeClasspath에서 버전이 바뀐 좌표를 결과에 적는다.
- `./gradlew test` 전체가 통과한다.
- 바꾸기 전후 Kafka 통합 테스트의 클라이언트 설정 값 차이를 결과에 적는다. 차이가 재시도·DLT·재전송에 닿으면 그 영향을 적는다.
- Modulith·Kafka 키워드 문서(볼트)의 버전 줄·`BackOff`·`setBackOffFunction` 항목·`updated`·출처를 갱신 규칙대로 고친다.
- `python3 scripts/check_pr.py --base origin/main`이 통과한다.

## 검증
- `./gradlew -q dependencyInsight --configuration runtimeClasspath --dependency` 뒤에 `tomcat-embed-core`, `jackson-core`, `jackson-databind`, `kafka-clients`, `lz4-java`를 차례로 넣는다. 실패 시나리오는 해석된 버전이 수정 버전보다 낮거나 기대값과 다른 것, 또는 `build.gradle.kts`에 `extra` 재정의가 남은 것이다.
- `./gradlew -q dependencies --configuration runtimeClasspath`를 바꾸기 전 출력과 비교하고, 좌표를 뽑아 OSV querybatch(ecosystem Maven)로 조회한다.
- `./gradlew test`.
- Kafka 통합 테스트 결과 XML의 system-out에서 클라이언트 설정 값을 뽑아 바꾸기 전 값과 비교한다.
- `python3 scripts/check_pr.py --base origin/main --worktree`, 제출 전에는 `--worktree` 없이.

## Wiki 영향
- 요구사항 변화는 없다. 라이브러리 버전과 그 근거만 바뀐다.
- `docs/wiki/event-contract.md`: Jackson 3 기본값 문장의 Boot 버전을 4.1.2로 바꾼다.

  - 남기는 이유: 고친 버전을 쓰는 `kafka-clients` 4.2.x 배포판이 없다. Maven Central에서 4.2.2가 4.2.x 최신이고, pom의 `lz4-java`는 4.2.2·4.4.0이 1.11.2, 4.3.2만 1.11.4다. 4.3.x·4.4.0은 마이너 올림이다. MODERATE(`LZ4FrameInputStream`이 프레임마다 버퍼를 다시 잡음)와 LOW(`LZ4BlockInputStream`의 빈 블록 재귀)는 `kafka-clients`가 쓰지 않는 클래스다. `kafka-clients` 4.2.2는 lz4 프레임을 자기 `Lz4BlockInputStream`·`Lz4BlockOutputStream`으로 다루고, lz4-java에서는 factory로 얻는 compressor·decompressor·`XXHash32`와 유틸(`LZ4Exception`·`SafeUtils`)만 쓴다(sources jar). HIGH(native 라이브러리를 공유 tmp에 풀 때 다른 로컬 사용자가 바꿔치기)는 `LZ4Factory.fastestInstance()`가 처음 불릴 때 일어난다. 그 호출은 `kafka-clients`의 `Lz4BlockInputStream`·`Lz4BlockOutputStream` 정적 초기화에 있어 lz4로 압축된 batch를 보내거나 받을 때 처음 불린다. 보내는 쪽은 이 저장소의 producer가 `compression.type = none`(기동 로그)이라 lz4를 쓰지 않는다. 받는 쪽은 토픽에 lz4 batch가 들어올 때인데, 토픽은 `KafkaAdmin`이 `compression.type` 없이 만들어 브로커 기본값(`producer`, 받은 압축 그대로 보관)을 따르고 쓰는 producer는 이 앱(externalization·DLT 전송·DLT 재투입)뿐이다. 그래서 다른 producer가 lz4로 쓰거나 운영에서 토픽·브로커의 `compression.type`을 lz4로 바꾸지 않는 한 불리지 않는다. 공격에는 그에 더해 같은 호스트의 `java.io.tmpdir`에 쓸 수 있는 다른 로컬 사용자가 필요하다.
