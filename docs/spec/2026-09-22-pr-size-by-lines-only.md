# PR spec: PR 크기를 줄 수로만 재고 스택 대신 독립 범위를 기본값으로 둔다

## 목적
한도가 두 가지 서로 다른 이유로 걸렸는데 그중 하나는 리뷰 부담과 무관했다.

- [contract-module-for-cross-module-events](2026-09-22-contract-module-for-cross-module-events.md)는 361줄짜리 패키지 이동인데 파일 25개에서 하드 상한에 걸렸다. 파일 대부분이 import 한두 줄 수정이라 리뷰 부담이 거의 없는데도 막혔고, 리뷰가 요구한 한 줄 수정을 빼야 통과했다.
- [payment-attempt-from-order-event](2026-09-22-payment-attempt-from-order-event.md)는 17파일 684줄로 줄 수 쪽에 근접했다. 이쪽은 실제로 리뷰가 무거웠다.

파일 수는 리뷰 비용을 재지 못한다. 같은 25개 파일이 한 줄씩 바뀐 것과 서른 줄씩 바뀐 것은 전혀 다른 일인데 지금 게이트는 둘을 같게 본다. 줄 수만 본다.

한도가 낮아서 생긴 두 번째 비용은 stacked PR이다. #43 → #44 → #45 → #46이 연달아 쌓였고, 앞 PR이 squash 머지될 때마다 뒤 PR의 base가 사라져 매번 `--onto` 리베이스가 필요했다. 분할이 리뷰를 쉽게 만든 만큼 머지를 어렵게 만들었다.

## 범위
**한도를 줄 수로만 판정한다.** `scripts/check_pr.py`의 일반 변경 게이트에서 파일 수 조건을 뺀다. 파일 수는 통계 줄에 계속 출력해 사람이 보게 두되 통과/실패를 가르지 않는다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 경고 | 600줄 또는 20개 파일 | 900줄 |
| 실패 | 800줄 또는 25개 파일 | 1400줄 |

`docs/references/` 원문 보관 한도(10개 파일 / 5000줄)는 그대로 둔다. 그 한도는 리뷰 부담이 아니라 한 번에 들어오는 외부 원문의 양을 제한하는 것이고, 파일 수가 그 양을 직접 나타낸다.

**다음 작업을 고를 때 독립 범위를 기본값으로 둔다.** [개발 워크플로](../wiki/development-workflow.md)에 판단 순서를 적는다. 열린 PR이 건드리는 경로를 피할 수 있으면 그쪽을 먼저 하고, 피할 수 없으면 쌓지 말고 한 PR로 합친다. 스택은 합쳐서 실패 한도를 넘을 때만 쓴다.

계약: 검사기의 판정 기준이 바뀐다. 지금까지 통과한 PR은 전부 새 기준에서도 통과한다 — 줄 수 한도만 올라갔고 파일 수 조건은 사라지기만 했다. 저장 형식도 API도 건드리지 않는다.

복구: 해당 없음.

관측성: 해당 없음.

## 제외
- 원문 보관 한도 변경.
- 한도를 CI에서 강제하는 것. 지금도 로컬 명시 실행이고 이 PR이 그 성질을 바꾸지 않는다.
- spec 첫 커밋·필수 항목·선언 경로 검사. 그대로다.
- 볼트의 orchestrator·git 스킬 본문. 저장소 wiki가 한도의 정본이고 스킬은 그것을 참조한다.
- 이미 열린 PR의 범위를 다시 합치는 것. 이 규칙은 다음 작업부터 적용한다.

## 인수 조건
1. 파일 수가 25개를 넘고 줄 수가 한도 안이면 통과한다.
2. 줄 수가 1400을 넘으면 실패한다.
3. 줄 수가 900 이상 1400 이하이면 경고한다.
4. 통계 줄에 파일 수가 계속 나온다.
5. 원문 보관 한도는 그대로 동작한다.
6. 기존 검사(spec 첫 커밋, 필수 항목, 선언 경로, Flyway 버전)가 그대로 동작한다.

## 검증
- `python3 scripts/check_pr.py --base origin/main --worktree` — PASS.
- `python3 scripts/test_check_pr.py` — 전부 통과. 하네스 테스트가 새 경계(900 경고 / 1401 실패)와 파일 40개가 통과한다는 사실을 고정한다.
- 실제 PR diff로도 확인한다. 파일 32개·1027줄이던 `#44~#46` 합산 범위가 FAIL에서 WARN으로 바뀌는지 본다.

## Wiki 영향

## 분할 계획
예상 3개 파일 / 100줄 안팎. 한도 안이다.

## TDD 검증 기록
검사기의 판정이 바뀌는 지점을 먼저 관측한다.

RED를 실제 입력으로 관측했다. `#44`의 머지 커밋을 base로 두고 contract 브랜치를 넣으면 32개 파일 / 1027줄이 나온다 — `#44`부터 `#46`까지를 한 PR로 묶었을 때의 크기다. 바꾸기 전에는 `PR 상한 25개 파일/800줄 초과`로 FAIL이었고, 바꾼 뒤 같은 입력이 `900줄 도달` 경고로 바뀌었다.

| 동작 / 테스트 이름 | RED 명령·실패 이유 | GREEN 명령·결과 | 리팩터링 후 회귀 명령·결과 |
|---|---|---|---|
| 파일 수는 판정하지 않는다 | `test_file_limit` — 파일 26개에 `800줄 초과` FAIL을 단언 | `test_file_count_does_not_fail`로 바꿔 파일 40개에 오류·경고 없음을 단언 — 통과 | `python3 scripts/test_check_pr.py` 115개 통과 |
| 1401줄이면 실패 | 바꾸기 전 — 800줄에서 이미 FAIL이라 새 경계를 관측할 수 없음 | `test_size_and_warning`이 900 경고·1401 실패를 단언 — 통과 | 같음 |
| 실제 PR 범위 | `--base f2c0893` contract 브랜치 — 32개 파일/1027줄로 FAIL | 같은 명령 — WARN | 같음 |
