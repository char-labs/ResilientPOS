# PR spec: PR 검사기가 실제로 규칙을 강제하게 한다

## 목적
전체 코드 감사에서 로컬 PR 검사기의 우회 경로 다섯 개를 찾아 전부 재현했다. 규칙은 문서에 있지만 검사가 잡지 못하므로 실질적으로 강제되지 않는다. 특히 Flyway 버전 중복은 CI가 강제하는 유일한 규칙인데 세 가지 경로로 빠져나간다.

재현한 것은 다음과 같다.
- `V005__dup.SQL`, `V005__sub/dup.sql`, `V005__Dup.kt` 중 무엇을 추가해도 버전 중복 검사가 통과한다. 배포하면 Flyway가 기동에서 죽는다.
- spec의 변경 경로에 별표 하나만 적으면 범위 검사가 무력화된다. `fnmatch`의 별표가 경로 구분자를 넘기 때문이다.
- 같은 이름의 절을 문서 끝에 한 번 더 쓰면 뒤엣것이 이긴다. 리뷰어는 앞 절을 읽고 검사기는 뒤 절을 쓴다.
- 하네스 테스트 파일을 직접 실행하면 96개 중 16개만 돌고 OK를 찍는다. Flyway 게이트와 스키마 검토 게이트의 회귀를 놓친다.
- 마이그레이션 파일명만 바꾸면 해결할 수 없는 실패가 난다. 옛 이름과 새 이름을 같은 버전의 중복으로 보기 때문이다.

## 범위
- 소유: 개발 하네스(`scripts/`)와 개발 규칙 문서. 애플리케이션 코드는 바꾸지 않는다.
- **마이그레이션 인식을 한 정의로 모은다.** 지금 `MIGRATION`과 `SCHEMA_CHANGE`가 "Flyway가 읽는 경로"를 서로 다르게 정의한다. 버전 추출을 `SCHEMA_CHANGE`가 인정한 경로에서만 하도록 바꿔서, 스키마 검토를 요구하는 경로와 버전 중복을 보는 경로가 같아지게 한다. 확장자 대소문자, 하위 디렉터리, Java·Kotlin 마이그레이션이 모두 버전 검사 대상이 된다. 버전이 없는 반복 마이그레이션(`R__`)은 그대로 대상이 아니다.
- **변경 경로 glob에서 별표가 경로 구분자를 넘지 않게 한다.** 별표 하나는 한 경로 조각 안에서만 매칭하고, 별표 둘은 여러 조각을 넘는다. `docs/**`처럼 지금 쓰는 패턴의 뜻은 바뀌지 않는다. Python 3.9라 표준 라이브러리에 이 동작이 없어서 glob을 정규식으로 옮기는 함수를 둔다.
- **같은 이름의 절이 둘이면 거절한다.** 어느 쪽을 쓸지 고르지 않고 spec을 고치게 한다.
- **절 판정을 코드 블록 밖에서만 한다.** 지금 필수 절 판정은 코드 블록 안의 제목을 인정하는데, 같은 파일의 스키마 검토 판정은 코드 블록을 먼저 지운다. 두 판정의 기준을 맞춘다.
- 문서 끝에 개행이 없는 절. 감사에서 결함으로 봤지만 확인 결과 이미 정상이었다. 마지막 절의 제목 뒤에는 개행이 있고 본문 뒤에만 없는 것이 실제 모양이라 판정에 영향이 없다. 고치지 않고 회귀 테스트만 남긴다.
- **이 PR이 지운 파일은 버전 중복 판정에서 뺀다.** 파일명만 바꾸는 변경이 통과하게 한다. 기준 브랜치에 나중에 머지된 마이그레이션과의 중복은 그대로 잡는다.
- **하네스 테스트의 `unittest.main()`을 파일 끝으로 옮긴다.** 파일을 직접 실행해도 모든 테스트가 돌게 한다.
- **자동으로 머지를 막는 장치가 없다는 사실을 개발 규칙에 적는다.** 브랜치 보호 API가 `403 Upgrade to GitHub Pro`를 돌려준다. 지금 문서는 "브랜치 보호 설정은 아직 쓰지 않는다"고 적어 선택처럼 읽히지만 실제로는 설정할 수 없다. 코드로 고칠 수 없는 항목이라 사실만 기록한다.
- 검사기 자신의 변경이므로 저장소 규칙대로 우회 경로가 없는지 리뷰가 따로 본다. 각 수정에 우회를 시도하는 테스트를 함께 둔다.

### 합의한 결정 (2026-09-21)
- 감사에서 나온 결함 중 이 PR은 하네스만 다룬다. 금액 상한은 목표가 달라서 앞선 PR로 냈다. 합치면 약 660줄로 경고 한도를 넘고, 저장소 규칙도 하네스 변경을 따로 리뷰하라고 정한다.

### 범위 조정 (2026-09-21, 제출 전 리뷰 반영)
검사기 자신의 변경이라 저장소 규칙대로 우회를 따로 검증받았다. 독립 검증자가 임시 저장소에서 우회를 다시 시도했고, `reviewer-claude`가 거짓 실패 위험을 기존 spec 전수로 확인했다(변경 경로 패턴 117개와 머지된 PR 29개를 재생해 옛 매처와 판정이 모두 같았다). 아래를 반영한다.
- **`- **` 한 줄이면 범위 검사가 그대로 무력화된다.** 별표 하나를 막았더니 별표 둘로 되살아났다. 리터럴 문자가 하나도 없는 패턴을 거절한다.
- **닫히지 않은 코드 블록이 절 판정을 뚫는다.** 여는 표시만 있고 닫는 표시가 없으면 아무것도 지워지지 않아, 코드 블록 안 제목이 다시 절로 인정되고 스키마 검토 답까지 통과한다. 여는 표시 뒤가 문서 끝까지 코드 블록인 것으로 본다.
- **본문이 코드 블록뿐인 필수 절이 미작성으로 거짓 실패한다.** 코드 블록을 지운 문자열로 본문까지 판정했기 때문이다. 절의 위치만 코드 블록 밖에서 찾고 본문은 원문 그대로 쓴다. `검증` 절에 명령만 적는 spec이 막히지 않는다.
- **최상위 `src/` 밖의 마이그레이션이 버전 검사에서 빠졌다.** 옛 `MIGRATION`은 경로 어디에 있든 잡았는데 `SCHEMA_CHANGE`에 종속시키면서 좁아졌다. 멀티모듈로 나누면 CI가 강제하는 유일한 규칙이 조용히 꺼진다. 앵커를 완화해 되돌린다.
- **`--migrations-only`의 `merge-base` 호출이 새 실패 모드다.** 얕은 클론이나 공통 조상이 없는 경우 게이트가 버전 충돌이 아닌 이유로 빨개진다. 실패하면 이 PR 이전 동작으로 되돌아가도록 감싼다.
- **`test_renaming_still_detects_a_real_conflict_on_base`가 이름이 말하는 것을 검증하지 않는다.** 충돌하는 두 파일이 모두 변경 뒤 트리에 있어서 제외 로직과 무관하게 통과한다. 기준 브랜치가 merge-base 이후로 전진한 경우로 고친다.
- 절 이름의 앞뒤 공백을 정규화한다. 공백 한 칸 차이로 중복 판정을 피할 수 있었다.
- 쓰이지 않는 테스트 helper를 지운다.
- `AGENTS.md`의 부등호 서술을 고친다. 코드 블록 밖에 있을 때만 미작성으로 판정하도록 바뀌었다.
- 사실 정정 둘. spec의 범위가 존재하지 않는 수정을 주장했다(위 "문서 끝에 개행"). 그리고 [개발 규칙](../wiki/development-workflow.md)의 다른 문단이 브랜치 보호가 켜져 있다는 전제로 쓰여 있어 이 PR이 새로 적는 사실과 모순이다. 함께 고친다.

## 제외
- 브랜치 보호를 실제로 켜는 것. 저장소 플랜에서 불가능하다. 저장소를 공개로 바꾸거나 플랜을 올리는 것은 이 PR이 정할 일이 아니다.
- CI가 spec 첫 커밋·필수 절·크기·wiki 기록까지 검사하게 하는 것. 지금 워크플로가 버전 중복만 보는 것은 "머지 결과 위에서 판정이 달라진다"는 기존 결정이다. 다시 보려면 그 결정부터 다뤄야 한다.
- 대조 기록이 실제로 구현자가 아닌 사람의 것인지 확인하는 것. 문서가 이미 한계로 인정했다.
- spec 본문의 내용이 실제로 채워졌는지 판정하는 것. 지금은 부등호 여는 문자만 placeholder로 본다. 마침표 하나로도 통과하지만, 내용의 품질은 리뷰가 본다는 기존 결정이다.
- `docs/references/`의 별도 한도에 내용 검사를 더하는 것.
- 하네스 테스트의 중복 실행(기반 클래스를 상속해 같은 테스트가 네 번 돈다). 실행 시간 문제이고 판정에는 영향이 없다.
- `V2`와 `V2.0`을 같은 버전으로 보는 것. 검사기는 다른 버전으로 본다. Flyway가 뒤쪽 0을 무시하는지 확인하지 못했고, 이 PR 이전부터 같은 동작이라 여기서 바꾸지 않는다.
- `spring.flyway.locations`를 바꿔 마이그레이션을 `db/migration` 밖으로 옮기는 경우. 경로로 알 수 없어서 두 판정이 함께 꺼진다. 기존 한계이고 개발 규칙이 이미 적고 있다.
- glob의 문자 클래스(`[0-9]` 같은 것). `fnmatch`는 받았지만 새 매처는 리터럴로 본다. 쓰는 spec이 없고, 쓰면 조용히 통과하는 게 아니라 범위 밖으로 시끄럽게 실패한다.
- `**`가 디렉터리 0단계를 매칭하지 않는 것(`docs/**/x.md`가 `docs/x.md`를 매칭하지 않는다). `fnmatch`도 같아서 회귀가 아니고, 지금 쓰는 패턴은 전부 끝에 붙는 형태라 영향이 없다.
- 스크립트의 성능(파일마다 `git show`를 띄우는 것, 매 실행 `ndiff`를 도는 것).

## 인수 조건
1. `src/main/resources/db/migration/V005__dup.SQL`, `src/main/resources/db/migration/sub/V005__dup.sql`, `src/main/kotlin/db/migration/V005__Dup.kt`를 각각 추가하면 기준 브랜치의 `V005`와 버전 중복으로 잡힌다. 지금은 셋 다 통과한다.
2. 반복 마이그레이션(`R__`)은 버전이 없으므로 중복 대상이 아니다. `docs/` 아래의 예시 SQL도 대상이 아니다.
3. 변경 경로에 별표 하나만 적은 spec은 경로에 구분자가 있는 파일을 범위 밖으로 잡는다. `docs/**`는 `docs/wiki/deep/x.md`를 지금처럼 범위 안으로 본다. `scripts/*.py`는 `scripts/check_pr.py`를 범위 안으로, `scripts/sub/x.py`를 범위 밖으로 본다.
4. 같은 이름의 `##` 절이 둘 있는 spec은 그 사실을 알리는 오류로 거절한다.
5. 코드 블록 안에만 있는 `## 결과`는 절로 인정하지 않는다.
6. 마지막 절 뒤에 개행이 없는 spec도 모든 절을 인식한다.
7. 마이그레이션 파일명만 바꾸는 변경은 버전 중복으로 잡히지 않는다. 기준 브랜치에 같은 버전이 따로 있으면 여전히 잡힌다.
8. `python3 scripts/test_check_pr.py`로 직접 실행하면 그 파일의 테스트가 전부 돈다(`discover`가 그 파일에서 세는 수와 같다). 지금은 16개만 돈다.
9. 기존 하네스 테스트 96개가 그대로 통과한다.
10. (범위 조정) 변경 경로에 `- **`처럼 리터럴이 없는 패턴만 있으면 거절한다.
11. (범위 조정) 닫히지 않은 코드 블록 안의 제목은 절이 아니고, 그 안의 스키마 검토 답도 인정하지 않는다.
12. (범위 조정) 본문이 코드 블록뿐인 필수 절은 미작성이 아니다.
13. (범위 조정) 최상위 `src/` 밖의 마이그레이션도 버전 중복 대상이다.
14. (범위 조정) 기준 브랜치가 merge-base 이후로 전진해 같은 버전이 생기면, 이 PR이 파일명을 바꿨더라도 중복으로 잡는다.

## 결과
- 인수 조건 1~14를 충족했다. `python3 -m unittest discover -s scripts -p 'test_*.py'`는 129개 중 실패 0이고, `python3 scripts/test_check_pr.py`는 120개가 돈다(고치기 전에는 16개였다). 애플리케이션 회귀로 `./gradlew test` 103개도 통과했다.
- 막은 우회는 일곱 가지다. 마이그레이션 인식 세 경로, 변경 경로의 별표 하나와 별표 둘, 절 이름 중복, 닫히지 않은 코드 블록이다. 없앤 거짓 실패는 둘이다. 마이그레이션 파일명 변경과 본문이 코드 블록뿐인 절이다.
- 리뷰가 잔여 우회 둘을 찾았다. 별표 하나를 막았더니 `- **`로 되살아났고, 닫히지 않은 코드 블록은 아무것도 지우지 못해 판정을 그대로 뚫었다. 첫 구현만으로는 목적에 적은 문제가 절반만 닫혔다.
- 리뷰가 새 회귀 둘도 찾았다. 코드 블록을 지운 문자열로 본문까지 판정해 명령만 적은 절이 미작성이 될 뻔했고, 경로 정의를 통합하면서 최상위 `src/` 밖의 마이그레이션이 검사에서 빠졌다. 둘 다 이 PR이 만든 것이라 함께 고쳤다.
- 거짓 실패가 없는지 전수로 확인했다. 머지된 spec에서 모은 변경 경로 패턴 117개를 저장소 파일 140개에 대입해 옛 `fnmatch`와 새 매처의 판정이 달라진 조합이 0건이었다. 리뷰어는 머지된 PR 29개를 실제 변경 파일로 재생해 같은 결론을 냈다.
- 사실 정정 둘을 함께 했다. spec의 범위가 존재하지 않는 수정을 주장했고(문서 끝 개행), 과거 spec이 기록한 "브랜치 보호를 켰다"가 지금 사실이 아니다. 브랜치 보호 API는 `403 Upgrade to GitHub Pro`를 돌려주고 저장소는 private이다. spec은 이력이라 고치지 않고 개발 규칙의 서술만 맞췄다.
- 코드로 고칠 수 없는 항목 하나는 기록만 했다. 지금 머지를 자동으로 막는 장치는 없다.
