# PR spec: 시연 포스 화면을 실제 토스 포스 배치에 맞춰 다듬고 결제 완료로 읽히는 문구를 바로잡는다

## 목적
[오프라인 결제 시연 화면](2026-10-05-terminal-demo-ui.md)(PR 82번)은 사용 가이드와 공개 캡처를 근거로 만들었다. 실제로 실행되는 토스 포스(macOS 앱 `im.toss.pos`)를 조작해 보니 배치와 상태 표시가 몇 군데 달랐다. 또 화면 일부 문구가 "결제 승인 완료"처럼 읽혀서, 서버 전송까지만 하는 시연 범위를 넘어선 약속을 한다.

기대 결과:
- 주문 홈과 결제하기 화면의 배치가 실제 포스와 같은 방향으로 읽힌다(상단 탐색 왼쪽 정렬, 결제 수단 타일의 왼쪽 정렬, 금액 위계).
- 동작하지 않는 버튼은 동작하는 버튼과 눈으로 구분되고, 빈 주문에서 쓸 수 없는 버튼은 비활성으로 보인다.
- 어떤 화면도 `SYNCED`(서버 전송 완료)를 결제 승인 완료나 메뉴 준비 약속으로 표현하지 않는다.

## 관찰 근거
부모 세션이 2026-10-06에 실행 중인 토스 포스(창 994×744)를 computer use로 직접 조작했다. 실제 승인이나 주문 접수는 하지 않았고, 담은 상품은 삭제해 빈 주문으로 되돌렸다. 캡처 파일은 부모 세션의 임시 경로에만 있고 저장소에는 넣지 않는다.
- 상단 바: 어두운 바의 왼쪽에 메뉴 아이콘과 `테이블`·`주문`·`예약` 탐색이 붙어 있고, 오른쪽에 토글·알림·시계·더보기가 있다. 가운데 정렬이 아니다.
- 주문 홈: 왼쪽에 분류 탭(오른쪽 끝에 이전·다음 화살표와 검색), 상품 타일, 하단의 편집모드·상품추가·쪽 표시, 즐겨찾는 옵션. 오른쪽은 주문서 패널이며 하단에 할인·분할 결제·주문·결제 버튼이 고정돼 있다.
- 빈 주문에서는 옵션·할인·분할·결제가 비활성이다.
- 상품을 담고 수량을 늘리면 금액이 바로 바뀌고, 선택한 줄 위에 감소·수량·증가와 삭제가 나온다. 줄은 `이름 × 수량`과 금액으로 읽힌다.
- 결제하기: 왼쪽 위에 뒤로와 시각, `총 결제금액` 작은 글자 아래 큰 금액(`12,000원 결제`), 결제 수단 타일은 아이콘과 글자가 타일의 왼쪽 위에 정렬된다. 오른쪽은 어두운 `주문내역 수정` 머리, `[포장 3개]`와 품목, 하단에 `총 3개`와 총금액이다.
- 확인하지 못한 것: 실제 고객 단말(프론트)의 얼굴결제 화면과 포스의 현황 화면은 조작하지 않았다. 그 화면들의 배치는 이 PR에서 관찰 근거로 삼지 않는다.

2차 관찰(2026-10-06, 같은 방식). 영구 설정 변경, 비상 결제모드 시작, 실제 승인, 주문 확정은 하지 않았고 모든 모달은 취소로 닫았다.
- 전체 메뉴: 매출(결제내역·시재·리포트), 상품(상품·할인, 선불권, 재고), 편의, 채널(키오스크, 테이블주문), 마케팅, 설정으로 나뉜다.
- 설정: 결제방식(고객이 주문을 담는 중에 결제수단을 미리 고르는 토글), 결제수단(카드·현금·QR·계좌·제로페이와 순서 편집), 현황 기능 사용(켜면 상단에 현황 탭이 생긴다), 비상 결제모드(오류나 인터넷 단절 때 자동으로 켜지고 결제 외 기능을 제한한다)를 각각 열어 읽었다.
- 예약 탭: 테이블 화면, 일·주·월·목록 선택 팝업, 목록 화면의 날짜·고객·메모·상품·테이블·상태 열.
- 옵션: 샷추가 토글을 누르면 4,000원이 4,500원으로 바로 반영된다. 옵션 상세에는 온도·농도 목록이 있다.
- 할인 모달: 상품별·총금액 탭, 저장된 할인(직원 30%, 포장 500원), 원·% 버튼과 숫자 키패드. 직원 할인을 고르고 총금액 탭에서 % 10을 입력한 뒤 취소하면 주문 금액 4,500원이 그대로였다.
- 분할결제: 금액·더치페이·메뉴별 라디오. 더치페이 2명 2,250원을 3명 1,500원으로 바꿀 수 있고, 메뉴별은 메뉴를 고르지 않으면 확인이 비활성이다.
- 결제 화면의 쿠폰 버튼은 전화번호 키패드 화면으로 가고 `안할래요`로 돌아온다.
- 현금 버튼은 결제를 바로 확정하지 않는다. 현금을 받은 뒤 현금영수증 여부를 고르라는 안내와 신청·안하기·취소 모달을 띄운다.
- 테이블 홈: 기본홀1에 들어가 인원 입력 숫자 키패드를 열고 취소했다. 담은 미확정 상품은 지워서 빈 테이블 홈으로 되돌렸다. 이 시연에 테이블 화면을 더하지는 않는다.

## 범위
바꾸는 파일은 `src/main/resources/static/terminal/index.html` 하나다. 서버 API, sync 요청 본문, localStorage 저장 형식(`rpos.terminal.v1`), 포스·단말 사이 postMessage 메시지 형식, 인증, 백엔드와 DB는 바꾸지 않는다.

1. 주문 홈
   - 상단 바의 `주문 홈`·`현황` 탐색을 메뉴 아이콘 바로 옆 왼쪽에 둔다. 키오스크 토글은 오른쪽 상태 영역으로 옮긴다.
   - 분류 탭이 많아져도 넘치지 않게 탭 줄만 가로로 스크롤한다. 이전·다음 화살표는 지금 자리만 있는 버튼인데, 이전·다음 분류로 옮기는 실제 동작으로 바꾸고 양 끝에서는 비활성으로 둔다.
   - 주문서 줄을 `이름 × 수량`으로 띄어 쓰고 금액을 고정폭 숫자로 맞춘다. 주문서 하단 버튼은 지금처럼 패널 아래에 고정한다.
2. 결제하기
   - 결제 수단 타일의 아이콘과 글자를 왼쪽 위로 정렬한다.
   - 총 결제금액은 `총 결제금액` 작은 글자와 큰 금액(`13,000원 결제`)으로 위계를 나눈다.
   - 주문내역은 `[매장 3개]` 머리, `이름 × 수량`과 금액, 하단 `총 3개`와 총금액으로 둔다.
3. 동작하지 않는 기능과 빈 주문
   - `data-act="todo"`인 버튼은 모두 `aria-disabled="true"`와 흐린 모양, "시연 범위 밖 기능" 설명(`title`)을 단다. 키보드 포커스는 받아서 누르면 지금처럼 범위 밖이라고 알린다. 진짜 `disabled`로 막지 않는 이유는 포커스와 설명까지 사라지기 때문이다.
   - 빈 주문에서는 할인·분할 결제·결제를 비활성으로 보인다. 옵션은 담은 줄을 고르지 않았으면 적용 대상이 없으므로 비활성으로 보인다(옵션 기능 자체는 여전히 범위 밖이다).
4. 결제 완료처럼 읽히는 문구
   - 현황 상세: `결제 금액`은 `결제 요청 금액`, `결제시간`은 `접수 시각`, `결제수단`은 `결제 요청 수단`으로 바꾼다.
   - 전송 상태 배지: `SYNCED`를 `서버 전송 완료`로 적는다. `SYNCED`는 sync 배치가 서버에 반영된 것이고 결제 승인이 아니다.
   - 고객 화면 결과: 전송이 끝난 결제는 "결제 요청을 서버에 전송했습니다"로 적는다. 결제 요청을 기다리는 화면은 "결제 요청을 보내고 있습니다"로 적는다.
   - 키오스크 결과: "준비 완료!"와 "메뉴가 나오면 알려드릴게요"는 이 시연이 하지 않는 약속이라 지운다. 주문번호와 전송 상태만 알린다.
   - 포스의 현금 접수 안내: "현금 결제를 접수했습니다"를 "현금 결제 요청을 접수했습니다"로 바꾼다.

5. 현금 결제 확인(2차 관찰 뒤 추가)
   - 지금 데모는 `현금` 한 번 클릭으로 주문을 접수한다. 실제 포스처럼 두 단계로 바꾼다. `현금`을 누르면 같은 가로 결제하기 화면 안에 확인 대화상자가 뜬다.
   - 대화상자는 금액, "현금을 받은 뒤 누르세요", 이 시연은 결제 요청을 단말에 저장하는 것까지라는 안내를 보인다. 버튼은 `취소`, `현금 받음 · 요청 저장`, 범위 밖 표시가 붙은 `현금영수증`이다. 현금영수증은 구현하지 않는다.
   - 고객용 세로 화면으로 바뀌지 않는다. 결제하기 화면 내부 상태 하나로 그린다.
   - 취소와 Esc는 주문서와 대기열을 그대로 둔다. 확인은 기존 `complete('CASH')` 경로(대기열 저장과 전송)를 그대로 쓴다. 저장에 실패하면 주문서를 유지하고 대화상자도 닫지 않는다.
   - 대화상자가 열리면 포커스가 대화상자로 가고 뒤 화면과 시연 제어 막대는 `inert`로 막는다. Tab·Shift+Tab은 대화상자 안에서 돈다. 닫히면 포커스가 `현금` 타일로 돌아온다.
   - 확인 대기 중에 고객 단말의 카드 결제가 먼저 접수되면 대화상자를 닫는다. 남은 대화상자로 같은 주문서를 한 번 더 접수할 수 없다.

## 제외
- 실제 결제 승인, 얼굴 인식, 옵션·할인·분할 결제 같은 자리만 있는 기능의 구현.
- 토스 포스의 로고, 캐릭터, 사진, 아이콘 그림의 복제. 배치와 정렬만 참고한다.
- 테이블·예약 탭과 같이 이 시연에 없는 화면 추가(테이블 홈과 인원 입력도 관찰만 했다).
- 고객 단말의 얼굴결제 화면과 현황 화면의 배치 변경. 실제 화면을 관찰하지 못했다. 문구만 위 범위 4대로 바꾼다.
- 저장소·메시지·sync 계약 변경.
- 2차 관찰에서 본 할인, 옵션, 분할결제, 쿠폰, 설정, 예약, 전체 메뉴. 이유는 후속 작업 절에 있다.
- 현금영수증 발행.

## 인수 조건
- 폭 1280에서 상단 탐색이 메뉴 아이콘 바로 오른쪽에 있다.
- 분류가 탭 줄 폭보다 많으면 탭 줄 안에서만 가로로 스크롤되고, 다음 화살표로 다음 분류가 선택된다.
- 빈 주문에서 할인·분할 결제·결제와 옵션이 비활성으로 보이고, 상품을 담으면 결제가 활성이 된다.
- 결제하기 타일의 아이콘과 글자 왼쪽 끝이 타일의 왼쪽 안쪽 여백에 맞는다.
- `data-act="todo"`인 모든 버튼에 `aria-disabled="true"`가 있다.
- `현금`을 처음 누르거나 대화상자를 취소·Esc로 닫아도 순번·대기열·주문 기록이 그대로다. 확인을 처음 누르면 `CREATE_ORDER`와 `REQUEST_CHECKOUT` 한 쌍만 저장되고, 확인을 두 번 빠르게 눌러도 한 쌍뿐이다. 오프라인 현금 결제는 새로 고침 뒤에도 대기열에 남고 재연결 뒤 전송된다. 카드와 고객 단말 경로는 그대로다.
- 화면 어디에도 "준비 완료", "메뉴가 나오면", `결제시간`이 남지 않는다.
- 모의 모드의 주문 추가·수량·삭제, 결제하기 뒤로, 현금 결제, 포스와 고객 단말 연결 결제, 오프라인 결제와 새로 고침 뒤 복구, `?selftest`가 PR 82번과 같게 동작한다.

## 검증
- 같은 파일을 두 포트로 서빙한다: `python3 -m http.server 8765 -d src/main/resources/static`, 같은 명령을 8766으로. 포스는 `http://localhost:8765/terminal/index.html?mock`.
- 브라우저 자동화로 수정 전(`HEAD`의 파일)과 수정 후를 1280×848에서 캡처해 비교한다.
- 위 인수 조건의 흐름을 모의 모드에서 돌리고, 차단 상태 결제 두 번 → 새로 고침 → 차단 해제 순서로 대기열과 `서버 전송 완료`를 확인한다.
- 키보드 Tab으로 상단 탐색·분류 탭·주문서·결제 버튼을 지나며 포커스 표시를 확인한다.
- 작은 창(800×600, 390×844)에서 단말 화면 밖으로 넘치는 요소가 없는지 계산된 위치로 검사한다.
- 현금 확인 대화상자: 열기·취소·Esc·확인·빠른 두 번 클릭·저장 실패 전후로 localStorage의 순번·대기열·주문 수를 비교하고, 열 때와 닫을 때의 포커스 위치를 본다.
- `?selftest`, `./gradlew test`, `python3 scripts/check_pr.py`.

## 후속 작업
2차 관찰에서 본 아래 영역은 지금 서버에 받아 줄 API와 도메인 모델이 없는 업무 기능이다. 화면만 만들면 서버에 남지 않는 금액 변경이 생겨 sync 계약과 어긋나므로 이 PR에서는 만들지 않는다.
- 할인(상품별·총금액, 저장된 할인, 원·%): 주문 금액을 바꾸므로 sync의 `CREATE_ORDER` 줄 금액이나 별도 할인 항목과 서버 검증이 먼저 필요하다.
- 옵션(샷추가 같은 가격 옵션, 온도·농도): 줄 단가를 바꾸므로 상품 옵션 모델과 줄 구조 확장이 필요하다.
- 분할결제(금액·더치페이·메뉴별): 주문 하나에 결제 요청 여러 건이 붙는다. 지금 `REQUEST_CHECKOUT`은 주문 금액 하나만 받는다.
- 쿠폰·포인트(전화번호 입력): 고객 식별과 적립 모델이 없다.
- 현금영수증: 발급 연동과 식별 번호 처리가 필요하다.
- 설정(결제방식 토글, 결제수단 순서, 현황 기능 켜기, 비상 결제모드): 단말 설정 저장소가 없다. 비상 결제모드는 이 프로젝트의 오프라인 결제 흐름과 직접 겹쳐서 별도 설계가 필요하다.
- 예약(일·주·월·목록, 목록 열), 전체 메뉴의 매출·상품·채널·마케팅: 이 시연 범위 밖의 화면이다.
