# PR spec: PR 템플릿을 의사결정 문서 형태로 개편

## 목적
지금 PR 템플릿은 spec 링크와 체크박스만 요구한다. 그래서 PR 본문에 "무엇을 포기했는지", "기존 기능에 어떤 영향이
있는지", "어디를 집중해서 봐야 하는지"가 남지 않는다. 리뷰어와 나중에 이력을 읽는 사람은 diff만 보고 이 판단을
복원해야 한다. 이 PR은 카카오페이손해보험 기술 블로그의
[PR을 더 느리게 만들기 위한 고민](https://tech.kakaopay.com/post/kakaopayins-slow-pr-fast-dev/)을 참고해서
PR 본문을 의사결정 문서로 쓰도록 템플릿을 바꾼다. 기대 결과는 PR 본문만 읽어도 한계·영향·실패 시나리오·버린
대안·위험도별 리뷰 지점을 알 수 있는 것이다.

## 범위
- `.github/pull_request_template.md`를 아래 절 순서로 교체한다.
  1. `왜 해야 하나요?` : 한두 문장과 spec 경로·첫 커밋 SHA 한 줄. spec의 목적·범위를 다시 옮겨 적지 않는다.
  2. `무엇을, 어떻게 해결했나요?`
  3. `한계와 트레이드오프` : 기존 "위험 / 후속 PR" 절의 위험을 흡수하고, 후속 PR을 적는 자리도 여기로 둔다.
  4. `기존 기능에 미치는 영향`
  5. `Edge case와 실패 시나리오`
  6. `검토한 대안과 선택 이유`
  7. `리뷰 포인트` : `| 파일/영역 | Risk | 봐야 할 것 |` 표. Risk는 🔴/🟡/🟢로 적는다. 표 아래에 "비즈니스
     로직·새 패턴·트레이드오프 변경이 있어 사람의 리뷰가 필요하다" 체크박스를 둔다.
  8. `확인 방법` : 기존 템플릿의 체크박스 다섯 개(한 가지 목표와 분할, spec 인수 조건 검증 기록, 로컬 PR harness
     통과, wiki 본문 반영, changes.md 기록)를 옮기고, "리뷰 포인트에 🔴 항목이 있으면 resilientpos-multi-review를
     실행하고 결과를 기록했다" 체크박스를 더한다.
- 해당 사항이 없는 절은 지우지 않고 `해당 없음: 근거` 한 줄로 채우도록 허용한다. 문서 전용 PR의 부담을 줄이기 위한
  규칙이다.
- 작성 가이드는 템플릿 안에 HTML 주석으로 넣는다. 주석은 GitHub에서 렌더링되지 않으므로 본문을 어지럽히지 않는다.
  - 각 절은 diff와 PR spec을 분석해서 채우고, 실행하지 않은 검증은 "미실행"으로 적는다.
  - Risk 판정 기준: 🔴는 비즈니스 로직·정합성 불변식·마이그레이션·동시성·새 패턴 도입, 🟡는 기존 패턴을 따르는
    기능 추가와 설정 변경, 🟢는 리네임·포맷팅·테스트 추가·메서드 추출·문서다.
- [개발 규칙](../wiki/development-workflow.md)의 "PR 본문" 절을 새 절 구성, `해당 없음: 근거` 허용, Risk 판정
  기준, 🔴일 때의 multi-review 규칙으로 갱신한다. 현재 문장은 "왜 / 무엇을 / 어떻게 / 확인 방법 4단"이라고 적혀
  있는데 실제 템플릿과 어긋나 있던 기존 불일치다. communicate 스킬의 네 가지 질문(왜 / 무엇을 / 어떻게 / 확인
  방법)은 새 템플릿의 골격으로 그대로 남는다는 점을 밝혀 둔다.
- "PR 본문 4단"을 언급하는 다른 wiki 문서는 grep으로 확인해서 서술이 틀려지는 곳만 고친다.
- [변경 기록](../wiki/changes.md)에 이 spec 링크와 요구사항 영향 근거를 추가한다.
- 독립 리뷰에서 나온 수정은 결과 절의 범위 조정에 적는다. 위 목록과 다른 부분은 범위 조정이 우선한다.

## 제외
- 볼트에 있는 스킬·에이전트는 수정하지 않는다. git 스킬이 PR 생성 전에 템플릿을 먼저 읽고 그 구조를 따르므로
  작성 가이드를 템플릿 주석에 두면 충분하다.
- AI 리뷰 봇(GitHub Action)은 도입하지 않는다. 최근 PR은 작성자가 한 명이고 기록된 리뷰가 0건이라서 봇이 줄여 줄
  리뷰 대기 시간이 없다. 로컬 `resilientpos-multi-review`가 같은 역할을 하므로, 🔴 항목이 있는 PR만 제출 전에
  multi-review를 실행하는 규칙으로 대신한다.
- 리뷰 코멘트 심각도 태그(`[r]`/`[c]`/`[a]`)는 도입하지 않는다. `resilientpos-review` 스킬이 이미
  Critical / Important / Nice-to-have로 표기한다.
- `check_pr.py`에 PR 본문이나 템플릿을 검증하는 기능은 넣지 않는다. 검사기는 저장소 트리만 보고 PR 본문을 읽지
  않는다. 본문 검증이 필요해지면 별도 PR로 다룬다.
- 애플리케이션 코드와 빌드 스크립트는 바꾸지 않는다.

## 관련 문서
없음. 이 PR은 장기 스펙 계층을 따르지 않는 개발 절차 변경이다. 선행 PR spec은 PR 본문 4단을 처음 정한
[development-rules-original-first](2026-09-13-development-rules-original-first.md)다.

## 인수 조건
- 템플릿에 범위 절의 여덟 개 절이 적힌 순서대로 있고, 기존 "위험 / 후속 PR" 절 제목이 남아 있지 않다.
- 기존 템플릿의 체크박스 다섯 개가 문구 그대로 "확인 방법" 절에 있다. multi-review는 조건부 체크박스가 아니라 실행 여부를
  적는 서술 한 줄로 있다.
- 템플릿의 HTML 주석에 작성 원칙("미실행" 표기, `해당 없음: 근거` 허용), Risk 판정 기준, 후속 PR을 적을 자리가
  들어 있다.
- 개발 규칙의 "PR 본문" 절이 템플릿의 절 구성과 일치하고, 네 가지 질문과 새 절의 대응 관계를 설명한다.
- wiki 어디에도 PR 본문이 네 개 절로 고정되어 있다고 읽히는 현재형 서술이 남아 있지 않다. 과거 시점의 기록
  (변경 기록의 지난 항목, 계약 조정 이력)은 고치지 않는다.
- 템플릿 파일명이 볼트 git 스킬이 읽는 표기(`PULL_REQUEST_TEMPLATE.md`)와 같다.
- Risk 판정 기준에 diff에서 확인할 수 있는 사실 기준이 있고, 🟢의 리네임과 메서드 추출에는 저장 형식·API 계약·프록시
  경계에 닿지 않는다는 단서가 붙어 있다.
- "사람의 리뷰가 필요하다" 체크박스에 체크했을 때 할 행동이 적혀 있다.
- 개발 규칙이 볼트 스킬의 "PR 본문 4단 고정" 선언과 충돌한다는 사실과 이 저장소에서의 우선순위를 밝히고 있다.
- 절 누락을 리뷰가 잡아 준다고 전제하는 서술이 spec과 wiki에 남아 있지 않다.
- 이 PR의 본문을 새 템플릿으로 직접 작성했을 때 모든 절이 내용 또는 `해당 없음: 근거`로 채워진다.

## 검증
- `python3 scripts/check_pr.py --base origin/main --worktree`가 PASS로 끝난다. 제출 직전에 `--worktree` 없이 한 번
  더 실행한다.
- `python3 -m unittest discover -s scripts -p 'test_*.py'`가 통과한다. 하네스 테스트가 템플릿 문구에 의존하지
  않는다는 것을 함께 확인한다.
- 이 spec 파일에 부등호 여는 문자가 없는지 커밋 전에 `grep -c`로 확인해서 0을 얻는다.
- wiki에서 수정한 상대 경로 링크가 실제 파일을 가리키는지 확인한다.
- 실패 시나리오: 열린 PR #26이 `docs/wiki/changes.md`를 수정하고 있어서 먼저 머지되면 충돌이 난다. 제출 직전에
  `git fetch`로 origin/main을 다시 확인하고, 앞서 있으면 사용자 확인을 받아 rebase한 뒤 검사를 다시 실행한다.
- 애플리케이션 코드가 바뀌지 않으므로 `./gradlew test`는 실행하지 않는다.

## 분할 계획
템플릿 1개와 문서 4개, 추가·수정 줄 수는 200줄 미만으로 예상한다. 개발 규칙의 파일·줄 수 한도에서 멀어 분할하지
않는다. 한도 경고가 나오면 템플릿 교체와 wiki 갱신을 별도 PR로 나눈다.

## TDD 검증 기록
적용하지 않는다. 문서·설정 전용 변경이라 업무 동작이 바뀌지 않고 실패시킬 테스트 대상이 없다. 대신 이 PR의 본문을
새 템플릿으로 직접 작성해서 템플릿이 실제로 채워지는지를 검증 사례로 삼는다.

### 알려진 한계
- 템플릿을 따랐는지는 자동으로 검사하지 않는다. `check_pr.py`는 PR 본문을 읽지 않고 기록된 리뷰도 없으므로, 절 누락을
  잡아 주는 장치는 없다. 작성자가 제출 전에 직접 점검한다.
- 볼트의 git 스킬 cli-reference와 communicate 스킬은 아직 "PR 본문 4단 고정"을 단일 출처로 선언한다. 개발 규칙에
  템플릿 우선 원칙을 적었지만, 볼트 문구를 고치기 전까지는 에이전트가 4단 양식으로 되돌아갈 가능성이 남는다.

### 범위 조정 - 독립 리뷰 반영 (개발 중)
PR을 올린 뒤에 Spring 백엔드 스페셜리스트 관점의 독립 에이전트 리뷰를 실행했다. 리뷰어는 이 PR을 작성한 세션의 맥락을
공유하지 않았고, 템플릿을 실제 코드와 PR #24·#26에 대입해서 근거를 모았다. P0는 없었다. 그중 P1 네 건, P2-2, P4-1을
이 PR에서 고친다. 나머지는 후속 PR 후보로 남긴다.

- P1-1 Risk 기준이 변경의 유형만 보고 영향 범위를 보지 않는다. enum 상수 리네임은 🟢로 분류되지만, 이 저장소는 주문
  상태를 `EnumType.STRING`으로 저장하므로 기존 행을 읽는 경로가 깨진다. 통합 테스트는 매번 빈 DB로 시작하고 새 이름으로
  데이터를 만들기 때문에 CI가 이를 잡지 못한다. 요청 DTO의 프로퍼티 리네임도 같은 PR에서 테스트가 함께 바뀌어 통과한다.
  그래서 🟢의 리네임과 메서드 추출에 "저장 형식·API 계약·프록시 경계에 닿지 않는"이라는 단서를 붙인다. 메서드 추출의
  프록시 경계 단서는 Spring의 일반적인 함정에서 가져온 것이고, 이 저장소에서 관측한 사례는 아니다.
- P1-2 🔴 판정이 작성자의 자기 신고라서 구조적으로 선택되지 않는다. 이 PR의 첫 본문이 실례다. "새 패턴을 도입한다"고
  쓰고도 표에는 🟡을 적어 multi-review를 건너뛰었다. 그래서 diff에서 확인할 수 있는 사실 기준(마이그레이션 경로,
  `application.yaml`의 flyway·jpa 설정, 트랜잭션·엔티티 어노테이션, 저장되는 enum 상수, 요청·응답 DTO 프로퍼티)을 두고,
  하나라도 해당하면 판단과 무관하게 🔴로 정한다. 조건부 체크박스는 조건이 거짓일 때도 체크되어 "실행하지 않은 검증은
  미실행으로 적는다"는 원칙과 어긋나므로, 실행 여부를 적는 서술 한 줄로 바꾼다. 이 PR의 본문도 템플릿 행을 🔴로 다시 판정한다.
- P1-3 개발 규칙은 템플릿이 단일 출처라고만 적었는데, 볼트의 git 스킬 cli-reference와 communicate 스킬은 "PR 본문 4단
  고정"을 단일 출처로 선언하고 있다. 충돌을 언급하지 않으면 에이전트가 어느 쪽을 따를지 정해지지 않는다. 개발 규칙에
  충돌 사실과 "이 저장소에서는 템플릿이 4단 고정을 대체한다"는 우선순위를 적고, 차용 내역에는 볼트 수정이 후속으로
  남아 있다고 적는다. 제외 절의 "볼트를 수정하지 않는다"는 그대로다.
- P1-4 템플릿의 규칙 중 자동으로 강제되는 것은 없다. `check_pr.py`는 PR 본문을 읽지 않고, PR 워크플로는 빌드와
  마이그레이션 버전만 본다. 최근 PR에 기록된 리뷰도 0건이다. 그래서 "절 누락은 리뷰에서 잡는다"는 서술을 사실대로
  고치고, "사람의 리뷰가 필요하다" 체크박스에는 체크했을 때의 행동(머지를 보류하고 사용자에게 알린다)을 붙인다.
  새 검사기는 만들지 않는다.
- P2-2 볼트 git 스킬은 템플릿을 대문자 파일명으로 읽는다. 대소문자를 구분하는 환경에서는 템플릿을 찾지 못하고 경고 없이
  4단 양식으로 되돌아간다. 이는 "스킬이 템플릿을 먼저 읽으므로 볼트를 고치지 않는다"는 제외 절의 전제를 무너뜨린다.
  볼트 대신 저장소의 파일명을 `PULL_REQUEST_TEMPLATE.md`로 바꾼다. GitHub은 두 표기를 모두 인식한다. 변경 경로 절에 옛
  경로가 함께 있는 이유는 검사기가 삭제된 경로도 변경으로 세기 때문이다.
- P4-1 실행 결과에 적은 줄 수가 마지막 커밋 이전의 값이었다. 최종 값으로 고친다.
