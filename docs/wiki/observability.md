# 관측성

애플리케이션은 metric·로그·trace를 표준 형식으로 내보내기만 한다. 수집·저장·대시보드는 밖에서 붙인다(Grafana LGTM 전제). 설계 방향은 [시스템 설계 7절](../references/02_System_Design.md#7-nfr-and-observability)을 따른다. 알림 규칙은 [`docker/prometheus/alerts.yaml`](../../docker/prometheus/alerts.yaml), 알림이 울렸을 때의 절차는 [runbook](runbook.md)이다.

## 지금 있는 것
- **알림 규칙**: [`docker/prometheus/alerts.yaml`](../../docker/prometheus/alerts.yaml)의 Prometheus rule 15개가 정본이다. 로컬은 lgtm의 Prometheus가 싣고, 운영은 같은 파일을 Mimir ruler에 올린다. 규칙마다 `severity`(`critical`·`warning`) label과 `summary`·`runbook_url` annotation이 있고 `runbook_url`은 [runbook](runbook.md)의 같은 이름 절이다. 여러 pod가 같은 DB를 세는 gauge는 `max`로 모으고, pod마다 도는 작업은 `instance`별로 본다. `./gradlew test`의 `AlertRulesTest`가 `prom/prometheus:v3.15.0`의 promtool로 규칙 검사와 단위 테스트(`alerts.test.yaml`)를 돌리고, `ObservabilityConfigurationTest`가 규칙이 쓰는 metric 이름이 앱 출력에 있는지 대조한다. 임계값 가운데 consumer lag 1000과 발행 지연 1시간, 감지 창(작업 생존 10분, 락 fail-open 2분, 503 2분, 매장 거절 2분, sync gap 5분)과 `for:`는 부하테스트 전의 시작값이다. `increase(x[W]) > 0`은 마지막 증가 뒤에도 W 동안 참이라, `for:`를 두는 규칙의 창은 `for:`보다 짧게 둔다. 모든 규칙이 앱의 series에 기대므로 앱 metric이 통째로 사라지면 `ResilientPosMetricsAbsent`(critical)가 울린다. DLT 두 규칙은 `keep_firing_for: 24h`로 마지막 DLT 뒤 하루 동안 firing을 유지한다([observability-alerts-tracing](../spec/2026-10-21-observability-alerts-tracing.md)).
- **metric**: `GET /actuator/prometheus`가 Prometheus text 형식을 돌려준다. 요청 수·지연·오류율(`http_server_requests_seconds_*`, 지연은 p95 등을 계산할 수 있는 histogram bucket 포함), JVM, Hikari 풀 metric이 들어 있다. 모든 metric에 `application="ResilientPOS"` 태그가 붙는다.
- **이벤트 발행 기록**: `event_publication_incomplete{status, module, listener}`가 커밋 뒤 리스너가 끝내지 못한 기록 수다. `status="failed"`는 리스너가 던진 기록(상태가 비어 있는 미완료 행 포함), `status="stale"`은 발행·처리·재전송 상태인 채 기본 5분(`resilientpos.event-publication.stale-after`)이 지난 기록이다. 1분마다 갱신하고, 마지막 갱신 시각은 `event_publication_incomplete_refreshed_seconds`(epoch 초)다. 조회가 실패한 인스턴스는 개수를 내리고 이 시각을 멈춘다. 모든 인스턴스가 같은 DB를 세므로 개수는 `max`로 모으고, 신선도는 인스턴스별로(또는 `min`으로) 보며 기동 직후를 위해 `for:`를 둔다. 갱신 스레드는 종료 때 가장 먼저 멈추며 최대 3초를 쓰므로 배포의 종료 유예 시간에 더한다. 규칙과 조치 절차는 [도메인 모델](domain-model.md) §4.3에 있다. 모듈 사이 이벤트가 Kafka로 가면서 이 metric은 브로커 전송 실패를 센다(`listener="EventExternalizerModuleListener"`). 재전송 작업이 행을 다시 보내는 동안(`RESUBMITTED`·`PROCESSING`, 브로커 장애 때 약 2분) 그 행은 `failed`에도 `stale`에도 잡히지 않는다. 끊긴 기록은 5분이 지나면 같은 작업이 `failed`로 옮기므로 `stale`은 잠깐만 보인다. 그래서 브로커 장애 중에도 `failed`가 잠깐 0이 될 수 있어, 사람이 볼 조건은 개수가 아니라 나이로 잡는다. 같은 갱신에서 gauge `event_publication_incomplete_oldest_seconds`가 완료되지 않은 기록 가운데 가장 오래된 것의 나이(발행 시각부터, 초)를 낸다. 없으면 0이고, 조회가 실패한 인스턴스는 `NaN`이다. 규칙(`EventPublicationOverdue`)은 `max(...) > 3600`에 `for: 5m`이다. 상태가 오가도 나이는 계속 늘어난다. 브로커 장애가 이어지거나 영영 나가지 못하는 기록이 있다는 뜻이고, 가르는 SQL은 도메인 모델 §4.3에 있다.
- **Kafka 소비**: `event_kafka_dead_letter_total{topic, reason}`이 토픽별로 DLT에 보낸 메시지 수다. `reason`은 도메인 오류 코드(예: `PAYMENT_APPROVAL_MISMATCH`, 업무 불일치)나 `error`(재시도 소진·버그)다. `reason="error"`는 기동할 때 0으로 등록되므로 `increase(...) > 0`으로 첫 증가를 잡는다. 도메인 reason은 처음 DLT로 보낼 때 생겨 첫 값을 `increase()`가 0으로 보므로, 규칙(`KafkaDeadLetter`)이 10분 전에 없던 series를 따로 잡는다(`unless … offset 10m`). `platform`이 `contract`의 코드를 미리 등록하면 순환하기 때문이다. Boot가 Kafka 클라이언트 metric(`kafka_consumer_*`·`kafka_producer_*`)을 함께 내보낸다. consumer lag는 파티션별 현재 값 `kafka_consumer_fetch_manager_records_lag{topic, partition}`이고 알림 규칙이 이것을 쓴다. `records_lag_max`는 fetch가 없는 동안 `NaN`이다. `client_id`에 consumer group 이름이 든다. Kafka 클라이언트가 같은 토픽을 점이 밑줄로 바뀐 이름으로 한 번 더 내므로 규칙은 점이 있는 이름만 본다. 이 값은 앱의 클라이언트가 내므로 앱이 없거나 fetch가 멈추면 사라지거나 멈춘다. 재시도마다 WARN(`소비 실패 topic=… key=… attempt=…`), DLT로 보낼 때 ERROR(`DLT로 보냄 …`) 로그가 한 줄씩 남는다. key는 `orderId`이고 로그 필드로만 남긴다. DLT 전송 자체가 실패하면 `event_kafka_dead_letter_failed_total{topic}`이 오르고 ERROR(`DLT 전송 실패…`)가 남는다. 이 counter도 기동할 때 토픽마다 0으로 등록된다. 0보다 크면 브로커·권한·메시지 크기를 먼저 본다. 재시도·DLT 규칙과 재투입 절차는 [도메인 모델](domain-model.md) §4.3에 있다.
- **노출 범위**: Actuator는 `health`와 `prometheus`만 연다. 앱은 `/v1/**`를 단말 토큰으로, `/owner/**`를 점주 세션 쿠키로 인증하고 `/actuator/**`는 인증 대상이 아니므로 외부 차단은 배포(ingress·네트워크)에서 한다. 배포 전에 ingress가 `/actuator/**`를 외부로 라우팅하지 않는지 확인한다. 단말 API(`/v1/**`)를 외부에 노출하기 전에 edge(API gateway·ingress)가 IP와 `Authorization` 값의 digest 단위로 요청 상한을 건다. 앱의 빈도 상한은 인증 뒤에 판정해서, `Retry-After`를 무시하고 폭주하는 유효 토큰이나 형식은 맞지만 모르는 토큰의 요청도 요청마다 인증 조회 1회를 치르게 한다([inbound-rate-limit](../spec/2026-10-21-inbound-rate-limit.md)).
- **도메인 오류 로그**: 도메인 규칙 위반은 `ApiControllerAdvice`가 한 줄(`method`·`uri`·`errorCode`)로 남긴다. `NOT_FOUND`(예: `STORE_NOT_FOUND`·`TERMINAL_NOT_FOUND`)는 없는 경로의 404처럼 INFO이고 그 밖은 WARN이다. 다른 매장 ID를 훑는 요청이 WARN 경보를 채우지 않게 하려는 것이다. 훑기를 감지하려면 INFO의 `errorCode=…_NOT_FOUND`를 같은 `uri` 패턴으로 센다.
- **인증 실패**: 401 `UNAUTHENTICATED`와 403 `TERMINAL_MISMATCH`·`ACCESS_DENIED`(점주 경로의 CSRF 토큰 오류)는 `ApiControllerAdvice`의 WARN 로그(`method`·`uri`·`errorCode`)로 남는다. 인증 실패 전용 metric은 없다. 토큰과 `Authorization` 헤더 값은 로그와 예외 메시지에 남기지 않는다. 401 예외는 스택 트레이스를 만들지 않아, 토큰 대입이 반복돼도 요청마다 한 줄만 쌓인다. 점주 경로의 CSRF 거절(403)은 코드만 남기고 예외 메시지·스택을 남기지 않는다. `InvalidCsrfTokenException`의 메시지가 제출 토큰을 담기 때문이다. unique 위반의 PostgreSQL 상세(`Key (email)=(…)`)는 pgjdbc `logServerErrorDetail=false`로 예외 메시지와 Hibernate 로그에서 빠진다. 요청 본문 변환 실패(400)는 예외 클래스 이름만 남긴다. Jackson 메시지가 입력 조각(예: 따옴표 없는 비밀번호)을 담기 때문이다. PostgreSQL 서버 로그의 DETAIL 줄에는 이메일이 남으므로, 서버 로그를 수집할 때는 같은 기준으로 다룬다. 앱 밖의 리버스 프록시·ingress access log는 이 보장 밖이다. 배포 전에 그 로그가 `Authorization` 헤더를 남기지 않거나 가리는지 확인한다.
- **단말 빈도 상한**([inbound-rate-limit](../spec/2026-10-21-inbound-rate-limit.md)):
  - **거절 metric**: 인증된 `/v1` 요청을 단말·매장 bucket이 거절하면 counter `inbound_rate_limited_total{scope}`가 오른다. `scope`는 거절한 bucket(`terminal`·`store`)이고, 둘 다 기동할 때 0으로 등록되므로 `increase(...) > 0`으로 첫 거절을 잡는다. 단말·매장 ID는 label로 쓰지 않는다. 고장 감지는 이 증가율로 한다. 알림은 매장 bucket 거절이 5분 넘게 이어질 때만 울린다(`InboundStoreRateLimited`, warning). 단말 bucket 거절은 오래 오프라인이던 단말의 정상 회복에도 이어지므로 알림을 걸지 않는다.
  - **거절 로그**: limiter가 scope별로 10초에 한 줄 INFO(`빈도 상한으로 거절했다 scope=… terminalId=… storeId=… retryAfterSeconds=… suppressedSinceLast=N lastLoggedAt=…`)로 남긴다. `suppressedSinceLast`는 직전 줄 뒤 남기지 않은 거절 수이고 `lastLoggedAt`이 그 직전 줄의 시각이다. advice는 429를 로그로 남기지 않는다. `Retry-After`를 무시하는 단말이 로그를 요청 수만큼 늘리지 못하게 하려는 것이다. backlog를 비우다 받는 429는 정상 동작이라 WARN이 아니다. 원인 단말은 `scope=terminal` 줄의 `terminalId`다. `scope=store` 줄의 `terminalId`는 매장 bucket이 빈 순간 막힌 단말(피해 단말)이고, 원인 단말이 자기 상한 안에서 매장 bucket을 비웠다면 그 단말의 거절 줄은 없다. 한 단말이 폭주하면 거의 모든 줄이 그 단말이고, 여러 단말이 함께 거절되면 표본 한 단말만 보인다. 토큰과 `Authorization` 값은 남지 않는다.
  - **Redis 장애**: 제한 없이 통과시키고(fail-open) 스택 없는 한 줄을 남긴다. 줄에는 감싼 Spring 예외가 아니라 근본 원인의 클래스와 메시지가 있다. 근본 원인이 Redis의 오류 응답이고 기다려도 풀리지 않는 것(스크립트 오류·OOM·NOPERM·CROSSSLOT·READONLY·WRONGTYPE, 연결 단계의 WRONGPASS·NOAUTH)이면 ERROR(`제한 없이 통과시킨다(Redis가 명령을 거절함, 설정·스크립트 확인 필요) …`)이고 바로 사람이 본다. 연결 실패·timeout·끊긴 동안의 거절과 기다리면 풀리는 응답(LOADING·BUSY·TRYAGAIN·CLUSTERDOWN·MASTERDOWN)은 WARN(`제한 없이 통과시킨다(Redis 오류) …`)이다. 같은 수준의 줄은 10초에 한 줄이고 같은 `suppressedSinceLast`·`lastLoggedAt`을 단다. 그동안은 보호가 없다. 이미 맺은 연결이 끊긴 뒤 재연결이 WRONGPASS·NOAUTH로 실패하는 동안(Redis 비밀번호·ACL 교체)에는 limiter가 보는 원인이 끊긴 동안의 거절이라 WARN이다. 그 사고는 새 pod의 기동 검사 실패와 점주 경로의 503 ERROR로 드러난다.
  - **1초 창과 탐침**: 연결 계열 실패(연결 단계의 오류 응답 포함)를 본 시각부터 1초 동안은 Redis를 부르지 않고 통과시키고 그 건수를 창을 연 실패와 같은 수준(WARN·ERROR)의 다음 줄에 더한다. 창이 지나면 요청 하나만 Redis를 다시 불러 보고(탐침) 탐침이 끝날 때까지 온 요청은 계속 건너뛴다. 탐침이 1초 넘게 걸려도 둘째 탐침은 없다. 탐침이 성공하거나 명령 단계의 오류를 받으면 창을 닫는다. 그래서 Redis가 timeout으로 실패하거나 단절되거나 한 번도 연결되지 못한 pod에서도 Redis를 기다리는 요청은 pod당 1초에 하나다. Redis가 돌아온 뒤 탐침이 성공할 때까지는 보호가 없다. 연결이 끊겼던 pod는 탐침 간격 1초와 Lettuce 재연결 간격(2배씩 늘어 최대 30초) 중 긴 쪽이다. timeout까지 가지 않고 느리기만 한 Redis는 창이 열리지 않아 요청마다 그만큼 더해진다.
  - **기동 검사**: 기동할 때 인스턴스마다 새 검사용 키(`rate-limit:{preflight:무작위}:…`)로 스크립트를 통과 분기까지 한 번 돌린다. 앱 쪽 설정 오류(NOPERM·NOAUTH·WRONGPASS·CROSSSLOT·WRONGTYPE·스크립트 오류·막힌 명령)면 원인 예외와 함께 기동을 멈춘다(`Redis가 rate limit 스크립트를 거절했다…`). Redis에 닿지 못하거나 OOM·READONLY·연결 수 초과 같은 Redis 쪽 상태면 WARN(`기동 검사를 건너뛴다…`)을 남기고 뜨며, 닿지 못했으면 1초 창을 연 채로 시작한다.
  - **Lettuce 설정**(`PlatformConfiguration`): 연결이 끊긴 것을 아는 동안 명령을 버퍼에 쌓지 않고 바로 거절하고(`REJECT_COMMANDS`), 응답 없는 명령은 1000개까지만 받는다(`requestQueueSize`). 점주 세션과 로그인은 끊긴 동안 바로 503이다. queue가 차면 Lettuce가 거절마다 남기는 스택 WARN(`Unexpected exception during request`)은 `logging.level.io.lettuce.core.protocol.DefaultEndpoint=ERROR`로 끈다. 응답 없는 연결은 커널 재전송 한도(Linux 기본 약 15분)가 지나야 끊기므로, Redis가 다른 주소로 옮겨 이전 주소가 계속 응답하지 않으면 그동안 보호가 없다. 같은 주소로 네트워크가 돌아오면 다음 재전송(최대 2분) 안에 회복한다. 유휴 연결의 단절은 TCP keepalive(Lettuce 기본값, 13초 쉬면 13초 간격 3회, 확장 keepalive를 지원하는 JDK 11+ NIO에서)로 1분 안에 드러난다.
  - **잠금의 부작용**: 잠금(`RedisDistributedLock`)의 Redis 오류 WARN은 스택을 달고 잠금 호출마다 남는다. `REJECT_COMMANDS`로 실패가 빨라진 결과이고, 이 PR 밖이라 후속에서 같은 방식(근본 원인 한 줄, 간격)으로 바꾼다.
- **점주 감사**: 점주 행위는 커밋 뒤 Controller가 INFO 한 줄(`audit action=… ownerId=…`)을 남긴다. `action`은 `OWNER_SIGNED_UP`·`OWNER_LOGGED_IN`·`STORE_CREATED`·`TERMINAL_REGISTERED`·`TERMINAL_CREDENTIAL_ROTATED`·`TERMINAL_DEACTIVATED`·`RECONCILIATION_CASE_RESOLVED`다. 대조 case 해소는 `storeId`·`caseId`·`paymentId`·`decision`·`paymentStatus`를 더하고, 점주가 적은 사유(`note`) 원문은 남기지 않는다(자유 입력이라 개인정보가 섞일 수 있다). 이 줄만 Controller가 아니라 `ReconciliationManagement.resolve`가 처음 해소한 뒤 남긴다. 같은 결론의 재요청에는 남지 않아 줄 수가 곧 해소 건수다. 매장·단말 행위는 `storeId`, 단말 행위는 `terminalId`, 등록은 `terminalCode`, 비활성화는 전후 `status`를 더한다. 이메일·비밀번호·세션 ID·평문 토큰은 남기지 않는다. 평문 토큰은 응답에 한 번만 실린다. 로그인 실패는 advice의 401 WARN만 남고 원인(없는 계정·틀린 비밀번호·잠김)을 나누지 않는다. 로그인 실패 카운터의 키는 이메일의 SHA-256이다. 카운터 증가의 Redis 오류는 503 ERROR(fail-closed, 아래 항목)이고, 로그인 성공 뒤 지우기의 Redis 오류는 WARN(`로그인 성공 뒤 실패 횟수를 지우지 못했다`) 한 줄을 남기고 로그인은 성공한다. 이 감사 로그는 로그 보관 기간에 기대며 DB에 남지 않는다. 사유·증거를 DB에 남기는 것은 대조 case 해소뿐이다(`t_reconciliation_case`의 해소 컬럼)([operator-authentication](../spec/2026-10-06-operator-authentication.md)).
- **플랫폼 운영자와 DLT 재투입**: `/admin/**`는 사내 IdP가 발급한 Bearer 토큰(권한 `resilientpos-operator`)으로만 부른다. 세션·쿠키를 쓰지 않는다. 토큰이 없거나 틀리면 401 `UNAUTHENTICATED`(`WWW-Authenticate: Bearer`), 권한이 없으면 403 `ACCESS_DENIED`이고 advice의 WARN 한 줄이 남는다. IdP에 닿지 못하면(discovery·JWK 조회 실패, HTTP 상한 connect 2초·read 3초) 503 `SERVICE_UNAVAILABLE`(ERROR)이다. 401의 원인(만료·서명·키 없음 등)은 INFO 한 줄(`operator unauthenticated … cause=…`)로 남는다. 모든 운영자가 401이면 IdP의 키 회전이나 빈 JWK Set을 의심한다. 앱은 IP로 거르지 않으므로 배포 전에 ingress가 `/admin/**`를 사내망·VPN에서만 받는지 확인한다. 운영자가 DLT 메시지를 처음 재투입하면 INFO 한 줄(`audit action=DEAD_LETTER_REDRIVEN operator=… dltTopic=… dltPartition=… dltOffset=… topic=… partition=… offset=…`)이 남고 counter `event_kafka_dead_letter_redriven_total{topic}`(원 토픽, 기동 때 0으로 등록)이 오른다. 같은 레코드의 재요청에는 둘 다 남지 않아 줄 수가 곧 기록된 재투입 건수다. 보냈는데 기록이 남지 않은 경우는 WARN 한 줄(`audit action=DEAD_LETTER_REDRIVE_UNRECORDED … cause=…`)이다. `cause`는 `DUPLICATE`(같은 레코드 동시 요청의 진 쪽), `RECORD_FAILED`(전송 뒤 기록 실패, 응답 500), `SEND_UNCONFIRMED`(ack 시간 초과, 실제 전송 여부 모름, 응답 503)이고, 이 줄이 그 전송의 행위자 정본이다. 목록을 읽으면 INFO 한 줄(`audit action=DEAD_LETTERS_LISTED operator=… topic=… partition=… fromOffset=… count=…`)이 남는다. `operator`는 토큰의 `sub`이고, 운영자가 적은 사유 원문은 로그에 남기지 않는다. 사유·행위자의 정본은 `t_dead_letter_redrive`다. 목록·재투입이 브로커에 닿지 못하면 503이고 재투입 기록이 남지 않는다. 재투입 절차는 [도메인 모델](domain-model.md) §4.3에 있다([platform-operator-dlt-redrive](../spec/2026-10-21-platform-operator-dlt-redrive.md)).
- **점주 세션 저장소(Redis)**: 점주 세션과 로그인 시도 카운터는 Redis에 있다. Redis에 닿지 못하면 점주 요청 중 세션이나 카운터가 필요한 것은 envelope의 `503 SERVICE_UNAVAILABLE`(ERROR 로그)이다. 세션 쿠키가 있는 인증 경로와 로그인이 여기에 든다. 처리 위치는 셋이다. Spring Session 필터 바깥의 `/owner/*` 필터, 로그인 Controller의 세션 조작, 카운터 adapter다. 카운터는 fail-closed라, 장애 중 로그인은 비밀번호를 비교하지 않고 503이다. 그래서 401과 503으로 비밀번호 정답을 가를 수 없다. MVC의 기본 `FlashMapManager`가 요청마다 세션을 읽지 않도록 아무것도 하지 않는 구현을 둔다. 그래서 단말 경로(`/v1/**`)는 세션 쿠키가 실려 와도 세션 때문에 Redis에 닿지 않는다. 단말 경로가 Redis를 쓰는 곳은 분산 락과 빈도 상한이고 둘 다 fail-open이다. health는 Redis를 보지 않는다. 보게 하면 Redis 장애 때 readiness가 빠져 단말 핫패스까지 막히기 때문이다. 감지는 `http_server_requests_seconds_count{status="503"}`의 증가와 Redis 자체의 모니터링으로 한다. `/actuator` 요청은 뺀다. health는 DB가 DOWN이거나 기동·종료 중이면 503이다. Spring Session 필터 단계에서 나는 503은 MVC handler 밖이라 `uri` 태그가 `UNKNOWN`이고(`OwnerSessionStoreOutageIntegrationTest`가 고정), 카운터 장애의 503만 `/owner/v1/login`으로 찍힌다. `/actuator` 밖에서 503을 내는 곳은 이 장애 처리와 위 플랫폼 운영자 항목의 IdP·브로커 장애다. 둘은 ERROR 줄의 `uri`로 가른다. 로그로는 ERROR의 `errorCode=SERVICE_UNAVAILABLE`을 센다. 503은 변경이 커밋되지 않았다는 뜻이 아니다. 인증 경로의 세션 저장은 응답을 커밋할 때 일어나므로, 등록·회전 뒤 503이면 목록으로 확인한다. 세션 속성은 Spring Security 허용 목록의 JSON이다. 읽지 못한 세션 값(옛 형식, 허용 목록 밖 타입)은 WARN 한 줄을 남기고 없는 값으로 다뤄져 401이 된다. 앱 계정 ACL은 단말 빈도 상한 스크립트에 쓰는 EVAL·EVALSHA와 스크립트 안 명령(TIME·HMGET·HSET·PEXPIRE), 키 패턴 `~rate-limit:*`를 허용해야 한다. 빠지면 기동 검사가 기동을 멈춘다. Redis 키에는 환경 구분이 없으므로 환경마다 Redis(또는 DB 번호)를 따로 둔다. 운영 Redis는 인증과 TLS를 갖춘 뒤 외부에 노출한다([operator-authentication](../spec/2026-10-06-operator-authentication.md)).
- **결과 불명 결제 확정**: 주기 작업(1분)이 provider 조회로 `UNKNOWN`을 확정하면 INFO(`결과 불명 결제를 확정했다 paymentId=… orderId=… checkoutNo=… status=…`), 조회로도 불명이면 WARN(`조회로도 결과를 확인하지 못했다 paymentId=… orderId=… queryCount=…`), 한 건이 던지면 ERROR(paymentId와 예외)가 남는다. 결과 불명 승인 시도 수는 gauge `payment_attempt_unknown`이다. 작업이 주기마다 조회·넘김이 끝난 뒤 세어 갱신하므로 scrape는 DB를 부르지 않고, 세기가 실패한 주기에는 마지막 성공값이 남는다. 모든 인스턴스가 같은 DB를 세므로 `max`로 모은다. 조회로도 불명인 채 60회(`resilientpos.payment.unknown-query-limit`)가 되거나 조회가 다른 금액의 승인을 알려 주면 시도를 reconciliation case로 넘기고 WARN(`paymentId`·`orderId`·`reason`·`queryCount`, 불일치면 알려 준 금액·참조)을 남긴다. 승인 요청 응답의 금액이 시도와 달라 결과 불명으로 둘 때도 WARN(`paymentId`·기대 금액·응답 금액·참조)이다. 넘긴 뒤 아직 `UNKNOWN`인 승인 시도 수는 gauge `payment_attempt_reconciliation_pending`이고 같은 주기에 갱신한다. 사람이 볼 조건은 둘이다. `max(payment_attempt_unknown) - max(payment_attempt_reconciliation_pending) > 0`이 2시간 넘게 이어지면(`for: 2h`) 작업이 멈췄는지 본다. 정상이면 한 건은 상한(약 1시간) 안에 확정되거나 넘어간다. `max(payment_attempt_reconciliation_pending) > 0`이 24시간 넘게 이어지면(`for: 24h`) 점주가 해소하지 않은 것이라 플랫폼이 연락한다. 두 조건은 규칙 `UnknownPaymentResolutionStuck`·`ReconciliationPendingUnresolved`다. 작업 규칙은 [도메인 모델](domain-model.md) §4.3에 있다.
- **결제 대조 case**: consumer가 case를 새로 열면 counter `reconciliation_case_opened_total{reason}`이 오르고 INFO(`caseId`·`paymentId`·`storeId`·`reason`·`status`·`ruleVersion`)가 남는다. 같은 사실의 재전달로 기존 case를 돌려줄 때는 세지 않는다. 점주가 처음 해소하면 counter `reconciliation_case_resolved_total{decision}`이 오른다. counter는 재기동하면 0부터라 미해소 건수는 위 pending gauge로 본다. case 열기가 실패하면 기존 Kafka 재시도·DLT(`payment.reconciliation-requested.DLT`)로 가고 넘긴 시도는 pending에 남는다. 해소 감사는 아래 점주 감사의 INFO 한 줄과 case 행의 해소 기록(`resolved_at`·`resolved_by_owner_id`·`decision`·`note` 등)이고, DB가 정본이다([payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)).
- **주기 작업 생존**: Spring이 `@Scheduled` 실행마다 observation을 남겨 `tasks_scheduled_execution_seconds_count{code_namespace, code_function, outcome, exception}`가 나간다. 실행 중인 것은 long task timer `tasks_scheduled_execution_active_seconds`다. 재전송 작업은 `code_function="resubmitAndPurge"`, 결과 불명 확정 작업은 `resolveUnknown`이다. 마지막 성공 시각 gauge를 따로 두지 않고, 살아 있는 인스턴스(`process_uptime_seconds`)인데 10분 동안 `outcome="SUCCESS"`가 늘지 않으면 규칙이 울린다. 기동한 뒤 한 번도 성공하지 못한 작업은 `SUCCESS` series가 없어서 이렇게 기준을 잡는다.
- **재전송 선택 건수**: counter `event_publication_resubmit_selected_total`이 재전송 한 주기에 Modulith가 다시 보내려고 읽은 `FAILED` 행 수다(`ResubmissionOptions.withFilter`에서 센다). 보낸 수가 아니라 고른 수이고, 락이 빠져 두 pod가 같은 행을 읽으면 두 번 센다. 전송 건수는 `FailedEventPublications.resubmit`이 결과를 돌려주지 않아 세지 않는다. 인스턴스별 1분 증가가 500 가까이에서 줄지 않으면 오래된 행이 한 주기의 읽기 자리를 모두 차지하고 있다는 뜻이다(runbook의 `EventPublicationOverdue`).
- **분산 락**: 잠그지 못하고 진행할 때마다 counter `lock_fail_open_total{lock, reason}`이 오르고 WARN(`잠금 없이 진행한다 … key=…`)이 남는다. `reason`은 `timeout`(대기 1.5초 초과)이나 `error`(Redis 오류)이고, `lock`은 키의 앞 두 마디(`order:create-lock`, `payment:checkout-lock`, `platform:event-publication`, `payment:unknown-resolve`)다. 키는 `모듈:이름:식별자…` 모양이어야 한다. 식별자를 앞 두 마디에 두면 식별자마다 시계열이 생긴다. 처음 fail-open될 때 생기는 counter라 한 번만 일어난 fail-open은 `increase()`가 놓칠 수 있고, 규칙은 10분 넘게 이어지는 것만 본다. 시도마다 Timer `distributed_lock_wait_seconds{lock, outcome}`에 얻기까지 걸린 시간이, 얻은 잠금은 Timer `distributed_lock_held_seconds{lock}`에 풀 때까지의 시간이 남는다. `outcome`은 첫 SET에 얻은 `acquired`, 다시 시도해서 얻은 `waited`, 잠금 없이 진행한 `timeout`·`error`다. 둘 다 SLO bucket(1ms~5초, 보유는 10초까지)만 낸다. 기다리는 요청은 채널 `platform:lock-released`의 해제 알림(`LockReleaseListener`)으로 깬다. Redis 없이 떠서 구독하지 못하면 5초마다 다시 구독하며 WARN(`잠금 해제 알림을 구독하지 못했다…`)을 남기고, 그동안 락은 재시도 간격으로만 기다린다. 구독자 수는 `PUBSUB NUMSUB platform:lock-released`로 본다(pod 수와 같아야 한다). 대기 한도 1.5초는 다시 시도하기를 멈추는 시각이라, 마지막 SET이 Redis timeout(1초)까지 걸리면 대기는 최대 2.5초다. 대기 비율·보유 p99.9로 대기 한도와 TTL을 정하고 Redisson이 필요해지는지 본다([용량 기준](capacity.md#redisson이-필요해지는-시점)).
- **공용 실행기**: Modulith 이벤트 외부화(`@ApplicationModuleListener`)가 Boot `applicationTaskExecutor`에서 돈다. 큐 길이는 `executor_queued_tasks{name="applicationTaskExecutor"}`, 바쁜 스레드는 `executor_active_threads`다. 큐가 차서 버린 작업은 counter `task_execution_rejected_total`(거절이 없어도 0으로 나간다)과 WARN(`실행기 큐가 가득 차 작업을 버렸다 누적=… queued=… active=…`)이다. WARN은 10초에 한 줄이라 정확한 수는 counter로 본다. 버린 외부화는 발행 기록이 미완료로 남아 재전송 작업이 `stale-after` 뒤 다시 보낸다. 그래서 버린 판매의 승인은 5분 넘게 늦고, 재전송은 클러스터 전체에서 1분에 최대 500건이라 버린 기록이 N건이면 약 N/500분이 더 걸린다. 다시 보낸 작업도 같은 실행기로 들어가 과부하가 이어지면 다시 버려질 수 있다. 큐가 부하 동안 계속 늘면 외부화가 입력을 못 따라가는 것이고 상한과 원인은 [용량 기준](capacity.md)에 있다.
- **Redis 명령 지연**: Lettuce observation의 `lettuce_seconds{db_operation}`이 histogram bucket을 낸다(`percentiles-histogram.lettuce`). `spring.data.redis.timeout`(1초)을 명령 p99.9와 대조한다.
- **sync**: counter `sync_operation_total{status}`가 배치 항목 결과마다 오른다. `status`는 `APPLIED`·`DUPLICATE`·`REJECTED`·`GAP`·`CONFLICT`이고 기동할 때 모두 0으로 등록된다. 시스템 설계의 `sync_gap_total`은 `status="GAP"`이다. 항목 결과가 정해질 때마다 세므로, 뒤 항목이 인프라 예외로 배치를 실패시켜도 그 전에 커밋된 항목은 세어진다. 상한 초과로 거절된 배치는 항목이 없어 세지 않는다. 수렴 시간은 timer `sync_convergence_seconds`로, 단말이 operation을 만든 시각(요청의 선택 필드 `createdAt`)부터 서버가 처음 확정(`APPLIED`·`REJECTED`)한 시각까지다. `createdAt`이 없거나, 차이가 음수(단말 시계가 앞섬)거나, `DUPLICATE`·`GAP`·`CONFLICT`면 기록하지 않는다. `createdAt`의 형식이 틀리면(offset 없는 시각, 숫자 등) 배치는 거절하지 않고 그 값만 버린다. 처음 확정한 항목의 값이 틀렸으면 counter `sync_created_at_invalid_total`이 올라 단말의 형식 버그를 알 수 있다. bucket은 1s·10s·1m·5m·15m·1h·6h·24h다. 긴 값은 매장 네트워크가 오래 끊겼다는 뜻이라 알림은 없다. 단말 시계가 늦은 만큼 크게 잡히는 것은 알아낼 방법이 없다.
- **trace**: Micrometer Tracing의 OpenTelemetry bridge(`spring-boot-starter-opentelemetry`)가 span을 만든다. HTTP 요청, Kafka 전송·소비, Redis 명령, 주기 작업, Spring Modulith의 모듈 API 호출(`spring-modulith-observability-core`, span 이름 `모듈 > 메서드`)이 span이 된다. 요청에서 Kafka를 지나 다음 consumer까지 trace 하나로 이어진다. 그러려면 Kafka template·listener의 observation(`spring.kafka.template.observation-enabled`, `spring.kafka.listener.observation-enabled`)과, 커밋 뒤 externalizer가 도는 executor로 trace를 넘기는 `spring.task.execution.propagate-context`가 켜져 있어야 한다. 셋 다 Boot 기본값은 `false`다. Kafka 레코드에는 W3C `traceparent` header가 붙는다. 샘플링은 1.0(`management.tracing.sampling.probability`, Boot 기본 0.1)이고 `MANAGEMENT_TRACING_SAMPLING_PROBABILITY`로 낮춘다. span을 보낼 곳(`management.opentelemetry.tracing.export.otlp.endpoint`)은 배포 환경 변수로만 주고, 없으면 exporter를 만들지 않는다. 보내지 못한 span은 앱 메모리 대기열(최대 2048개)이 차는 대로 버려지고 요청은 막히지 않는다. 같은 starter가 들이는 OTLP metric registry는 끈다(`management.otlp.metrics.export.enabled: false`). metric은 Prometheus scrape 한 경로로만 내보낸다. Modulith는 `platform`의 빈 호출(`TxRunner`, 응답 advice, 락)에도 span을 만든다. 끄면 커밋 뒤 Kafka 전송 span의 부모가 사라지거나 trace가 끊겨서 그대로 둔다(checkout 하나에 span 32개 안팎). 재전송 작업이 다시 보낸 메시지는 원래 요청의 trace를 잇지 못하고 그 주기 작업의 trace에 남는다.
- **로그**: 기본은 평문이다. `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`를 주면 stdout이 한 줄에 ECS JSON 객체 하나가 된다. trace가 있는 줄에는 Micrometer Tracing이 MDC에 넣은 `traceId`·`spanId`가 필드로 실린다. 평문에서는 줄 앞의 `[traceId-spanId]`다.

## LGTM을 붙일 때
- Prometheus(또는 Alloy의 `prometheus.scrape`)가 각 인스턴스의 `/actuator/prometheus`를 scrape하고 `remote_write`로 Mimir에 보낸다. 애플리케이션 설정은 바꾸지 않는다.
- 배포 환경에 `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`를 주고, Alloy가 컨테이너 stdout을 읽어 Loki로 보낸다. Loki label 이름에는 점을 쓸 수 없으므로 Alloy가 ECS 필드 `service.name`·`log.level`을 꺼내 `service_name`·`level` label로 올린다. label은 이 둘로 한정한다. `log.logger`처럼 값이 많은 필드는 label로 두지 않고 쿼리에서 `| json`으로 거른다.
- `orderId`·`paymentId`·`terminalId`는 metric label로 쓰지 않는다. 로그 필드나 trace attribute로 남긴다.
- 알림 규칙은 `docker/prometheus/alerts.yaml`을 그대로 Mimir ruler에 올린다(Prometheus rule 형식). 발송은 Alertmanager(또는 Mimir alertmanager)가 맡는다.
- 앱에 `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT`(OTLP HTTP, 예: `http://alloy:4318/v1/traces`)를 주고, Alloy가 `otelcol.receiver.otlp`로 받아 Tempo로 넘긴다. Alloy는 로그의 `traceId`를 label이 아니라 Loki structured metadata `trace_id`로 올린다. 줄마다 값이 달라 label로 두면 stream이 폭증한다. Grafana의 Tempo·Loki 데이터소스가 이 이름으로 trace와 로그를 서로 링크한다.

## 로컬에서 띄우기
`docker compose -f docker/docker-compose.yaml --profile app --profile obs up -d --build`가 앱 컨테이너, Alloy, `grafana/otel-lgtm`을 띄운다. PostgreSQL과 Kafka(KRaft 단일 노드, 호스트에서는 `localhost:9092`)는 profile 없이 늘 뜬다. 설정은 [docker-compose.yaml](../../docker/docker-compose.yaml)과 [Alloy 설정](../../docker/alloy/config.alloy)이다. Grafana는 `localhost:3000`이다.
- 위 "LGTM을 붙일 때"의 방식을 그대로 쓴다. Alloy가 `app:8080/actuator/prometheus`를 15초마다 scrape하고, docker socket으로 이 compose 프로젝트의 `app` 컨테이너 stdout만 읽어 `service_name`·`level` label과 `trace_id` structured metadata를 올린다. 앱의 span은 Alloy(4318)를 거쳐 lgtm의 Tempo로 간다.
- lgtm 이미지의 Prometheus 설정에는 `rule_files`가 없어 [`docker/prometheus/prometheus.yaml`](../../docker/prometheus/prometheus.yaml)로 바꿔 끼우고 `alerts.yaml`을 싣는다. Alertmanager가 없어 알림은 발송되지 않는다. 울린 알림은 Grafana의 알림 목록이나 데이터소스 proxy(`/api/datasources/proxy/uid/prometheus/api/v1/alerts`)로 본다.
- 앱 컨테이너는 늘 Alloy로 span을 보내므로 `obs` profile 없이 띄우면 보낼 곳이 없다. 그때 OTel exporter가 ERROR(`Failed to export spans`)를 남긴다.
- 운영과 다른 점: Mimir 자리를 otel-lgtm 안의 Prometheus가 remote_write로 받는다. 호스트(IDE)에서 띄운 앱은 수집하지 않는다.
- kotlin-logging이 기동할 때 logback을 거치지 않고 평문 한 줄(`kotlin-logging: initializing...`)을 찍는다. JSON이 아니라 label이 없어서 Loki가 `service_name="unknown_service"`로 둔다.

## 아직 없는 것
- 기준선이 없어 넣지 않은 알림. 기준선이 생기는 PR(부하테스트, 대시보드)이 더한다(#103).
  - HTTP 지연·오류율 SLO 알림(주문 p95 200ms 등). 부하테스트 기준선이 없다.
  - sync 수렴 시간 알림. 오프라인 길이는 매장 사정이라 임계값 근거가 없다.
  - 재전송 선택 건수 알림. 지금은 진단용이고, 실패 1시간 알림이 같은 상황을 덮는다.
- Alertmanager와 알림 발송 경로, Grafana 대시보드 provisioning, exemplar(metric에서 trace로 가는 링크).
- tail sampling. 부하테스트에서 exporter·저장 비용이 보이면 Alloy tail sampling(오류·느린 trace는 모두, 나머지는 일부)으로 바꾼다.
- 재전송 메시지가 원래 요청의 trace를 잇는 것. 발행 기록에 trace context를 저장해야 한다.
- 결과 불명 결제와 미해소 대조 case의 나이 gauge. 지금 gauge `payment_attempt_unknown`·`payment_attempt_reconciliation_pending`은 기동 직후 첫 주기(1분)까지 0이라, replica가 하나이거나 전부 재기동하면 2시간·24시간 규칙의 `for:`가 처음부터 다시 센다. 가장 오래된 `UNKNOWN` 시도와 미해소 case의 나이를 내는 PR이 규칙을 나이로 바꾼다(#104).
- DLT 미해소 건수. DLT 메시지는 지워지지 않는데 지금 규칙은 증가를 보고 24시간 붙잡을 뿐이다. #91의 재투입 기록과 함께 "아직 재투입하지 않은 DLT 수"를 내면 그것으로 상태 알림을 건다(#105).
- 발생 수 metric(`payment_unknown_total` 같은 것).
- histogram bucket 범위와 SLO 경계. HTTP는 Micrometer 기본 bucket이고 락 Timer 둘만 `slo` 고정 bucket이다. endpoint가 늘어 series 비용이 보이면 `minimum-expected-value`·`maximum-expected-value`나 `slo`로 좁힌다.
