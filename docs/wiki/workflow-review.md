# 워크플로우 리뷰 기준

지침·스킬·에이전트 변경 검토 시에만 읽는다. workflow-reviewer의 역할/권한/컨텍스트 검토와 develop-workflow spec-validator의 검증 가능성 관점을 차용했다. [출처](borrowed-workflows.md)

## 입력과 경계
PR spec, 대상 파일 목록, 기준 ref와 실제 diff를 입력으로 받는다. 파일이 없으면 관련 지침 경로를 먼저 찾는다.
셸 도구가 없는 리뷰어에는 호출자가 diff를 전달한다. diff/이력 근거가 없으면 그 검증은 미완료로 표시한다.
읽기 전용으로 검토하며 직접 수정·commit·push·재위임하지 않는다. 코드 리뷰나 전체 도메인 설계로 범위를 넓히지 않는다.

## 확인 항목
- **요청 적합성**: 선언된 목적과 실제 변경이 맞는가? 한 PR이 독립적으로 검토 가능한가?
- **역할**: 스킬은 작업 절차, 에이전트는 명확한 담당 범위, 도구별 파일은 진입점 역할을 하는가?
- **로딩**: root 지침이 과도하지 않은가? 전체 wiki/외부 vault를 항상 읽는가? 조건부 참조가 실제로 연결되는가?
- **근거**: 빌드 선언과 도입 계획을 구분하는가? 문법/스킬 이름/참조 파일이 실제 존재하는가?
- **SDD/TDD**: spec 선작성·범위 조정·wiki 동기화를 지키는가? 업무 TDD에서 Repository 자체 테스트 제외와 REST Docs/Fixture Monkey 정책을 보존하는가?
- **Git 권한**: commit-only와 push 요청을 구분하는가? staged 범위와 spec 첫 커밋을 보존하는가? 기본 브랜치/분기 이력에 자동 force/rebase를 하지 않는가?
- **검증 증거**: 실행한 검사와 설계상 기대를 구분하는가? 의존성 없는 스킬을 실행 가능하다고 주장하지 않는가?

도구 개수·모델 이름·규칙 파일 개수는 **신호**로 참고할 수 있지만, 그것만으로 결함을 판정하지 않는다. 2026-09-13에 이식한
`workflow-reviewer` 정의는 원본의 안티패턴 표(예: 도구가 많은 Command, 단순 작업에 상위 모델)를 갖고 있다. 그 표에 걸리면
역할·실제 영향·구체적 근거를 확인한 뒤에만 지적으로 올린다. 모델 배정은 [지침 설계 근거](agent-instructions.md#에이전트-모델-배정과-스킬-선행-규칙)의
역할별 기준을 따르므로, 배정표와 다른 값만 문제로 본다.
중복 절차는 공통 정본으로 모으되 다른 도구의 discovery에 필요한 얇은 진입점은 허용한다.

## 결과
`PASS`는 검토 범위 내 구체적 결함 없음, `WARN`은 사용 가능한 개선점, `FAIL`은 계약 위반 또는 실행 불가다.
각 지적은 파일/줄, 관측한 문제, 실제 영향, 최소 수정안으로 작성한다. 발견 사항이 없으면 없다고 적는다.
별도 review/plan 파일을 생성하지 않는다. 결과는 호출자에게 반환하고 관련 결정은 기존 PR spec에 남긴다.
