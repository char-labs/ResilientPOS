# 도메인 모델과 유비쿼터스 언어

이 프로젝트가 쓰는 DDD 용어의 정의, bounded context 9개의 요약, 코드·스키마·문서가 함께 쓰는 단어 목록이다.
업무 기능 spec을 쓰거나 새 도메인 타입·테이블·이벤트 이름을 만들 때 먼저 읽는다. Facade/Service/Aggregate의
책임 분리 표는 [README의 Engineering Principles](../../README.md#engineering-principles)가 정본이며 여기서 반복하지 않는다.
Kotlin으로 Aggregate·Value Object·Event·Repository를 어떤 형태로 쓰는지는 볼트 규칙 `rules/domain-modeling-kotlin.md`가
담당한다(`.claude/rules` 링크로 `src/**/*.kt` 편집 시 자동 로드).

원문 근거는 [도메인 청사진](../references/05_Domain_Development_Blueprint.md), [개발 가이드](../references/03_Development_Guide.md),
[시스템 설계](../references/02_System_Design.md)다. 원문은 참고 자료라 이 페이지가 정본이고, 원문과 다르게 정한 것은 §4에 적는다.
용어 정의의 골격은 [카카오페이 여신코어 DDD 사례](https://tech.kakaopay.com/post/backend-domain-driven-design/)를 참고했고,
사례의 도식 여섯 장에서 가져온 규약은 §2·§5·§6에, 사례와 다르게 가는 점은 §8에 있다.

## 1. 용어 정의

표의 타입 이름은 목표 모델이며 아직 코드에 없는 것도 있다. 원문의 커맨드·이벤트가 지금 코드에 있는지는 [아키텍처 §5.4](architecture.md#54-지금-코드에-있는-것과-없는-것)에 있고, 현재 구현 상태는 현재 상태(`docs/wiki/current-state.md`, 볼트)가 정본이다.

| 용어 | 정의 | 구분 기준 | ResilientPOS 예시 |
|---|---|---|---|
| 도메인 (Domain) | 소프트웨어가 해결하려는 문제 영역 | — | 네트워크 단절과 부분 실패 속에서도 주문·결제 상태가 중복 없이 수렴하는 매장 판매 운영 |
| 유비쿼터스 언어 (Ubiquitous Language) | 기획·개발·문서·코드·스키마가 같은 뜻으로 쓰는 단어 집합 | 한 단어가 두 뜻이면 둘 중 하나를 바꾼다 | §3 용어집. `terminal`(단말)을 코드·테이블·spec이 모두 쓰고 `pos`는 쓰지 않는다 |
| 바운디드 컨텍스트 (Bounded Context) | 한 모델과 그 용어가 유효한 명시적 경계. 경계 밖과는 공개 계약(Facade·이벤트)으로만 통한다 | 같은 단어가 다른 뜻이거나 데이터 소유자가 다르면 경계가 다르다 | Spring Modulith application module 9개 `com.resilientpos.{owner,store,catalog,terminal,order,payment,sync,reconciliation,fulfillment}`. `ModuleStructureTest`가 경계를 검사한다. Gradle 모듈이 아니다 |
| 애그리거트 (Aggregate) / 루트 | 한 트랜잭션에서 함께 일관성을 지켜야 하는 객체 묶음. 루트 하나만 외부에 노출되고 루트가 불변식을 소유한다 | "이 둘이 한 트랜잭션에서 반드시 함께 맞아야 하는가?" 예면 같은 aggregate, 아니면 별도 aggregate이고 ID로만 참조한다 | `Order`(루트) + `OrderLine` + checkout 금액. `OrderLine`을 밖에서 바꾸지 않고 `order.changeLine(...)`으로 바꾼다. `Order`와 `PaymentAttempt`는 별개 aggregate라 `orderId`로 참조하고 이벤트로 연결한다 |
| 엔티티 (Entity) | 식별자로 구별되고 생명주기가 있는 객체 | 속성이 모두 같아도 식별자가 다르면 다른 것 | `Order`, `PaymentAttempt`, `Watermark`, `ReconciliationCase`, `Fulfillment`. 식별자는 UUID v7을 애플리케이션이 저장 전에 만든다 |
| 값 객체 (Value Object) | 식별자가 없고 속성이 같으면 같은 것. 불변 | "두 인스턴스의 모든 속성이 같으면 같은 것인가?" 예면 값 객체 | `Money`, `OrderId`, `TerminalCode`, checkout 확정 금액. Kotlin `data class` + `of`/`from` 팩토리 |
| 정책 (`*Policy`) | 어느 한 aggregate에 자연스럽게 속하지 않는 계산·판정을 가진 불변 값 객체. 상태가 없고 입력 → 출력만 있다 | 규칙이 두 aggregate 사이에 있거나 매장·버전별로 바뀌면 Policy | `CheckoutPolicy`(통화 scale·반올림·합계), store가 소유하는 판매 정책. DDD 표준 용어로는 도메인 서비스의 한 형태다 |
| 도메인 서비스 (`*Service`) | 한 bounded context 안의 비즈니스 행위를 표현하는 객체 | 규칙이 어느 aggregate에도 자연스럽게 속하지 않을 때만 만든다. 책임 경계는 [README](../../README.md#engineering-principles) | `CheckoutService.request(order, policy)` |
| 애플리케이션 서비스 (`*Facade`) | use case 하나를 대표하는 진입점 | 호출자(Controller·이벤트 리스너·스케줄러)가 누구든 같은 use case면 같은 Facade다. 책임과 금지 사항은 [README](../../README.md#engineering-principles) | `OrderCommandFacade.create(OrderCommand.Create): OrderCommand.Create.Result`, `PaymentQueryFacade.findAttempts(PaymentQuery.FindAttempts)`. 조회 Facade는 쓰기 Facade와 따로 둔다 |
| 명령 / 조회 / 결과 / 뷰 | 쓰기 의도(`OrderCommand.Create`)와 그 결과(`OrderCommand.Create.Result`), 읽기 의도(`*Query`/`*Criteria`)와 그 투영(`*View`). 규약은 [README](../../README.md#engineering-principles) | 상태를 바꾸면 Command, 바꾸지 않으면 Query. 커맨드는 모듈 이름공간 `object`(`OrderCommand`) 아래 use case별 `data class`로 두고, 입력 조각(`Line`)과 결과(`Result`)는 그 커맨드 안에 둔다. Facade의 공개 입력이라 aggregate 안에 중첩하지 않는다. 중첩 타입은 따로 import하지 않고 `OrderCommand.Create.Result`처럼 이름공간부터 쓴다. 조회도 같은 모양이다. 모듈 이름공간 `object`(`PaymentQuery`) 아래 use case별 `data class`로 두고, 동적 검색 조건이 생기면 그 Query 안에 `Criteria`를 둔다. 투영 `*View`만 이름공간 밖 최상위 타입이다. 같은 투영을 여러 조회가 돌려줄 수 있어서 한 use case에 묶지 않는다 | `OrderCommand.Create → OrderCommand.Create.Result`, `PaymentQuery.FindAttempts → PaymentAttemptView` 목록. 전체 카탈로그는 [청사진 §4](../references/05_Domain_Development_Blueprint.md) |
| 도메인 이벤트 (Domain Event) | 이미 일어난 한 가지 사실. 불변이고 과거형이다 | aggregate가 상태 전이의 결과로 만들고, Facade가 커밋 안에서 발행하고, Event Publication Registry가 전달한다 | `OrderPaymentRequested`, `PaymentApproved`, `PaymentUnknown`, `SyncGapDetected`, `FulfillmentCreated`. `OrderCompleted`처럼 여러 사실을 뭉친 이름은 쓰지 않는다 |
| 리포지토리 (Repository) | aggregate 단위로 읽고 저장하는 port | aggregate 전체를 다루면 Repository, 화면용 투영은 port 없는 조회 클래스(§4.2) | `OrderRepository.findById(OrderId): Order?`, `save(Order)` |
| 공개 API (module public surface) | 다른 모듈이 import할 수 있는 것. Facade·커맨드와 조회 이름공간·`*View`·ID 값 타입·이벤트만 | `internal` 패키지 아래는 비공개. Modulith 검증이 위반을 빌드 실패로 만든다. 모듈을 건너가는 이벤트만 예외로 `contract`가 소유한다(§4.4) | `payment/PaymentManagement.kt`, `PaymentQueryFacade.kt`, `PaymentQuery.kt`, `PaymentAttemptView.kt`, `PaymentId.kt`, `PaymentEvent.kt`처럼 모듈 루트(§4.4) |

## 2. Bounded context 요약

전체 aggregate 맵과 불변식은 [청사진 §2](../references/05_Domain_Development_Blueprint.md)가 원문이다. 여기서는 용어를 맞추기 위한 요약만 둔다.

| Context | Aggregate 루트 | 소유하는 것 | 핵심 불변식 | 공개 Facade |
|---|---|---|---|---|
| `owner` | `Owner` | 점주 계정(이메일, 비밀번호 해시), 가입, 로그인 자격 확인, 로그인 실패 제한 | 이메일은 계정 하나(unique `t_owner.email`, 소문자 정규화). 평문 비밀번호는 저장하지 않는다 | `OwnerManagement` |
| `store` | `Store` | 매장 이름과 소유 점주, 판매 정책, 통화·반올림, 매장 설정 | 매장의 소유 점주는 바뀌지 않고 점주는 자기 매장만 다룬다(소속 정본은 `t_store.owner_id`). 정책은 버전으로 관리하고 과거 주문 금액을 사후에 바꾸지 않는다(정책은 아직 없다) | `StoreManagement` |
| `terminal` | `Terminal` | 단말 코드, 소속 매장, 활성화, credential rotation 이력 | 매장 안에서 코드 유일(unique `(store_id, terminal_code)`). 코드와 소속 매장은 바뀌지 않는다. 비활성 단말은 인증 불가. 이력 삭제 금지 | `TerminalManagement` |
| `order` | `Order` | line, 할인, checkout 금액·통화, lifecycle | `OPEN`에서만 금액·line 변경. checkout 이후 금액·통화 불변. 결제 승인 금액은 checkout과 일치해야 한다 | `OrderManagement` |
| `payment` | `PaymentAttempt` | provider 참조, provider idempotency, 승인·취소 시도, 결제 정본 상태 | 같은 checkout에 진행 중인 승인 시도는 하나. `UNKNOWN`은 실패가 아니다. provider 결과는 한 번만 적용한다(`UNKNOWN`은 결과가 없다는 기록이라 provider 조회로 한 번 확정한다). provider가 다른 금액으로 승인했다고 답하면 그 승인을 믿지 않고 `UNKNOWN`으로 둔다. reconciliation으로 넘긴 시도는 조회로 확정하지 않고 reconciliation의 결론으로만 확정한다 | `PaymentManagement`(쓰기), `PaymentQueryFacade`(조회) |
| `sync` | `Watermark` | 단말 watermark, operation 접수·중복 제거, gap·conflict | `lastAckedSequence`는 단조 증가. gap을 건너뛰어 전진하지 않는다 | 공개 Facade 없음(`internal`의 `SyncCommandFacade`, HTTP만 부른다) |
| `reconciliation` | `ReconciliationCase` | 불일치 case의 근거, 규칙 버전, 승인·조치 감사 기록 | 근거·규칙·감사 없이 해결하지 않는다. 결제 상태를 직접 고치지 않는다. 결제 시도 하나에 case 하나(unique `t_reconciliation_case.payment_id`). 점주는 자기 매장의 case만 해소한다 | `ReconciliationManagement`(쓰기), `ReconciliationQueryFacade`(조회) |
| `fulfillment` | `Fulfillment`, `ReceiptDelivery` | 주문 이후의 이행과 영수증 전달 | 원본 주문당 natural key로 한 번만 생성. 재시도 side effect는 멱등 | 소비 이벤트만 |
| `catalog` | `Menu` | 매장 메뉴(항목의 코드·이름·가격·분류, 통화 하나) | 매장당 메뉴 하나(PK `t_menu_pkey`). 메뉴 안에서 코드 유일, 항목 200개 이하, 코드·이름·분류는 주문 line과 같은 글자 규칙. 전체 교체만 하고 version으로 동시 수정을 거절한다. 주문 line은 메뉴와 대조하지 않는다 | `MenuManagement` |

컨텍스트 사이의 소유 규칙:
- `payment`만 결제 정본 상태를 바꾼다. `reconciliation`은 case와 근거를 소유하고 결론을 좁은 공개 command `PaymentManagement.resolveFromReconciliation`으로 요청한다. 해소 트랜잭션은 `reconciliation`이 소유하고 `payment`가 합류한다(§4.6). 결제 확정과 case 해소가 한 커밋이다.
- `payment`가 시도를 case로 넘기는 일은 사실(`PaymentReconciliationRequested`)이다. `reconciliation`의 consumer가 `paymentId`로 멱등하게 case를 연다. 넘기는 조건은 조회 결과가 불명인 채 횟수가 상한(`resilientpos.payment.unknown-query-limit`, 60)에 닿은 것(`QUERY_LIMIT_EXCEEDED`)과, 조회가 다른 금액의 승인을 알려 준 것(`AMOUNT_MISMATCH`)이다. 넘긴 시도는 더 조회하지 않는다([payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)).
- case 상태는 [시스템 설계 §5](../references/02_System_Design.md)의 `OPEN → INVESTIGATING → AUTO_REPAIRED 또는 MANUAL_REVIEW → RESOLVED`다. 분류 규칙 v1은 두 사유를 모두 `MANUAL_REVIEW`로 보낸다. 사람 없이 안전하게 내릴 결론이 없기 때문이다. 여는 명령이 `OPEN`·`INVESTIGATING`·`MANUAL_REVIEW`를 한 커밋에 처리하고 행에는 분류 결과만 남는다. 중간 상태는 따로 기록하지 않는다(같은 시각이라 연 시각·규칙 버전·상태가 같은 사실을 말한다). `AUTO_REPAIRED`로 가는 전이는 자동 조치 규칙을 만드는 PR이 더한다. case는 분류 규칙 버전을 저장해 규칙이 바뀌어도 옛 case의 분류 근거가 남는다. 점주의 승인 해소에는 PG 승인 참조와 PG 화면에서 본 승인 금액이 필수이고, 금액이 시도와 다르면 거절한다. provider가 승인이라고 답한 적이 있는 case(넘김 사유나 불명 사유가 `AMOUNT_MISMATCH`)의 거절 해소에는 PG 취소 참조가 필수다. 취소하지 않은 채 거절하면 재결제가 열려 이중 청구가 된다. 해소 기록(점주·시각·결론·참조·승인 금액·사유)은 case 행의 컬럼이다. 해소는 case당 한 번이라 이력 표를 두지 않고, 재개·배정·2인 승인처럼 이력이 필요해지면 그 PR이 만든다.
- `order`와 `payment`는 서로의 테이블·엔티티·repository를 읽거나 쓰지 않는다. 사실은 이벤트로 건너간다(`OrderPaymentRequested` → payment, `PaymentApproved` → order, `PaymentReconciliationRequested` → reconciliation, `OrderPaid` → fulfillment).
- **결제 결말 셋 중 `PaymentApproved`만 `contract`에 있다.** 그것만 경계를 넘기 때문이다. `PaymentEvent.Declined`·`PaymentEvent.Unknown`은 `payment`의 sealed 계층에 남는다(§4.4). 거절·불명이어도 주문은 `CHECKOUT_REQUESTED`에 머물고(그 회차의 결제가 아직 끝나지 않았다), 재결제는 같은 회차의 새 시도이며, `UNKNOWN`은 `payment`가 provider 조회로 확정하므로 `order`가 받을 일이 없다([payment-unknown-resolution](../spec/2026-10-01-payment-unknown-resolution.md)). 주문 취소처럼 주문이 거절을 알아야 하는 명령이 생기는 PR이 옮기고, 그 이동은 `event_publication`의 `event_type`을 바꾸므로 배포된 행이 있는지부터 본다.
- **모듈을 건너가는 이벤트는 `contract` 모듈이 소유한다.** 두 모듈이 서로의 사실을 주고받으면 타입 의존이 양방향이 되어 Modulith의 순환 검사에 걸린다. 양쪽이 함께 의존하는 곳에 그 사실을 둔다. `contract`는 bounded context가 아니다 — 업무 규칙도 상태도 없고 계약만 있다. **`contract`를 의존하는 모듈의 타입을 들지 않는다**(`orderId`·`paymentId`는 raw `UUID`로 든다). 들면 그 방향으로 간선이 생겨 순환이 되돌아온다. `contract`를 의존하지 않는 `store`·`terminal`의 `StoreId`·`TerminalId`는 순환이 없어 그대로 든다(`OrderPaid` KDoc). `ModuleStructureTest`가 `contract`에서 `order`·`payment`·`sync`·`reconciliation`·`fulfillment`·`platform`으로 가는 의존을 막는다. 소비자가 없는 이벤트는 소유 모듈에 남는다 — 경계를 넘는 것만 공유한다.
- `order`는 합계가 0원인 주문도 똑같이 checkout을 확정하고 `OrderPaymentRequested`를 낸다. 전액 할인·프로모션 주문이 거절되지 않고 주문·결제·영수증 조회가 같은 경로로 보이게 하려는 것이다. `payment`는 0원 attempt를 provider 호출 없이 승인으로 기록하고 `PaymentApproved`를 내야 한다.
- `order`는 `catalog`를 모른다. 주문 line의 상품 코드·이름·단가는 단말이 보낸 판매 시점 원본이고 서버는 메뉴와 대조하지 않는다. 메뉴가 바뀌어도 과거 line은 그대로다([menu-catalog](../spec/2026-10-26-menu-catalog.md)).
- `sync`는 접수·중복·순서만 판정하고, 받아들인 명령은 소유 컨텍스트의 Command Facade로 넘긴다. `SyncOperationApplied`는 기술 감사 이벤트이며 `OrderCreated`를 대체하지 않는다.
- `foundation`은 프레임워크 없는 값 타입(`Money`, 식별자 생성기)과 모델링 원시 타입(`Transition`, `DomainEvent`, §4.5)만 공유한다. 주문·결제 같은 업무 개념을 두는 곳이 아니다. 모듈을 건너가는 이벤트는 업무 사실이므로 `foundation`이 아니라 `contract`에 둔다.

### aggregate 안의 구성
루트가 바뀔 때 같은 트랜잭션에서 함께 남겨야 하는 것은 별도 컨텍스트가 아니라 그 aggregate의 자식 엔티티다. 상태 변경과 그 기록이 따로 구현되면 기록이 누락되거나 중복된다. 아래는 [청사진 §2·§6.2](../references/05_Domain_Development_Blueprint.md)를 바탕으로 이 PR에서 정리한 설계안이며, 각 모듈의 첫 마이그레이션이 정본이 된다.

| 루트 | 자식 엔티티 (같은 트랜잭션) | 왜 같은 aggregate인가 |
|---|---|---|
| `Order` | `OrderLine`(판매 시점 상품 코드·이름·단가·수량), checkout(회차별 확정 금액. 통화는 주문의 것이다. 정책 버전은 store 정책이 생길 때 더한다. `Checkout`은 `OrderLine`처럼 도메인 ID `CheckoutId`를 갖고 `t_order_checkout`의 PK는 `id` 하나다. 회차 중복은 unique `(order_id, checkout_no)`가 막는다) | line 변경과 금액, checkout 확정과 상태 전이가 한 커밋으로 맞아야 한다 |
| `PaymentAttempt` | provider 요청·응답 결과. provider idempotency 기록이 attempt의 자식인지 컨텍스트 공용 테이블인지는 payment PR spec에서 정한다 | "provider 결과를 한 번만 적용했다"를 같은 트랜잭션의 기록이 증명한다. 취소는 별도 attempt다([외부 연동 전략](../references/04_External_Integration_Strategy.md)) |
| `Terminal` | credential rotation 이력(`TerminalCredential`, `t_terminal_credential`). 수가 한정되지 않아 루트가 목록으로 들지 않는다. 회전은 terminal 행을 잠그고 옛 credential 폐기와 새 credential 발급을 한 커밋으로 한다 | 회전과 이력이 따로 커밋되면 어느 자격증명이 유효한지 알 수 없다 |
| `Watermark` | operation 접수 기록(`SyncOperation`, `t_sync_operation`). 수가 한정되지 않아 루트가 목록으로 들지 않고 같은 트랜잭션에서 함께 쓴다 | watermark 전진과 접수 기록이 함께 커밋돼야 gap을 건너뛰지 않는다 |
| `ReconciliationCase` | 없음(근거와 해소 기록은 루트의 값이다. 해소는 case당 한 번이고 근거 출처는 payment 하나다) | "근거·감사 없이 해결하지 않는다"를 한 행이 지킨다. 출처가 늘거나 이력이 필요해지면 evidence·이력을 자식으로 뺀다([payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)) |
| `Store` | policy 버전 | 정책을 바꿀 때 새 버전 행이 함께 커밋되지 않으면 이미 발행된 checkout이 가리키는 버전이 없어진다 |
| `Fulfillment`, `ReceiptDelivery` | 없음(단독 루트) | natural key 한 건이면 충분하다 |

지금 있는 JPA 엔티티 14개의 역할·참조 관계·UX 흐름별 동작은 [엔티티 지도](entity-map.md)에 있다. 자식 엔티티는 루트를 통해서만 만들고 바꾼다. 다른 aggregate의 사실(예: 결제 승인)이 필요하면 자식으로 끌어오지 않고 이벤트로 받는다. 한 컨텍스트에 루트가 여럿일 수 있다(`fulfillment`). 루트 하나가 곧 컨텍스트는 아니다.

## 3. 유비쿼터스 언어 용어집

코드 식별자, 테이블·컬럼 이름, 이벤트 이름, spec 본문은 이 표의 단어를 쓴다. 화면 라벨은 현장 용어("포스기")를 써도 되지만 도메인·스키마 이름은 바꾸지 않는다.
새 단어가 필요하면 PR spec에서 제안하고 머지 시 이 표에 추가한다. 이미 있는 단어에 다른 뜻을 붙이지 않는다.
영어 이름은 직역이 아니라 업무 의미를 담는다. 사례가 납부를 Payment가 아니라 Recovery(한도를 복원한다)로 부른 것처럼, 이 저장소의 `reconciliation`(불일치를 근거로 해소한다), `fulfillment`(주문 이후를 이행한다)도 같은 기준이다.

| 용어 (코드·스키마) | 뜻 | 기각한 대안 | 이유 |
|---|---|---|---|
| `terminal` | 매장에 설치된 판매 단말 | `pos` | 제품 전체가 POS라 자기 참조다. 코드에서 `pos`는 position으로 읽힌다. 원문 요구사항과 오프라인 명령 봉투(`terminalId`)가 이미 `terminal`을 쓴다 |
| `credential` (terminal) | 단말을 인증하는 비밀값과 그 이력. 평문은 저장하지 않고 해시만 둔다. 유효한 것은 단말당 하나이고 폐기된 것도 지우지 않는다 | `token` | 코드에서 `token`은 단말이 드는 평문 하나만 가리킨다. 폐기 상태와 이력을 담는 행은 `credential`이다. 테이블은 `t_terminal_credential` |
| `owner` | 점주. 매장을 소유하고 자기 매장의 단말을 관리하는 SaaS 고객. 앱 자체 계정(이메일·비밀번호)으로 로그인하고 경로는 `/owner/**`다 | `merchant`, `manager`, `operator` | `merchant`는 payment의 PG 가맹점과 뜻이 겹친다. `manager`는 매장 직원 관리자로도 읽힌다. `operator`는 매장을 넘나드는 플랫폼 운영자에 남겨 둔다 |
| `operator` | 플랫폼 운영자. 우리 조직에서 매장을 넘나드는 운영 작업(DLT 재투입·폐기 표시)을 하는 직원. 앱에 계정이 없고 사내 IdP가 발급한 Bearer 토큰(권한 `resilientpos-operator`)으로 `/admin/**`를 부른다. 행위자는 토큰의 `sub`다 | `admin` | `admin`은 경로(`/admin`) 이름으로만 쓰고 주체는 참고 문서의 operator를 따른다. 점주와 섞지 않는다. 계정을 IdP에 둔 이유는 [platform-operator-dlt-redrive](../spec/2026-10-21-platform-operator-dlt-redrive.md) 결정 1 |
| `dismissal` (DLT) | 폐기 표시. 플랫폼 운영자가 DLT 메시지를 재투입하지 않기로 한 기록(사유·행위자). 메시지를 DLT에서 지우지 않고, 미처리 DLT 수에서만 빠진다 | `discard`, `delete`, `skip` | 메시지는 지워지지 않고 표시만 남는다. 한국어 "폐기"는 단말 `credential`의 폐기(revoke)와 겹치므로 코드·스키마는 `dismissal`을 쓴다. 테이블은 `t_dead_letter_dismissal`([alert-state-gauges](../spec/2026-10-22-alert-state-gauges.md)) |
| `oldest_seconds` (경과 시간) | 아직 끝나지 않은 일 가운데 가장 오래된 것이 시작된 뒤 지금까지 흐른 시간(초). 결과 불명 결제·발행 기록 알림이 개수 대신 이 값을 본다 | `나이`, `수명`, `생명주기` | 운영 모니터링의 영어 age를 그대로 옮긴 "나이"는 한국어로 어색하다. 수명은 살 수 있는 전체 기간(TTL), 생명주기는 상태가 거치는 단계라 뜻이 다르다. metric 이름은 영어 `…_oldest_seconds`를 그대로 쓴다([alert-state-gauges](../spec/2026-10-22-alert-state-gauges.md)) |
| `operation` (sync) | 단말이 오프라인에서 만든 명령 한 건. 식별자는 `operationId`(UUID v7) | `receipt` | 한 스키마에서 receipt가 접수증과 고객 영수증 두 뜻으로 쓰였다. 봉투의 `operationId`와 어휘를 맞췄다. 테이블은 `t_sync_operation` |
| `watermark` | 단말별로 서버가 확정한 마지막 sequence(`lastAckedSequence`) | `terminal sync state` | state는 모든 테이블에 해당해 아무 말도 하지 않는다. 기획 문서가 이미 쓰는 단어다. 테이블은 `t_sync_watermark` |
| `sequence` (terminal sequence) | 한 단말 안에서 단조 증가하는 명령 순번. 누락(gap) 탐지의 근거 | — | UUID 생성 순서, Kafka 순서, aggregate version과 다르다. 서로 대체하지 않는다 |
| `checkout` | 결제 시도 회차에 대해 확정한 금액·통화·정책 버전(정책 버전은 store 정책이 생길 때 더한다) | `checkout snapshot` | snapshot은 구현 용어다. 이 값은 "N회차 결제 시도의 확정 금액"이라는 업무 사실이다. 테이블은 `t_order_checkout`. [청사진 §1.1](../references/05_Domain_Development_Blueprint.md)의 `CheckoutSnapshot`·`snapshotOf`는 `Checkout`·`checkoutOf`로 대체한다 |
| `attempt` (payment) | 한 주문에 대한 provider 요청 1회. 식별은 `PaymentId`이고 회차 번호는 두지 않는다. 승인과 취소는 각각 별도 attempt다 | `payment`, `transaction` | 한 요청의 결과(승인·거절·`UNKNOWN`)를 한 회차에 담아야 한다. transaction은 DB 용어와 충돌한다 |
| `UNKNOWN` | provider 결과를 아직 확인하지 못한 결제 상태. 실패가 아니다 | `FAILED`, `TIMEOUT` | timeout은 전송 관찰의 실패이고 결제 결과의 실패가 아니다. `UNKNOWN`에서 새 승인 요청을 재시도하지 않고 provider 조회 → reconciliation으로 수렴한다. 조회 확정은 `payment`의 주기 작업이 하고(§4.3), 조회로도 확정되지 않으면 reconciliation case로 넘긴다. 불명이 된 사유(`unknown reason`)를 시도에 남긴다 |
| `gap` / `duplicate` / `conflict` / `rejected` | sync 판정 결과. 순번 누락 / 이미 접수한 operation의 같은 내용 재전송 / 확정한 순번에 다른 내용이나 모르는 operation / 소유 컨텍스트가 도메인 규칙으로 거절한 operation(순번은 확정되고 단말은 버린다) | 일반 `error`, HTTP 500 | 네 가지는 각각 다른 복구 경로를 가진 업무 결과다. 항목 단위 결과로 돌려주고 부분 성공을 200 하나로 숨기지 않는다. 적용된 항목은 `applied`다([sync-intake](../spec/2026-09-30-sync-intake.md)) |
| `menu` | 매장 메뉴. 판매할 상품 항목과 통화를 담은 문서 하나다. 서버가 정본이고 단말은 받아 둔 사본으로 판다 | `product`, `catalog` | `t_product`(상품 마스터)를 두지 않는다는 결정([order-line-blank-product](../spec/2026-09-21-order-line-blank-product.md))과 섞이지 않게 `product`를 쓰지 않는다. `catalog`는 모듈 이름으로만 쓴다. 테이블은 `t_menu`([menu-catalog](../spec/2026-10-26-menu-catalog.md)) |
| `menu item` | 메뉴 항목. 코드·이름·가격·분류 넷이다. 표시 순서는 항목 배열 순서다 | `product`, `catalog item` | 위 `menu`와 같다. 항목은 메뉴 문서 안의 값이고 따로 행을 두지 않는다. 주문 line은 항목을 가리키지 않고 판매 시점 값을 기록한다 |
| `case` (reconciliation) | 불일치 한 건의 근거·규칙 버전·조치·감사 기록 | `issue`, `ticket` | ticket은 KDS·프린터의 표시 매체(화면 카드, 종이 주문표)를 가리키는 업계 용어다 |
| `evidence` | POS·서버·provider 각각이 말하는 사실의 기록 | `proof`, `log` | 세 출처를 나란히 비교하는 것이 reconciliation의 본질이다 |
| `reconciliation requested` (넘김) | `payment`가 스스로 확정하지 못한 시도를 case로 넘긴 사실. 넘긴 시각은 `t_payment_attempt.reconciliation_requested_at`이 정본이다 | `escalated`, `handed off` | 이벤트 이름 `PaymentReconciliationRequested`와 같은 말을 쓴다. 넘긴 뒤 `payment`는 그 시도를 조회하지 않는다 |
| `unknown reason` (불명 사유) | 시도가 `UNKNOWN`이 된 까닭. `RESULT_UNCONFIRMED`(결과를 받지 못함)와 `AMOUNT_MISMATCH`(받은 승인의 금액이 다름) | `failure reason` | 불명은 실패가 아니라서 실패 사유라고 부르지 않는다. `UNKNOWN`이 될 때 정하고 바꾸지 않는다 |
| `rule version` (분류 규칙 버전) | case를 자동 조치와 사람 확인 가운데 어디로 보낼지 정한 규칙의 버전 | `policy version` | policy version은 store 판매 정책의 버전을 가리킨다 |
| `fulfillment` (aggregate) | 결제된 주문 하나를 이행하는 단위. 주문당 natural key로 1건 | `kitchen ticket`, `ticket`, `fulfillment order` | 업종(카페의 바, 식당의 주방, 소매 픽업)을 가리지 않는다. 원문 청사진의 `KitchenTicket`이 이것이다. kitchen은 F&B 업종을, ticket은 KDS·프린터의 표시 매체를 전제해서 쓰지 않는다. 이름은 [Square Orders API](https://developer.squareup.com/docs/orders-api/fulfillments)의 `Fulfillment`(주문당 이행 단위, 이행 방식 `type`)를 따랐다. Shopify·Salesforce의 `FulfillmentOrder`는 위치별 품목 묶음이라 한 주문에 여럿이고 `Order`와 헷갈린다. 업종에 따른 구분은 이름이 아니라 이행 방식 `type`이 맡는다. 재시도해도 한 번만 만들어진다 |
| `receipt` (fulfillment) | 고객 영수증 전달(`ReceiptDelivery`) | — | sync 쪽에서는 이 단어를 쓰지 않는다(위 `operation` 참고) |
| `store policy` | 통화·반올림·판매 규칙. 버전이 있다 | `settings`, `config` | 정책은 업무 규칙이고 버전으로 과거 주문에 적용된 값을 추적한다 |
| `aggregate version` | 한 aggregate의 상태 순서(`@Version`) | — | 동시 수정 충돌 감지용이다. terminal sequence와 다르다 |
| `contract` (모듈) | 모듈을 건너가는 이벤트와 그 payload를 소유하는 모듈. bounded context가 아니다 | `shared`, `common`, `api` | "공개 계약"이라는 일반어와 겹치지만, 여기서는 **그 계약을 담는 모듈 이름**으로만 쓴다. 모듈 자신의 공개 surface는 §1의 "공개 API"로 부른다. `shared`·`common`은 무엇이든 들어와도 되는 이름이라 경계가 서지 않고, `api`는 §4.4가 쓰지 않기로 한 하위 패키지 이름과 충돌한다 |

이벤트 이름은 과거형 한 가지 사실이다.

| 쓰지 않는 이름 | 대신 쓰는 이름 | 이유 |
|---|---|---|
| `OrderCompleted` | `OrderAccepted`, `OrderPaid`, `FulfillmentCompleted`, `OrderClosed` | "완료"가 결제 완료인지 주방 완료인지 마감인지 읽히지 않는다 |
| `PaymentFailed`(timeout 시) | `PaymentUnknown` | timeout은 결과가 아니라 미확인이다 |
| `SyncCompleted` | `SyncOperationApplied` + 소유 컨텍스트의 사실 이벤트 | 동기화 접수와 업무 사실을 분리한다 |
| `PaymentConfirmed`(provider 승인 시) | `PaymentApproved` | 원문 [개발 가이드 §1.1](../references/03_Development_Guide.md)과 [청사진 §3](../references/05_Domain_Development_Blueprint.md)이 두 이름을 섞어 쓴다. provider 승인 사실은 `PaymentApproved`다. reconciliation 해소 결과는 새 이벤트 없이 조회 확정과 같은 `PaymentApproved`·`PaymentEvent.Declined`를 낸다([payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)) |

## 4. 확정한 설계 결정

### 4.1 Aggregate 상태 전이는 불변 객체가 새 인스턴스를 반환한다
- 전이 메서드는 자신을 바꾸지 않고 바뀐 aggregate와 발생한 이벤트를 돌려준다. 예: `order.requestCheckout(ids, now)`는 `CHECKOUT_REQUESTED` 상태의 새 `Order`와 `OrderPaymentRequested`를 반환한다. 처음 설계의 인자는 `policy`였다. 합계가 단가 곱 수량의 합뿐이고 `Money`가 통화 자릿수를 강제해서 반올림할 계산이 없으므로 `CheckoutPolicy`와 정책 버전은 할인·세금처럼 반올림이 필요한 첫 PR이 store 정책과 함께 도입한다([order-request-checkout-domain](../spec/2026-09-21-order-request-checkout-domain.md)).
- 근거: 볼트 규칙 `effective-java-for-kotlin.md` Item 17과 `kotlin-idioms-and-design-patterns.md` §1(`order.cancelled(reason)`)이 이미 이 방향이다. 도메인 테스트가 Spring 없이 값 비교로 끝나고, 전이 실패 시 원본이 그대로 남아 실패 원자성(Item 76)이 공짜로 따라온다.
- 원문 [청사진 §1.1](../references/05_Domain_Development_Blueprint.md)의 `status = OrderStatus.CHECKOUT_REQUESTED` 예시는 이 결정으로 대체한다. `@Version` 낙관적 잠금은 JPA 엔티티에 남고, Repository 구현이 새 aggregate를 관리 엔티티에 적용할 때 버전 충돌을 감지한다.

### 4.2 Aggregate와 JPA 엔티티는 별개 클래스다
- aggregate·값 객체·Policy·Service는 `internal/domain`에 두고 JPA·Spring 애너테이션을 갖지 않는다. JPA 엔티티, Spring Data repository, 변환기(`from(aggregate)`, `apply(aggregate)`, `toDomain()`)는 `internal/adapter/persistence/command`에 둔다. Repository 인터페이스는 도메인 쪽, 구현은 adapter 쪽이다.
- 화면용 조회는 `internal/adapter/persistence/query`의 구체 클래스(`PaymentAttemptQueries`)가 하고 조회 Facade(`PaymentQueryFacade`)가 그것을 바로 부른다. port 인터페이스를 두지 않는다. `*View`는 aggregate 경계에 들어가지 않아(§5 경계표) 도메인 port의 시그니처가 될 수 없고, 구현이 하나뿐인 인터페이스는 두지 않는다. aggregate를 거치지 않고 엔티티를 바로 View로 바꾼다. 조회 메서드는 Kotlin JDSL이고 `@ReadOnlyTransactional`이다. 한 쿼리면 Facade는 트랜잭션을 선언하지 않고, 여러 쿼리를 한 시점에 읽어야 하면 Facade가 `Tx.readOnlyTx`로 묶는다([payment-status-query](../spec/2026-10-06-payment-status-query.md)).
- 근거: [청사진 §6.1](../references/05_Domain_Development_Blueprint.md) 패키지 구조가 이미 이 분리를 전제하고, [의존성 방향 가드 spec](../spec/2026-09-15-dependency-direction-guard.md)이 "도메인 레이어는 Spring·repository에 의존하지 않는다"는 ArchUnit 규칙을 첫 도메인 PR에 추가하기로 했다. 4.1의 불변 aggregate는 JPA 관리 엔티티와 같은 클래스일 수 없다.
- 이름: JPA 엔티티는 aggregate 이름 + `Entity`(`OrderEntity`, `OrderLineEntity`)이고 `Jpa`를 넣지 않는다. Spring Data repository만 도메인 port(`OrderRepository`)와 단순 이름이 겹치므로 `OrderJpaRepository`처럼 `Jpa`를 넣는다.
- **JPA 연관관계 매핑을 쓰지 않는다.** `@OneToMany`·`@ManyToOne`·`@OneToOne`·`@ManyToMany`와 `@ElementCollection`이 대상이다. 다른 aggregate는 물론 같은 aggregate 안의 자식도 부모 ID 컬럼만 가진 독립 엔티티로 두고(`OrderLineEntity.orderId`) adapter가 부모 ID로 조회한다(§4.3). 조립과 변경 반영(자식 ID로 맞춰 갱신·추가·삭제)은 persistence adapter가 한다. fetch 전략·cascade·flush 순서가 매핑 뒤에 숨지 않고 읽는 쿼리가 코드에 보인다. 그래서 자식도 도메인 ID(`OrderLineId`)를 가진다. 위치는 식별자가 아니다. DB FK 제약도 두지 않는다. 참조 컬럼에는 index만 두고, 무결성은 aggregate를 한 트랜잭션으로 저장하는 소유 모듈이 지킨다.
- 엔티티는 `platform.BaseEntity`를 상속한다. Hibernate의 `@CreationTimestamp`·`@UpdateTimestamp`(`SourceType.VM`, 애플리케이션 시각)가 채우는 `created_at`·`updated_at`, `@SoftDelete(TIMESTAMP)`의 `deleted_at`(DB `current_timestamp`)을 준다. 두 시각을 `SourceType.DB`로 두지 않는다. Hibernate 7.4.5가 UPDATE의 generated 값을 읽느라 갱신 행 수 검사를 건너뛰어 `@Version` 충돌이 낙관적 잠금 예외로 나오지 않는다. 한 INSERT의 `created_at`과 `updated_at`은 같지 않을 수 있고 `@Version`을 선언한 엔티티에서 갱신된 적 없는 행은 `version = 0`으로 판정한다([commit-version-conflict-optimistic-lock](../spec/2026-09-21-commit-version-conflict-optimistic-lock.md)). 삭제된 행은 모든 조회에서 걸러진다. JPA callback이나 활성 상태 컬럼으로 직접 구현하지 않는다. `id`는 `BaseEntity`에 없다(도메인 ID는 UUID v7을 저장 전에 만든다). 엔티티 생성자 파라미터에는 기본값을 두지 않는다. 인자 없는 생성자는 `kotlin("plugin.jpa")`가 만들고, 기본값이 있으면 값이 빈 엔티티가 컴파일된다([order-create-order-persistence](../spec/2026-09-16-order-create-order-persistence.md)).
- **`@Version`은 `BaseEntity`에 두지 않고 낙관적 잠금이 필요한 엔티티가 직접 선언한다.** 지금은 aggregate 루트인 `OrderEntity`뿐이다. 루트를 통해서만 바뀌는 `OrderLineEntity`와 넣기만 하는 `OrderCheckoutEntity`에는 없고 두 테이블에 `version` 컬럼도 없다. 기반 클래스를 버전 있는 것과 없는 것 둘로 나누지도 않는다. 공통 기반에 두면 모든 테이블에 `version`이 생겨서 필요 없는 곳에 왜 있는지를 매번 설명해야 한다. 필요한 곳에 선언이 있으면 그 선언이 의도를 말해 준다. 선언할 때 타입은 `Long?`이다. 도메인 ID를 저장 전에 만들기 때문에 primitive면 Spring Data가 새 엔티티를 기존 행으로 보고 `merge`해 SELECT와 UPDATE가 더 나간다. 같은 이유로 `@Version`이 없는 엔티티의 새 행은 Spring Data의 `save`·`saveAll`에 넘기지 않고 persistence adapter가 `EntityManager.persist`로 넣는다. 넘기면 새 행마다 SELECT가 하나씩 더 나간다. 기존 행은 같은 트랜잭션에서 읽은 관리 엔티티라 `apply`만 하면 된다. adapter의 저장 메서드는 `@Transactional`을 선언해 Facade의 트랜잭션에 합류한다. 선언이 없으면 트랜잭션 없이 부른 호출에서 루트만 커밋되고 자식의 `persist`가 실패해 자식 없는 루트가 남는다([base-entity-explicit-version](../spec/2026-09-21-base-entity-explicit-version.md)).
- **저장 메서드는 저장만 한다. 제약 위반은 커밋을 소유한 Facade가 번역한다.** persistence adapter의 저장 메서드는 변경을 영속성 컨텍스트에 넘기는 데서 끝나고, 제약 위반을 가리려고 예외를 바꾸지 않는다. 운영 코드는 목적과 관계없이 flush하지 않는다. 위반은 커밋에서 `DataIntegrityViolationException`으로 드러나고, 그 커밋을 연 Facade 메서드(`Tx`·`Lock` 블록을 연 쪽)가 블록 밖에서 제약 이름으로 가려 바꾼다. 블록 안의 JPA 조회가 auto-flush를 일으켜 위반이 커밋 전에 드러나도 같은 예외다. JPA 쿼리는 `@Repository`인 `JdslQueryExecutor`와 Spring Data repository만 만들어 번역되고, `EntityManager.find`는 auto-flush하지 않는다. `@Repository`가 아닌 빈에서 `EntityManager`나 Hibernate 세션으로 쿼리를 만들면 Hibernate 예외가 그대로 나와 이 번역을 빗나가므로 구조 테스트가 막는다. 업무 규칙이 막은 중복(같은 이메일, 같은 매장의 단말 코드)은 도메인 예외(`OWNER_EMAIL_DUPLICATED` 등)이고, 같은 멱등 키의 요청이 겹친 경합(같은 `clientOrderId`의 주문 생성)은 경합 예외(`ConcurrencyFailureException`, 409 `CONCURRENT_REQUEST`)다. 호출자 트랜잭션에 합류하는 메서드(`OrderCommandFacade.createInCallerTransaction`)는 커밋이 호출자의 것이라 번역하지 않는다. 그래서 저장 메서드가 SQL을 바로 내보내거나 영속성 컨텍스트 전체를 내보내지 않는다. flush로 SQL 순서를 맞추지도 않는다. 한 커밋 안의 변경 순서가 제약에 걸리면 그 제약을 커밋 때 검사하게 한다(`ux_terminal_credential_active`). 그 위반도 커밋에서 `DataIntegrityViolationException`으로 오지만 exclusion 제약이면 SQLState가 `23P01`이라 판별 함수(unique `23505`만 본다)에 걸리지 않는다. exclusion 위반을 업무 오류로 번역해야 하면 그 PR이 판별 함수가 `23P01`도 보게 바꾼다(그 전에는 500이다). `ConstraintTranslationTest`가 어댑터의 판별 함수 호출, 운영 코드의 flush(`EntityManager`·Spring Data repository·`TransactionStatus`의 `flush`·`saveAndFlush`·`saveAllAndFlush`) 호출, `JdslQueryExecutor` 밖의 `EntityManager`·Hibernate 세션 쿼리 생성을 막고 `JdslQueryExecutor`의 `@Repository`를 고정한다([contention-error-mapping](../spec/2026-10-20-contention-error-mapping.md)).
- 비용: aggregate마다 클래스가 둘이고 변환기가 붙는다. 그 대신 도메인 테스트에 DB가 없고, JPA 엔티티 규칙(`data class` 금지, 프록시, 지연 로딩)이 도메인에 새지 않는다.

### 4.3 이벤트 전달과 저장 형식
- 모듈 안 이벤트 전달은 Spring Modulith Event Publication Registry(`EVENT_PUBLICATION` 테이블)를 쓴다. 별도 outbox 테이블과 processed-event 보조 테이블은 만들지 않는다. 멱등성은 자연 키의 unique 제약이 담당한다. `payment`가 같은 `OrderPaymentRequested`를 다시 받을 때는 그 checkout의 승인 시도를 결말과 무관하게 찾아 돌려준다 — 거절된 시도는 partial unique의 술어 밖이기 때문이다. `payment`에서 사실의 멱등 키는 사실로 만든 첫 승인 시도의 unique다(`retried_from`이 없는 승인 시도를 `(order_id, checkout_no)`당 하나로 묶고 soft delete된 행에도 걸린다). 같은 사실이 동시에 와서 앞 시도가 거절된 뒤에도 두 번째가 들어가지 않는다. 여러 인스턴스에 같은 사실이 동시에 오면 분산 락 블록(`Lock.executeWithLock`, 아래 "분산 락은 `Lock` 블록으로 건다")이 늦게 온 요청을 앞 요청의 커밋까지 기다리게 해서 앞 시도를 돌려받게 한다. 이 잠금은 완화 수단이라 Redis 장애나 대기 초과면 잠그지 않고 진행하고(fail-open) 그때는 unique가 막는다. 재결제로 만든 시도는 `retried_from`에 원래 시도를 가져 그 술어 밖이다([payment-advisory-lock](../spec/2026-09-26-payment-advisory-lock.md)). 진행 중인 승인을 하나로 묶는 partial unique(`(order_id, checkout_no)`에 상태 술어를 건다)는 재결제를 포함한 이중 승인의 방어선이다. 무조건적인 복합 키는 한 주문의 시도 수를 제한하므로 쓰지 않는다. 근거는 [ADR-004](../references/01_ResilientPOS_PRD_Backend_Requirements.md)이고, 보조 테이블을 두지 않는 것은 이 PR에서 정했다. "스키마 변경 검토" 절의 질문 1·4와 같은 판단이다. [README](../../README.md#engineering-principles)의 "Event Publication Registry 또는 outbox/inbox"에서 outbox는 외부 전달(Kafka)을 붙일 때의 이야기다.
- **모듈 사이 이벤트 다섯은 Kafka를 거친다.** 이벤트 타입에 `@Externalized`를 달아 Modulith가 커밋 뒤 토픽으로 보내고, 받는 쪽은 `@KafkaListener` consumer다. `event_publication`에는 이벤트마다 externalizer(`org.springframework.modulith.events.support.EventExternalizerModuleListener.externalize(java.lang.Object)`)의 행 하나만 남고 "브로커로 보냈는가"만 추적한다. 소비 실패는 Kafka 쪽 재시도와 DLT가 맡는다([kafka-event-redelivery](../spec/2026-09-26-kafka-event-redelivery.md)).

  | 이벤트 | 토픽 | consumer(모듈) | consumer group |
  |---|---|---|---|
  | `contract.OrderPaymentRequested` | `order.payment-requested` | `OrderPaymentRequestedListener`(payment) | `payment.order-payment-requested` |
  | `payment.PaymentEvent.AttemptCreated` | `payment.attempt-created` | `PaymentAttemptCreatedListener`(payment) | `payment.attempt-created` |
  | `contract.PaymentApproved` | `payment.approved` | `PaymentApprovedListener`(order) | `order.payment-approved` |
  | `contract.OrderPaid` | `order.paid` | `OrderPaidListener`(fulfillment) | `fulfillment.order-paid` |
  | `contract.PaymentReconciliationRequested` | `payment.reconciliation-requested` | `PaymentReconciliationRequestedListener`(reconciliation) | `reconciliation.payment-reconciliation-requested` |

  - key는 `orderId`다. 흐름이 인과적이라(다음 이벤트는 앞 consumer의 커밋 뒤에 발행된다) 토픽 사이의 순서는 필요 없고, 같은 주문이 한 파티션에 차례로 서면 된다. 동시 배달은 리밸런스 순간으로 좁혀진다.
  - 값은 `serialized_event`와 같은 Jackson JSON이다. consumer는 메서드 파라미터 타입으로 읽고 타입 헤더를 쓰지 않는다. 아래 "이벤트 클래스의 모양이 저장 형식" 규칙이 Kafka 메시지에도 그대로 걸린다.
  - **토픽 이름·consumer group·key도 저장 형식이다.** 토픽 이름을 바꾸면 이미 쌓인 메시지를, group을 바꾸면 커밋된 offset을 잃는다(새 group은 처음부터 다시 읽는다). 토픽은 `application.yaml`의 `resilientpos.kafka.topics` 목록으로 앱이 기동할 때 만들고(DLT `이름.DLT` 포함, DLT는 보존 기간 없음), 브로커의 자동 생성은 끈다. 새 이벤트를 더하면 이 목록에도 넣고 fixture와 `schemaVersion`도 붙인다([이벤트 계약](event-contract.md) 7절). consumer가 듣는 토픽이 빠지면 `KafkaEventDeliveryIntegrationTest`가 잡는다. 파티션 수(`resilientpos.kafka.partitions`, 3)는 환경 변수로 열지 않는다. 값이 커지면 `KafkaAdmin`이 기동하면서 늘려 key 배치가 바뀌고 그 순간 같은 주문의 순서가 깨질 수 있으니, consumer를 비운 뒤 설정을 바꾸는 PR로 늘린다. consumer 스레드 수는 파티션 수와 같다. 새 consumer group은 `auto-offset-reset: earliest`라 첫 배포에서 보존된 메시지를 모두 처리한다. 외부 부작용이 있는 consumer를 더하는 PR은 `@KafkaListener(properties = ["auto.offset.reset=latest"])`가 맞는지 함께 정한다.
  - **재시도는 blocking이고 허용 목록이다.** 잠금 대기 초과·쿼리 타임아웃·트랜잭션 시간 초과·unique 경합, 그리고 처리 도중 DB 연결이 끊겨 롤백까지 실패한 경우(`JpaSystemException`·`TransactionSystemException`으로 온다)는 같은 자리에서 1초에서 2배씩 5회(합계 약 31초, `resilientpos.kafka.retry.*`) 다시 시도하고, DB에 닿지 못하는 실패(커넥션 획득 실패·연결 끊김)는 횟수 없이 30초 간격까지 늘려 기다린다. 그동안 같은 파티션의 뒤 메시지는 기다린다. 경합 재시도가 모두 실패하면 `원토픽.DLT`로(key로 파티션을 정해) 보내고 offset을 넘긴다. 목록 밖의 예외(`DomainException`, 변환 실패, 버그)는 다시 해도 같은 결과라 바로 DLT로 간다. **파티션 안의 순서는 전송 순서다.** externalizer가 비동기라 같은 주문의 두 이벤트가 커밋 순서와 다르게 전송될 수 있으므로 consumer는 순서에 기대지 않고 멱등으로 견딘다. `PAYMENT_APPROVAL_MISMATCH`의 case 자리가 발행 기록에서 `payment.approved.DLT`로 옮겨졌다.
  - DLT 전송 자체가 실패하면 재시도 상태가 처음으로 돌아가 같은 메시지를 다시 처리한다(메시지를 버리지 않는다). 그때 ERROR 로그와 `event_kafka_dead_letter_failed_total{topic}`이 남는다. 복제 수는 설정하지 않으면 브로커 기본값을 따르고, 한 번의 poll은 최대 40건이며(`max-poll-records`, 승인 consumer의 레코드 최대 처리 시간 3.7초 × 40이 `max.poll.interval.ms`의 절반 아래다. [용량 기준](capacity.md)), 기동 때 브로커에 닿지 못하면 앱이 뜨지 않는다(`admin.fail-fast`).
  - **DLT 재투입.** 원인을 고친 뒤 플랫폼 운영자가 `/admin` API로 DLT의 메시지를 원 토픽에 다시 넣는다. consumer가 멱등이라 다시 넣어도 결과는 하나다([platform-operator-dlt-redrive](../spec/2026-10-21-platform-operator-dlt-redrive.md)).
    1. `GET /admin/v1/dead-letters?topic=order.paid.DLT&partition=0&fromOffset=0&limit=50`으로 메시지를 고른다. 항목에 key, 값, 원 토픽·partition·offset, 원인 예외, `schemaVersion`, 재투입 기록, 폐기 기록이 있다. 설정된 DLT 토픽만 읽고 consumer group의 offset을 바꾸지 않는다. 다음 쪽은 마지막 `offset + 1`이다.
    2. `POST /admin/v1/dead-letters/{topic}/{partition}/{offset}/redrive`에 사유(`reason`)를 실어 한 건씩 넣는다. 같은 key와 값 바이트를 원 토픽에 보내고, 넣은 자리·운영자(`sub`)·사유를 `t_dead_letter_redrive`에 남긴다. 같은 레코드(좌표와 레코드 시각)를 다시 요청하면 다시 보내지 않고 처음 기록을 돌려준다. DLT 토픽을 다시 만들어 offset이 재사용돼도 레코드 시각이 달라 새 메시지로 본다. 동시 요청의 진 쪽처럼 보냈는데 기록이 남지 않으면 WARN 감사 줄(`DEAD_LETTER_REDRIVE_UNRECORDED`)이 행위자를 남긴다.
    3. 넣기 전에 지금 코드로 값을 읽어 본다. 아는 것보다 높은 `schemaVersion`이나 모르는 enum 값이면 `422 DEAD_LETTER_NOT_READABLE`이고 아무것도 보내지 않는다([이벤트 계약](event-contract.md) 8절). 롤링 배포 중이면 요청을 받은 pod만 확인하므로, 그 버전을 아는 코드가 모든 pod에 배포됐는지는 운영자가 본다.
    4. 원인이 남아 있으면 넣은 메시지가 다시 DLT로 간다. 새 DLT 레코드의 `kafka_dlt-original-offset`이 재투입 기록의 넣은 offset과 같아 목록에서 이어 볼 수 있다.
    5. 넣지 않기로 한 메시지(불일치 승인처럼 다시 넣어도 같은 결과인 것, 다른 경로로 이미 처리된 주문, 시험용 메시지)는 `POST /admin/v1/dead-letters/{topic}/{partition}/{offset}/dismiss`에 사유를 실어 폐기를 표시한다. 메시지를 지우지 않고 운영자(`sub`)·사유를 `t_dead_letter_dismissal`에 남긴다. 같은 레코드를 다시 요청하면 처음 기록을 돌려준다. 읽기 검사는 하지 않는다. 재투입과 폐기는 서로를 확인하지 않아, 잘못 폐기한 메시지도 재투입할 수 있고 기록은 둘 다 남는다. 재투입도 폐기도 하지 않은 메시지 수가 gauge `event_kafka_dead_letter_unhandled{topic}`이고 알림 `KafkaDeadLetter`는 그 값이 0보다 큰 동안 울린다([관측성](observability.md)).

    앱을 쓸 수 없을 때만 Kafka CLI로 넣는다. 이때는 재투입 기록이 남지 않으므로 사유를 이슈에 남긴다. key와 함께 옮겨야 파티션이 유지된다.
    ```
    kafka-console-consumer.sh --bootstrap-server 주소 --topic order.paid.DLT --from-beginning --timeout-ms 5000 \
      --property print.key=true --property key.separator=$'\t' | grep 주문ID > redrive.txt
    kafka-console-producer.sh --bootstrap-server 주소 --topic order.paid \
      --property parse.key=true --property key.separator=$'\t' < redrive.txt
    ```
  - **경합 재시도는 `REQUESTED` 시도로 provider를 다시 부른다.** 승인 뒤 결과 저장이 잠금 대기 초과 같은 경합으로 실패하면 같은 시도에 승인을 다시 요청하게 된다. 지금은 `FakePaymentGateway`라 해가 없고, 실제 provider를 붙이는 PR은 `paymentId`를 provider 멱등 키로 넘겨야 한다.
  - **provider 호출의 deadline은 3초다.** 넘으면 승인 요청은 결과 불명(`UNKNOWN`)이고 결과 불명 확정 작업이 조회로 수렴시킨다. 지금은 `FakePaymentGateway`가 `resilientpos.payment.fake-gateway.deadline`으로 흉내 내고, 실제 PG adapter에서는 HTTP client timeout이 이 자리다(외부 연동 전략 §4.2 출발값).
    승인 consumer는 consumer 스레드에서 provider를 동기로 부르므로 처리량이 파티션 수 ÷ provider 지연에 묶인다(지연 1초면 인스턴스 하나가 초당 3건, [용량 기준](capacity.md)). 느린 provider는 메시지당 최대 deadline만큼 그 파티션을 막는다.
    비동기 반환 listener로 풀지 않는 이유는 실패한 레코드의 offset이 재시도·DLT보다 먼저 커밋되어 재시작 때 시도가 `REQUESTED`에 남을 수 있기 때문이다(spring-kafka 4.1.1). 오래 `REQUESTED`에 머문 시도를 다시 집어드는 회수 경로가 생기면 다시 본다([k6-capacity-measurement](../spec/2026-10-21-k6-capacity-measurement.md)).
  - **배포 조건(리스너를 consumer로 바꾸는 배포).** 옛 리스너 이름으로 남은 미완료 기록은 끝낼 주체가 없다. 배포 전에 `completion_date is null`이고 `listener_id`에 네 리스너 클래스 이름이 든 행이 0건이어야 한다. 조건 SQL은 [kafka-event-redelivery](../spec/2026-09-26-kafka-event-redelivery.md)에 있다.
  - **Kafka 관련 작업은 공식 문서로 대조한다.** [Spring Modulith 이벤트](https://docs.spring.io/spring-modulith/reference/events.html), [Spring Kafka 오류 처리](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html), Apache Kafka 설정 문서를 보고, 문서가 기본값을 설명하지 않거나 페이지를 읽지 못하면 클라이언트가 기동 때 찍는 `ProducerConfig values`·`ConsumerConfig values` 로그로 실제 값을 확인한다. 2026-09-27 점검 결과와 남은 결정(전송 직렬화, 운영 복제 수, 리밸런스 프로토콜)은 [kafka-event-redelivery](../spec/2026-09-26-kafka-event-redelivery.md)에 있다. `DefaultErrorHandler`는 `RuntimeException`만 다루므로 consumer 본문에서 `Error`를 던지지 않는다.
  - **브로커로 보내지 못한 기록은 주기 작업이 다시 보낸다**(`platform.EventPublicationResubmitter`, [event-publication-resubmit](../spec/2026-09-29-event-publication-resubmit.md), [modulith-2-1-2-resubmit](../spec/2026-10-12-modulith-2-1-2-resubmit.md)). 1분마다 세 단계를 돈다.
    1. 끊긴 기록을 `FAILED`로 바꾼다. `PUBLISHED`·`PROCESSING`·`RESUBMITTED`인 채 마지막 시도(재전송 시각, 없으면 발행 시각)부터 5분(`stale-after`)이 지난 미완료 기록이 대상이고, 조건을 건 UPDATE 한 문장이다. 쿼리 상한 10초를 건다. Modulith staleness 모니터는 규모 때문에 쓰지 않는다. 모니터도 pod마다 돌지만 상태마다 그 상태의 행을 직렬화된 이벤트까지 모두 읽어 메모리에서 시각으로 거르고 한 건씩 UPDATE한다. 브로커 장애 중에는 판정 기간 동안 들어온 전송 대기 행이 모두 읽힌다.
    2. `FAILED` 기록을 오래된 것부터 최대 500건 다시 보낸다. 모든 pod에서 돌고 `Lock.executeWithLockNoTx`로 줄 세운다. 트랜잭션을 열지 않아 재전송 표시(완료되지 않았고 `status != RESUBMITTED`인 행만 바꾸는 조건부 UPDATE)가 한 건씩 바로 커밋되고, 다음 pod는 표시된 행을 건너뛴다. 완료된 행은 표시되지 않는다. 다만 표시 직후 Modulith가 리스너 호출 전에 그 행을 `PROCESSING`으로 바꾸고 표시는 `RESUBMITTED`만 거르므로, 락이 빠지면(fail-open, TTL 초과) 같은 `FAILED` 행을 먼저 읽어 둔 pod가 처리 중인 행을 다시 표시해 보낼 수 있다. 락은 정합성 수단이 아니라 이 중복 전송을 줄이는 수단이다. 이 중복과, 전송 뒤 완료 표시 전에 프로세스가 죽거나 전송이 5분을 넘겨 끊긴 기록이 된 행의 재전송은 멱등 consumer가 견딘다. 500건을 넘는 실패는 다음 주기에 이어서 나간다.
    3. 완료 뒤 7일(`retention`)이 지난 기록을 지운다. 멱등 DELETE라 락 밖에서 따로 커밋한다.
    - 앞 단계가 던지면 뒤 단계는 그 주기에 건너뛰고 다음 주기에 다시 한다. 스케줄러가 로그를 남긴다.
    - 재전송 횟수에 상한은 없다. Modulith가 읽은 **뒤에** 거르므로 상한에 걸린 행이 읽기 자리를 차지해 새 실패까지 막는다.
    - **영영 나가지 못하는 기록.** 원인은 둘이고 증상이 다르다.
      - 리스너가 사라진 기록(배포 조건 위반)은 Modulith가 행마다 ERROR 로그(`Listener … not found!`)를 남기고 곧바로 `FAILED`로 돌린 뒤 다음 행으로 넘어간다. 매 주기 다시 시도되고, 500건을 넘게 쌓이면 가장 오래된 행이라 읽기를 모두 차지해 새 실패가 나가지 못한다.
      - 이벤트 타입을 역직렬화할 수 없는 기록은 그 재전송 실행 전체를 끊는다. 재전송 루프의 catch에서 다시 역직렬화하다 예외가 새기 때문이다(spring-modulith#1904). 그 주기의 정리(3단계)도 건너뛰고, 로그는 스케줄러의 ERROR `Unexpected error occurred in scheduled task`와 역직렬화 예외다. 그 행은 `RESUBMITTED`로 남아 다음 주기에는 건너뛰어진다. 1단계가 5분 뒤 `FAILED`로 되돌릴 때마다 실행이 한 번씩 끊기고, 그 실행에서 뒤에 올 행은 다음 주기로 밀린다. 6건 안팎(5분 ÷ 1분 주기)만 쌓여도 거의 모든 실행이 첫 행에서 끊긴다.

      찾는 SQL은 아래와 같다. 역직렬화할 수 없는 기록은 대부분 `RESUBMITTED`로 있으므로 함께 본다. 정상 재전송 중인 행과는 `completion_attempts`로 가른다. 원인(리스너·타입)을 되살려 보내거나, 버리기로 결정한 기록만 `completion_date`와 `status = 'COMPLETED'`를 채운다.
      ```sql
      select listener_id, event_type, count(*), max(completion_attempts) from event_publication
      where completion_date is null and (status in ('FAILED', 'RESUBMITTED') or status is null)
      group by 1, 2 order by 4 desc;
      ```
    - 재전송은 Modulith API(JPA)로 한다. externalizer 리스너를 다시 부르는 일이라 Modulith 밖에서 할 수 없다. 읽어 온 엔티티는 저장소 호출마다 트랜잭션이 끝나 분리되고, Modulith에 변경 메서드가 없어 flush가 쓰지 않는다(테스트로 고정). 끊긴 기록 표시는 `JdbcTemplate` 한 문장이다.
    - **정리를 JDBC로 옮기는 시점.** 둘 중 하나가 생기면 정리를 `JdbcTemplate`으로 나눠 지운다(`delete ... where id in (select ... limit N)` 반복).
      1. 완료 행이 쌓여 한 번의 DELETE가 쿼리 상한(10초)이나 트랜잭션 상한(30초)을 넘는다.
      2. 우리 업무 테이블에 대량 변경 배치가 생긴다. 이때는 처음부터 JDBC로 쓰고 영속성 컨텍스트를 거치지 않는다.
    - `republish-outstanding-events-on-restart`는 끈 채로 둔다.

  - 승인 시도만 다룬다. 취소 시도는 고르지 않고 `resolveUnknown`에 직접 넘겨도 조회하지 않는다. provider가 아직 처리 중이라고 답하면 `Unknown`이다(어댑터 계약). 처리 중을 거절로 접으면 재결제가 이중 청구가 된다.
  - Spring 공용 스케줄러를 쓰고 `spring.task.scheduling.pool.size`를 2로 두었다. 기본값(스레드 하나)이면 이 작업이 provider 조회로 길어질 때 발행 기록 재전송과 Moments가 멈춘다.
  - `resolveUnknown`은 `authorize`와 같은 모양이다. provider 조회는 트랜잭션 밖이고, 확정은 행을 잠근 뒤 `UNKNOWN`을 다시 확인하고 적용한다. 승인이면 `PaymentApproved`가 나가 기존 consumer가 주문을 `PAID`로 넘기고, 거절이면 그 시도가 재결제 대상이 된다. 조회로도 불명이면 조회 횟수만 하나 올린다(가짜 성공 금지). 승인인데 금액이 시도와 다르면 확정하지 않는다.
  - 락은 provider 중복 조회를 줄이는 완화 수단이다. 배치가 락 대기 한도(1.5초)를 넘기면 늦게 온 pod는 fail-open으로 함께 돈다. fail-open이나 TTL 초과로 pod가 겹쳐도 조회는 읽기이고, 같은 확정이 두 번 적용되는 일은 잠근 뒤 재확인이 막는다. 이 블록은 `Lock` 안에서 행 잠금을 기다리는 예외다. 그 행을 잠그는 다른 경로(`authorize`의 적용, `retryAuthorization`)는 이 키를 잡지 않아 순환이 없다.
  - 지난 주기에 읽은 마지막 `id` 다음부터 읽고(pod 메모리의 keyset 커서), 100건보다 적게 읽히면 다음 주기는 처음부터 읽는다. 그래서 영영 불명인 건이 100건을 넘어도 새 건은 늦어도 `ceil(불명 건수 / 100)` 주기 안에 조회된다. 커서는 pod마다 따로이고 재기동하면 처음부터다. 조회가 겹치거나 늦어질 뿐 정합성에는 닿지 않는다.
  - 한 건이 던지면 ERROR 로그를 남기고 다음 건으로 간다.
  - 조회 횟수가 상한(`resilientpos.payment.unknown-query-limit`, 60)에 닿거나 조회가 다른 금액의 승인을 알려 주면 그 시도를 reconciliation case로 넘긴다. 넘김과 `PaymentReconciliationRequested` 발행이 같은 커밋이다. 넘긴 시도는 대상 조회가 고르지 않는다(§2, [payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)).
  - 주기마다 결과 불명 승인 시도 수와 그중 넘긴 시도 수를 세어 gauge `payment.attempt.unknown`과 `payment.attempt.reconciliation.pending`에 두고, 넘기지 않은 시도 가운데 가장 오래된 것의 경과 시간과 넘긴 시도 가운데 가장 이른 넘긴 시각부터의 경과 시간을 `payment.attempt.resolution.oldest`·`payment.attempt.reconciliation.pending.oldest`에 둔다(observability). 알림은 경과 시간으로 건다.
- `event_publication`의 인덱스는 V004가 만든 두 개(`serialized_event` hash, `completion_date`)와 V009의 `status`다. `status` 인덱스는 재전송 작업과 Modulith가 매분 status로 거르는 조회(`countByStatus`, `findFailedPublications`)를 위한 것이고, Modulith가 파라미터로 거는 조회의 generic plan에서도 쓰이도록 partial이 아닌 전체 인덱스로 두었다(실측은 [event-publication-resubmit](../spec/2026-09-29-event-publication-resubmit.md) 스키마 변경 검토).
- `event_publication`은 테이블·컬럼 이름을 Modulith의 JPA 엔티티가 정한다. `t_` 접두어 규칙과 `BaseEntity` 공통 컬럼의 예외다. 엔티티가 라이브러리 안에 있어서 바꿀 수 없다. 스키마는 같은 버전 JDBC 모듈의 공식 PostgreSQL 스키마를 기준으로 Flyway 마이그레이션에 직접 쓴다. JPA가 `validate`라서 Modulith를 올릴 때 엔티티의 컬럼이 바뀌었는지 확인하고 마이그레이션을 함께 넣어야 한다([event-publication-registry](../spec/2026-09-21-event-publication-registry.md)).
- **Modulith 버전을 올리는 PR의 절차.** 라이브러리는 이 테이블을 만들어 주지 않는다. JPA 모듈에는 스키마 SQL이 없고 스키마의 소유자는 Flyway다.
  1. 새 버전 `spring-modulith-events-jdbc` jar의 `schemas/vN/schema-postgresql.sql`을 쓰던 버전의 것과 diff한다. Modulith가 자기 스키마를 버전으로 관리해서 두 버전이 jar에 함께 들어 있다. 실제 v1 → v2 변경은 nullable 컬럼 셋(`status`, `completion_attempts`, `last_resubmission_date`) 추가였다.
  2. 바뀐 만큼 마이그레이션을 추가한다. 추가만 하는 변경이면 이전 버전 인스턴스는 모르는 컬럼이 늘어난 것뿐이라 함께 떠 있어도 된다.
  3. 추가가 아닌 변경(이름·타입)이면 라이브러리 엔티티를 우리가 못 바꿔서 이중 쓰기를 할 수 없다. 남아 있는 미완료 기록을 어떻게 보존할지 함께 정한다.
  4. `EventPublication.Status`의 값도 diff한다. `status`가 문자열 컬럼이라 새 값은 스키마 diff에 나오지 않는데, 발행 기록 metric은 아는 미완료 상태(`PUBLISHED`·`PROCESSING`·`RESUBMITTED`)만 `stale`로 세므로 새 미완료 상태는 조용히 빠진다. 새 미완료 상태가 있으면 `EventPublicationMetrics`의 조회 SQL 상태 목록에 더한다.
  5. 재전송 작업(`EventPublicationResubmitter`)이 기대는 동작을 새 버전 소스와 대조한다. 재전송 경로(`FailedEventPublications.resubmit` → registry → 저장소)에 바깥 트랜잭션이 없는지, `markResubmitted`가 완료되지 않았고 `status != RESUBMITTED`인 행만 바꾸는 조건부 UPDATE인지, 실패 표시도 완료되지 않은 행만 바꾸는지(빠지면 완료된 행이 다시 나간다), 완료 표시가 상태와 완료 시각을 함께 쓰는지(`MARK_COMPLETED_BY_ID`·`MARK_COMPLETED_BY_EVENT_AND_LISTENER_ID`), 재전송 루프가 역직렬화 실패에 실행 전체를 끊는지(#1904), staleness 모니터가 여전히 상태별로 전체 행을 읽는지(바뀌었으면 모니터로 돌아갈지 다시 본다), 끊긴 기록 표시가 쓰는 컬럼(`status`, `completion_date`, `last_resubmission_date`, `publication_date`)과 상태 이름이 그대로인지 본다.
- **컬럼이 늘거나 타입·테이블 이름이 바뀌면 기동이 막히고 CI가 먼저 잡는다.** `Schema validation: missing column [이름] in table [event_publication]`처럼 대상이 메시지에 나온다. 통합 테스트가 컨텍스트를 띄우므로 버전을 올리는 PR에서 실패한다(2026-09-21에 `V004`를 v1 스키마로 되돌려 확인했다). **반대로 라이브러리가 컬럼을 없애면 조용히 통과한다.** `validate`는 매핑된 컬럼만 검사해서(4.7절 질문 8) 쓰이지 않는 컬럼이 남는다. 이건 사람이 정리한다.
- **이벤트 클래스의 모양이 저장 형식이다.** 발행 기록은 이벤트를 JSON으로, `event_type`에는 클래스의 정규 이름을 저장한다. Kafka 메시지와 DLT에도 같은 JSON이 남는다. 이벤트 클래스를 옮기거나 이름을 바꾸면 미완료 기록을 복원할 수 없으므로 그런 기록이 0건일 때만 한다. 필드는 기본값이 있거나 nullable인 것만 더하고, 지우거나 이름을 바꾸지 않는다. 이름을 바꾸면 옛 메시지가 실패하지 않고 옛 값을 잃는다. 빠진 새 필드의 값은 "모름"이어야 한다. 그 밖의 변경은 [이벤트 계약](event-contract.md) 4절 표를 따른다. 변경 종류별 규칙, 버전 가드, golden fixture와 계약 테스트는 [이벤트 계약](event-contract.md)이 정본이다.
- **리스너의 이름도 저장 형식이다.** `listener_id`에는 리스너의 클래스 정규 이름·메서드·이벤트 타입이 저장되고(`패키지.클래스.메서드(이벤트타입)`) Modulith는 `serialized_event`와 `listener_id`가 같은 행을 찾아 완료를 표시한다. 미완료 기록이 남은 동안 리스너의 패키지·클래스·메서드 이름을 바꾸면 그 기록을 끝낼 주체가 없어진다. 지금 기록되는 리스너는 Modulith externalizer 하나다(위 Kafka 문단).
- **끝나지 않은 발행 기록은 gauge `event.publication.incomplete{status, module, listener}`로 센다**(Prometheus 이름 `event_publication_incomplete`). `status`가 `failed`면 리스너가 던진 기록(`status`가 비어 있는 미완료 행도 Modulith처럼 실패로 본다)이고, `stale`이면 `PUBLISHED`·`PROCESSING`·`RESUBMITTED`인 채 발행 뒤(재전송된 기록은 마지막 재전송 뒤) 기본 5분(`resilientpos.event-publication.stale-after`로 바꾸며 양수만 받는다)이 지난 기록이다. `module`은 `listener_id`의 패키지에서 `com.resilientpos.` 다음 세그먼트(그 접두어가 아니거나 기본 패키지 바로 아래 클래스면 `unknown`), `listener`는 리스너 클래스의 단순 이름이라 리스너의 모듈·이름을 바꾸면 알림 규칙도 함께 바꾼다. 모듈 사이 이벤트가 Kafka로 가면서 지금 나오는 조합은 `module="unknown"`, `listener="EventExternalizerModuleListener"` 하나이고 브로커 전송 실패를 센다. 이벤트별 소비 실패는 DLT counter가 센다. 모든 인스턴스가 같은 DB를 세므로 개수는 `sum`이 아니라 `max`로 모은다. 전용 스레드에서 1분마다 갱신하고(공용 스케줄러를 붙잡지 않는다) 상태는 바꾸지 않는다. 끊긴 기록은 5분이 지나면 재전송 작업이 `FAILED`로 옮기므로 `stale`은 잠깐만 보인다. `failed`는 재전송 작업이 1분마다 다시 보내므로 브로커가 돌아오면 스스로 줄어든다. 행을 손으로 완료 처리하거나 지우지 않는다 — 곧 다시 나갈 메시지를 버리게 된다. 줄지 않으면 브로커 장애가 이어지거나 영영 나가지 못하는 기록이 있다는 뜻이고, 가르는 SQL과 조치는 위 재전송 항목에 있다. 조회가 실패한 인스턴스는 개수를 내리고 `event.publication.incomplete.refreshed`(Prometheus 이름 `event_publication_incomplete_refreshed_seconds`, 마지막 갱신 시각)를 멈춘다. 신선도는 인스턴스별로(또는 `min`으로) 보고, 기동 직후 첫 갱신 전에는 0이므로 알림에 `for:`를 둔다. 모든 인스턴스가 막히면 `failed` 알림이 resolved로 바뀌므로 규칙 쪽에서 `keep_firing_for`로 신선도 알림이 울릴 때까지 붙잡을 수 있다([failed-publication-metric](../spec/2026-09-25-failed-publication-metric.md)).
- **외부를 부르는 리스너는 트랜잭션이 아니어야 한다.** `@ApplicationModuleListener`는 `@Transactional(REQUIRES_NEW)`를 함께 달아 리스너를 트랜잭션으로 만들고, Facade가 여는 트랜잭션은 그 안에 합류한다. 그러면 §4.6·§6의 "provider 호출은 트랜잭션 밖"을 지킬 자리가 없다. 그런 리스너는 `@ApplicationModuleListener(propagation = NOT_SUPPORTED)`로 트랜잭션을 끄고, 트랜잭션은 Facade가 나눠 연다. 지금 모듈 사이 consumer는 `@KafkaListener`라 트랜잭션이 없고 같은 규칙(트랜잭션은 Facade가 연다)을 따른다. 속성이 메타 애너테이션의 `@Transactional`로 그대로 이어진다. 발행 기록의 추적은 그대로다 — 기록은 발행하는 쪽 트랜잭션에서 쓰이고 완료 표시는 Modulith가 리스너 반환 뒤 자기 트랜잭션에서 한다(`payment` PR에서 기본값과 같은 테스트로 관측해 확인했다).
- **이벤트는 Facade의 트랜잭션 안에서만 발행한다.** 발행 기록이 업무 상태와 같은 커밋에 들어가려면 발행이 커밋 전, 트랜잭션 안이어야 한다. 리스너는 커밋 뒤에 실행된다. 트랜잭션 밖에서 발행하면 발행 기록은 남는데 리스너가 실행되지 않아서 그 기록이 미완료로 남는다(2026-09-21 임시 테스트로 확인).
- **이벤트는 모듈 publisher가 구체 타입으로 발행한다.** Facade는 `ApplicationEventPublisher`를 직접 받지 않고 자기 모듈의 `OrderEventPublisher`·`PaymentEventPublisher`를 쓴다. publisher는 이벤트 타입마다 구체 타입 파라미터를 받는 `publish`를 따로 두고, Facade는 `transition.events.forEach(eventPublisher::publish)`로 부른다. IntelliJ Spring 플러그인이 `publishEvent` 인자의 정적 타입으로 리스너와 발행 지점을 잇기 때문이다. `publishEvent` 자체를 메서드 참조로 넘기거나(`forEach(publisher::publishEvent)`) `DomainEvent` 타입으로 넘기면 리스너마다 발행 지점을 찾지 못한다. 그래서 전이는 `Transition`의 이벤트 타입을 하나로 좁힌다. 결말에 따라 다른 사실을 내는 전이는 결말마다 메서드를 나눈다(`PaymentAttempt.approve`·`decline`·`markUnknown`, 0원 승인은 `approveIfFree`)([checkout-lock-static-calls](../spec/2026-09-28-checkout-lock-static-calls.md)).
- **트랜잭션 경계는 `Tx`로 선언한다.** 쓰기는 `Tx.masterTx { }`(`REQUIRED`), 읽기 전용은 `Tx.readOnlyTx { }` 또는 메서드의 `@ReadOnlyTransactional`(`readOnly = true`, `SUPPORTS`)이다. `Tx`는 `platform`의 전역 object이고 프록시를 거친 `TxRunner`를 부르므로 같은 클래스 안에서도 블록마다 트랜잭션이 열린다. 한 Facade 메서드 안에서 트랜잭션을 나눌 때 보조 빈을 만들지 않고 블록을 나눈다. `Tx.newTx { }`(`REQUIRES_NEW`)는 `Lock`이 락을 풀기 전에 커밋하려고 쓰며 Facade가 직접 부르지 않는다. main 코드는 `TransactionOperations`·`TransactionTemplate`·`PlatformTransactionManager` 같은 내장 트랜잭션 타입을 주입받지 않는다. `@Transactional`을 직접 쓰는 곳은 `TxRunner`, 트랜잭션 없이 부른 경우의 안전망인 persistence adapter 저장 메서드(`OrderPersistenceAdapter.save`), 아래 `NOT_SUPPORTED`뿐이다. 메서드에만 붙이고 클래스에는 붙이지 않으며(나중에 더한 조회 메서드까지 트랜잭션이 걸린다), `@Transactional(readOnly = true)`는 직접 쓰지 않는다. `TransactionDeclarationTest`가 막는 것은 이 두 가지다. 러너는 컨텍스트가 뜰 때 `PlatformConfiguration`이 넣는다. 넣기 전에 부르면 `UninitializedPropertyAccessException`(`lateinit property runner has not been initialized`)으로 실패한다. 전역이라 한 JVM에서는 마지막 초기화가 이기므로, 테스트는 `TxRebindingTestExecutionListener`가 Spring 테스트마다 그 컨텍스트의 러너로 다시 묶고 컨텍스트 없는 Facade 단위 테스트는 프록시가 아닌 `TxRunner()`를 넣는다. 테스트는 바깥 트랜잭션을 커밋·롤백하는 시나리오를 만들려고 `TransactionOperations`를 쓴다.
- **쓰기 경로는 트랜잭션 안에서 돈다.** 단건 수정이어도 빼지 않는다. 이벤트 발행 기록은 트랜잭션이 없으면 `@TransactionalEventListener`가 건너뛰고(위 문단), 주문 저장처럼 여러 문장이 한 커밋이어야 한다.
- **`SUPPORTS` 읽기는 호출자 트랜잭션이 없으면 트랜잭션 없이 돈다.** 쿼리마다 따로 커밋되고, 세션 read-only(더티 체킹 스냅샷 생략)와 커넥션 read-only는 걸리지 않는다. 읽기 전용 표시(`TransactionSynchronizationManager.isCurrentTransactionReadOnly()`)와 Hibernate flush 생략(`FlushMode.MANUAL`)은 걸린다(실측). 호출자 트랜잭션에 합류하면 읽기 전용 설정은 무시되고 호출자의 것을 따른다. 레플리카 라우팅은 아직 없고, 도입할 때 라우팅이 보는 값이 이 경우에 무엇인지 확인한다. 한 시점이 필요한 조회는 한 쿼리로 읽거나 루트를 잠그고 읽는다(`findByIdForUpdate`). PostgreSQL 기본 격리(READ COMMITTED)에서는 `masterTx` 안에서도 문장마다 스냅샷을 새로 잡으므로 트랜잭션만으로 한 시점이 되지 않는다. aggregate의 `findById`(`Order`, `PaymentAttempt`)를 `@ReadOnlyTransactional`로 선언한다. 트랜잭션이 없어도 루트와 자식을 읽는 쿼리가 한 EntityManager를 쓴다.
- **트랜잭션 밖이어야 하는 메서드는 `NOT_SUPPORTED`로 호출자 트랜잭션을 멈춘다.** 쓰는 조건은 "외부 호출을 트랜잭션 밖에서 하고 결과는 따로 커밋한다" 하나다. 읽기 전용 목적이면 `SUPPORTS`다. `NEVER`·`MANDATORY`는 쓰지 않고, 그 밖의 전파는 기본값(`REQUIRED`)이다. 예외는 `Lock` 안의 `REQUIRES_NEW` 하나다. `PaymentManagement.authorize`·`retryAuthorization`이 이렇게 provider 호출을 트랜잭션 밖에 두고, 적용은 `Tx.masterTx`가 새 트랜잭션으로 열어 반환 전에 커밋한다. 호출자 트랜잭션이 커밋하지 않은 행은 보이지 않고, 바깥이 롤백돼도 적용 결과는 남는다. 그래서 §4.6 sync intake처럼 한 커밋으로 묶어야 하는 흐름 안에서 부르지 않는다. `NOT_SUPPORTED` 구간에서 `SUPPORTS` 조회를 그냥 부르면 트랜잭션이 열리지 않아 EntityManager가 구간이 끝날 때까지 스레드에 묶인다. 외부 호출 전 조회는 `masterTx`로 감싸 끝날 때 놓게 한다(`authorize`의 첫 `findById`).
- **분산 락은 `Lock` 블록으로 건다.** `Lock.executeWithLock(key) { }`가 Redis에서 키를 잠그고, 블록을 새 트랜잭션(`Tx.newTx`, `REQUIRES_NEW`)에서 돌려 커밋한 뒤 `finally`에서 푼다. 블록이 곧 락 범위다. 바깥 트랜잭션에 합류하면 바깥 커밋 전에 락이 풀려 뒤 요청이 커밋되지 않은 상태를 읽으므로 따로 커밋한다. 그래서 바깥이 롤백돼도 블록의 커밋은 남고, 바깥이 있으면 커넥션을 둘 쓴다. §4.6 sync intake처럼 한 커밋으로 묶어야 하는 흐름 안에서 부르지 않고 그 흐름은 락 없는 합류 경로를 부른다. 바깥 트랜잭션을 거절하는 검사는 두지 않는다 — KDoc 계약이다([sync-intake](../spec/2026-09-30-sync-intake.md) 결정 2). 전파 속성 `MANDATORY`·`NEVER`로 검사하는 안은 같은 spec의 제외 절에 스케치로 남아 있고 사용자가 검토한다. 운영 코드가 Spring 트랜잭션에서 쓰는 것은 `@Transactional` 애너테이션뿐이고 `org.springframework.transaction.support`는 부르지 않는다. 락은 완화 수단이라 Redis 오류나 대기 1.5초 초과([용량 기준](capacity.md))면 잠금 없이 블록을 실행하고(fail-open) DB 제약이 막는다. 키는 부르는 모듈 Facade의 companion이 접두어 상수와 타입 있는 함수로 만든다(`PaymentManagement.checkoutLockKey`, `OrderCommandFacade.createLockKey`). 잠글 행이 이미 있으면 행 잠금(`findByIdForUpdate`)을, 행이 아직 없거나 DB 밖의 일을 감싸야 하면 `Lock`을 쓰고, 한 경로에서 둘을 함께 기다리지 않는다. 락을 쥔 쪽이 행을, 행을 쥔 쪽이 락을 기다리면 둘 다 대기 한도까지 멈춘다. 예외는 결과 불명 확정 작업 하나이고 근거는 아래 항목에 있다. AOP 애너테이션과 확장 함수로 두지 않은 이유는 [shared-distributed-lock](../spec/2026-09-28-shared-distributed-lock.md)의 제외 절이다. 트랜잭션 없이 줄만 세우는 `Lock.executeWithLockNoTx`는 블록 안의 쓰기가 각자 커밋되는 주기 작업(발행 기록 재전송, 결과 불명 확정)용이고 Facade는 쓰지 않는다. 바깥 트랜잭션 안에서 부르지 않는다 — 합류하면 바깥이 커밋하기 전에 락이 풀린다. 검사는 두지 않고 KDoc 계약이다.
- **조회는 간단하면 `*JpaRepository`, 그 밖에는 Kotlin JDSL로 쓴다.** 조건 몇 개와 정렬로 끝나는 조회는 엔티티마다 둔 Spring Data repository의 파생 쿼리로 해도 된다. 조인·동적 조건·projection 같은 조회와 비관적 잠금 조회는 persistence adapter가 `platform.JdslQueryExecutor`(`findAll`·`findFirst`·`findFirstForUpdate`)로 JPQL을 만들어 실행한다. 지금 있는 조회는 모두 JDSL이다. 쓰지 않는 repository도 지우지 않는다. `@Query` 문자열은 쓰지 않는다. Spring Data의 기본 CRUD 조회(`findById` 등)는 스스로 `REQUIRED` 읽기 전용 트랜잭션을 열고 파생 쿼리는 트랜잭션을 선언하지 않으므로, `NOT_SUPPORTED` 구간 앞의 조회에 쓸 때는 자원 결속을 확인한다. 결제 시도·fulfillment repository는 `JpaRepository`가 아니라 `Repository`를 상속한다. `deleteAllInBatch` 같은 대량 삭제가 soft delete와 만나 모든 행을 조용히 조회에서 지우기 때문이다. 비관적 잠금은 `findFirstForUpdate`다(`PESSIMISTIC_WRITE`, PostgreSQL에서 `for no key update`, 대기 3초). 실행기는 트랜잭션을 선언하지 않고 호출자를 따른다. `@Repository`라 JPA 예외가 Spring 예외로 번역된다. 번역이 없으면 잠금 대기 초과가 `jakarta.persistence.PessimisticLockException`으로 올라와 위 Kafka 재시도 허용 목록(Spring 예외 타입)에 걸리지 않고 곧바로 DLT로 간다. Spring Data 지원 모듈의 `KotlinJdslJpqlExecutor`는 쓰지 않는다. 구현이 `@Transactional(readOnly = true)`(`REQUIRED`)이고 `update`·`delete` 대량 변경을 함께 열기 때문이다. 쓰기 메서드 안에서 관리 엔티티를 찾는 PK 조회는 `EntityManager.find`다. 같은 트랜잭션에서 이미 읽은 엔티티면 SELECT가 나가지 않는다.
- 금액은 `NUMERIC(19,4)` + 통화 코드 컬럼, 식별자는 PostgreSQL native `uuid`다([개발 가이드 §3.1·§3.2](../references/03_Development_Guide.md)). 테이블 이름은 `t_` + 단수 명사(`t_order`, `t_payment_attempt`)다.

### 4.4 공개 타입은 모듈 루트에 둔다
- Facade, 커맨드 이름공간(`OrderCommand`), `*Query`/`*Criteria`/`*View`, 도메인 이벤트, ID 값 타입은 모듈 기본 패키지(`com.resilientpos.order`)에 두고, 그 밖은 전부 `internal/` 아래다.
- **예외는 모듈을 건너가는 이벤트다.** 소유 모듈에 두면 보내는 쪽과 받는 쪽이 서로를 의존해 순환이 된다. 그런 이벤트와 그 payload는 `com.resilientpos.contract`가 소유하고, 양쪽이 그 모듈을 함께 의존한다. 소비자가 없는 이벤트는 소유 모듈에 남는다 — 경계를 넘는 것만 옮긴다([contract-module-for-cross-module-events](../spec/2026-09-22-contract-module-for-cross-module-events.md)). Facade는 인터페이스를 따로 두지 않는 구체 클래스(`class OrderCommandFacade`)다. 구현이 둘이 될 때 인터페이스를 뽑는다. [ADR-002](../references/01_ResilientPOS_PRD_Backend_Requirements.md)를 따르고 [청사진 §6.1](../references/05_Domain_Development_Blueprint.md)의 `api/` 하위 패키지는 쓰지 않는다.
- 근거: Spring Modulith는 모듈 기본 패키지만 공개로 보므로 애너테이션 없이 지금의 `ModuleStructureTest`가 그대로 경계를 지킨다. `api/`를 쓰려면 모듈마다 `@NamedInterface`가 필요하다.
- 다시 볼 조건: 한 모듈의 루트 파일이 20개를 넘거나 공개 surface를 `api`/`events`처럼 나눠 의존을 허용해야 할 때 `@NamedInterface`로 옮긴다. 그때도 패키지 이름만 바뀌는 파일 이동이다.

### 4.5 `Transition`과 `DomainEvent`는 `foundation`에 둔다
- `data class Transition<A, E : DomainEvent>(val aggregate: A, val events: List<E>)`와 `interface DomainEvent { val eventId: UUID; val occurredAt: Instant }`를 `Money` 옆에 둔다. 둘 다 프레임워크 의존이 없어 `DependencyDirectionTest`의 `foundation` 규칙 안에 있다.
- `eventId`는 소비자 멱등성 기록 `(consumer, eventId)`([개발 가이드 §4.2](../references/03_Development_Guide.md))의 키다. 모듈 안에만 머무는 이벤트는 `sealed interface OrderEvent : DomainEvent`처럼 닫아 `when` 누락을 컴파일러가 잡게 하고, 커맨드처럼 **그 안에 중첩한다**(`OrderEvent.Created`, `PaymentEvent.AttemptCreated`). 이 문서의 사실 이름 `OrderCreated`는 코드에서 `OrderEvent.Created`다. 중첩 클래스의 JVM 이름은 `$`로 이어져 `event_type`에 `com.resilientpos.order.OrderEvent$Created`로 저장된다.
- **§4.4의 `contract` 이벤트는 닫힌 계층에 들어가지 않는다.** 선택이 아니라 언어 제약이다. Kotlin은 sealed 타입의 구현을 같은 패키지로 제한해서(`A class can only extend a sealed class or interface declared in the same package.` — 실제로 컴파일해 확인했다) 다른 패키지로 옮긴 이벤트는 `OrderEvent`·`PaymentEvent`를 구현할 수 없다. `DomainEvent`를 직접 구현한다. 한 전이는 한 종류의 사실만 내므로(§4.3) `Transition`의 이벤트 타입 인자는 그 구체 타입이고 `DomainEvent`까지 넓히지 않는다. 한 aggregate가 모듈 이벤트와 `contract` 이벤트를 함께 내도 전이마다 나뉜다.
- 이것은 §2의 "업무 개념을 두지 않는다"에 어긋나지 않는다. 주문·결제를 모르는 모델링 원시 타입이며, 모듈마다 복제하면 이벤트 공통 필드를 강제할 수 없다. 처음 필요한 도메인 PR에서 추가한다.

### 4.6 컨텍스트 사이 동기 쓰기는 sync intake와 대조 해소 둘만, 한 트랜잭션으로
원문이 서로 다르다. [청사진 §1](../references/05_Domain_Development_Blueprint.md)은 "Facade끼리 호출하지 않는다"고 조건 없이 금지하고, [시스템 설계 §1.3](../references/02_System_Design.md)은 "단일 즉시 결과와 강한 일관성이 필요한 경우에만 다른 모듈의 public facade를 동기 호출한다"고 조건부로 허용하며, 청사진 자신도 §3.2에서 `sync`가 받아들인 명령을 소유 컨텍스트의 Command Facade로 넘긴다. 시스템 설계 §1.3을 따르되 허용 범위를 다음으로 좁힌다.

- **허용되는 동기 쓰기 호출은 둘이다.** `sync` → `order`의 공개 Command Facade와 `reconciliation` → `PaymentManagement.resolveFromReconciliation`이다. 그 밖의 컨텍스트 간 변경은 이벤트다. `payment`는 sync의 동기 경로에 없다(다음 항목).
- **`reconciliation` → `payment`도 같은 조건이다.** `ReconciliationManagement.resolve`가 트랜잭션을 소유하고 case 행을 매장 조건으로 잠근 뒤(대기 3초) `resolveFromReconciliation`을 부른다. 그 메서드는 `REQUIRED`로 합류해 시도 행을 잠그고(대기 3초) 결론을 적용하며 발행 기록을 남긴다. 결제 확정과 case 해소(같은 행의 해소 기록 포함)가 한 커밋이다. provider를 부르지 않으므로 트랜잭션 밖에 둘 이유가 없고, 커밋을 나누면 결제만 확정되고 case가 남는 틈이 생긴다. 잠금 순서는 case 다음 시도로 고정이다. 시도 행을 잠그는 다른 경로(조회 확정, 승인 적용, 재결제)는 case를 잠그지 않아 순환이 없다. 트랜잭션 안에서만 부른다는 것은 KDoc 계약이다. 반대 방향(넘김)은 이벤트다([payment-reconciliation-case](../spec/2026-10-20-payment-reconciliation-case.md)). 같은 모듈 안에서 Facade가 Facade를 부르지 않는다는 청사진 §1은 그대로 적용한다.
- 상태를 바꾸지 않는 동기 호출이 하나 더 있다. `terminal`의 점주용 Controller(`TerminalOwnerController`)가 단말 Facade를 부르기 전에 `StoreManagement.requireOwned`로 매장 소유를 확인한다. 남의 매장과 없는 매장은 같은 `404 STORE_NOT_FOUND`다([operator-authentication](../spec/2026-10-06-operator-authentication.md)).
- **항목 하나 = 로컬 트랜잭션 하나.** `sync` Command Facade가 트랜잭션을 소유하고, 호출된 `order` Facade는 같은 트랜잭션에 합류한다(`REQUIRED`). `REQUIRES_NEW`로 커밋을 나누지 않는다. `OrderCommandFacade.create`는 `Lock` 블록이라 스스로 커밋하므로 sync는 락 없는 합류 경로 `OrderCommandFacade.createInCallerTransaction`을 부른다. 트랜잭션 안에서만 부른다는 것은 KDoc 계약이고 검사 코드는 없다. sync의 줄 세우기는 단말별 `t_sync_watermark` 행 잠금이 맡고(한 경로에 기다리는 수단 하나, §4.7 질문 6), HTTP `create`와 겹치는 경합은 unique `(terminal_id, client_order_id)`가 막는다. `Lock` 블록은 바깥 트랜잭션을 검사하지 않고 `REQUIRES_NEW`로 따로 커밋한다(§4.3). `PaymentManagement.createAttempt`는 sync의 동기 경로에 없다 — 단말의 결제 요청은 `order.requestCheckout`이고 시도 생성은 이벤트가 잇는다([sync-intake](../spec/2026-09-30-sync-intake.md)). sync의 `REQUEST_CHECKOUT` 항목은 `OrderCommandFacade.requestCheckout(OrderCommand.RequestCheckoutByClientOrderId)`를 부른다. 단말은 오프라인에서 `orderId`를 모르므로 `(terminalId, clientOrderId)`로 주문 행을 바로 잠그고 읽는다. `clientOrderId`만으로는 어느 내용의 주문인지 알 수 없어 단말이 본 합계를 함께 받고, 전이한 뒤 저장하기 전에 확정 금액과 대조해 다르면 `CHECKOUT_AMOUNT_MISMATCH`로 거절한다(`Order.verifyCheckoutAmount`). 같은 키의 주문이 다른 내용으로 이미 있을 때 단말이 모르는 금액으로 결제 요청이 나가는 것을 막는다. `requestCheckout`은 `Lock` 블록이 아니라 `Tx.masterTx`라 합류 전용 메서드가 따로 없다. 그 항목 트랜잭션은 watermark 행 다음에 주문 행을 잠그고(각각 대기 3초, 순서 고정), HTTP checkout과 `markPaid`는 주문 행만 잡아 순환이 없다([sync-request-checkout](../spec/2026-09-30-sync-request-checkout.md)). 중복·gap·conflict 판정, 소유 aggregate 쓰기, 접수 기록, watermark 전진, 도메인 이벤트의 Event Publication Registry 기록이 한 커밋이다. 응답은 청사진 §3.2대로 커밋된 항목만 `APPLIED`다.
- **후속 처리는 커밋 뒤 이벤트다.** 항목이 낸 도메인 이벤트 가운데 받는 쪽이 있는 것(지금은 결제 요청의 `OrderPaymentRequested`)의 발행 기록이 같은 커밋에 들어간다. `OrderCreated`는 받는 쪽이 없어 기록되지 않고 `SyncOperationApplied`는 아직 없다. `@Externalized`로 Kafka에 보내고 받는 쪽은 Kafka consumer다(§4.3). 앱 밖 consumer도 같은 토픽을 쓴다. provider 승인 호출은 트랜잭션 밖이다. sync의 `REQUEST_CHECKOUT` 항목은 checkout 확정과 `OrderPaymentRequested` 발행 기록까지만 트랜잭션 안이고, attempt 생성은 커밋 뒤 `payment`의 consumer가 한다.
- 근거: 기획 PRD 3.2·PR-02는 항목별 수락·중복·충돌·누락 판정과 watermark를 응답으로 요구하고, 개발 가이드 §4.3은 "안전한 명령 하나를 트랜잭션으로 적용하고 항목별 결과를 반환"한다. 커밋을 나누면 크래시 창이 생기고, 순수 이벤트로 바꾸면 주문 상태에 기반한 충돌 판정을 응답에 실을 수 없다.
- 다시 볼 조건: `order`나 `payment`를 독립 배포로 분리할 때다. [시스템 설계 §6.2](../references/02_System_Design.md) 2단계대로 이 경로를 먼저 "`ACCEPTED` 응답 + 이벤트 적용"으로 바꿔 원격 경계를 시뮬레이션하고 단말 계약을 함께 바꾼다. 시스템 설계 §1.3의 `checkout` orchestration module이 필요해지면 같은 조건(한 곳, 한 트랜잭션)으로 ADR을 쓴다.

### 4.7 스키마 변경 검토
컬럼·테이블·제약·인덱스를 더하거나 빼는 PR은 spec에 `스키마 변경 검토` 절을 두고 아래 질문에 답한다. 해당 없는 질문은 이유를 적는다. 답은 구현자가 스스로 승인하지 않는다. PR을 제출하기 전에 구현자가 아닌 리뷰어가 마이그레이션 SQL, 엔티티, 그 컬럼을 읽고 쓰는 코드를 열어 spec의 답과 대조한다. 에이전트가 작업했으면 `code-reviewer`처럼 읽기 전용 도구만 가진 다른 에이전트에 맡긴다. 대조한 주체와 시점, 불일치 항목을 spec의 같은 절 끝에 `- 대조 기록:`으로 시작하는 한 줄로 남긴다. `check_pr.py`는 마이그레이션을 바꾸는 PR에 이 절과 이 줄이 있는지를 제출 전 이력 검사에서 확인한다([개발 규칙](development-workflow.md)). 원칙 자체는 [README의 데이터 정본 원칙](../../README.md#engineering-principles), [청사진 §6.2·§7.1](../references/05_Domain_Development_Blueprint.md), [개발 가이드 §2.5](../references/03_Development_Guide.md)에 있고, 이 절은 그것을 스키마를 바꾸는 시점의 질문으로 모은 것이다.

**필요성: 불필요한 컬럼을 넣지 않는다.**
1. PostgreSQL에 이미 저장된 컬럼·테이블에서 그 값을 도출하거나 직접 비교할 수 있는가.
2. 지금 있는 코드가 그 값을 실제로 읽는가, 아니면 아직 없는 명령을 대비하는 것인가.
3. 필요해지는 시점에 기존 행을 채울 수 있는가.
- 나중에 채울 수 있는 값인데 기존 데이터로 지금 판단할 수 있거나 지금 읽는 코드가 없으면 추가하지 않고, 다시 볼 조건만 spec과 코드 주석에 남긴다. 단 질문 4에 해당하는 값이면 이 판정보다 질문 4가 우선한다. 참고 문서가 그 컬럼을 예시로 들었더라도 같은 확인을 거친다.
- 중복 컬럼은 디스크를 쓰는 데서 끝나지 않는다. 같은 사실의 정본이 둘이 되어 어긋났을 때 어느 쪽이 맞는지 알 수 없고, 나중에 읽는 사람이 그 컬럼이 왜 있는지를 이력에서 찾아야 하며, 머지된 뒤에는 제거에도 마이그레이션과 배포된 데이터 처리가 필요하다.

**정합성: 필요한 컬럼을 빼지 않는다.**
4. 이 값이 불변식의 마지막 방어선인가. unique 제약, `@Version`, 멱등 키와 접수 기록, 상태, 판매 시점 snapshot이 여기에 든다. 그렇다면 PostgreSQL의 컬럼과 제약으로 두고 질문 1~3으로 빼지 않는다. Redis의 값, Kafka의 이벤트와 offset은 질문 1의 "기존 데이터"가 아니다. Redis 값은 TTL·eviction·장애로 사라질 수 있다. Kafka 이벤트는 보존 기간 안에서는 남지만 PostgreSQL 트랜잭션과 함께 commit되지 않고 다시 전달될 수 있으며 unique 같은 불변식 검사 수단이 없다. 그래서 둘 다 정본이 될 수 없다. unique 제약마다 soft delete된 행이 계속 걸려야 하는지도 적는다. `BaseEntity`의 `@SoftDelete`는 조회만 거르고 제약은 삭제된 행에도 걸린다. 걸려야 하는 값(멱등 키)이면 그 조회가 삭제된 행도 보는지 확인하고, 재사용을 허용하는 값이면 `WHERE deleted_at IS NULL` partial unique 인덱스로 둔다.
5. 정본은 하나인가. 성능이나 조회를 위해 일부러 만드는 사본(캐시, read model, consumer 쪽 테이블)은 질문 1에서 도출할 수 있다고 나와도 추가할 수 있다. 대신 사본임을 밝힌다. 같은 사실을 두 컬럼이나 두 저장소가 가지면 누가 쓰는지와 같은 트랜잭션에서 함께 바뀌는지를 적는다. 다른 트랜잭션이나 다른 저장소에서 갱신되는 사본은 정본이 무엇인지와 어긋났을 때의 복구 경로를 적는다.
6. 이 값을 읽고 판단한 뒤 쓰는 경로(check-then-act)가 있는가. 있다면 경합을 막는 것이 unique 제약, `@Version`, 조건부 UPDATE, row lock 중 무엇인지 적는다. 답이 `@Version`이면 그 변경이 version을 가진 행을 실제로 UPDATE하는지 확인한다. `@Version`은 필요한 엔티티만 선언하므로(4.2) 자식 행에는 version이 없다. 엔티티 사이에 연관관계 매핑이 없어서 자식 행만 바뀌면 루트의 version이 오르지 않고, 그 변경은 낙관적 잠금으로 보호되지 않는다. Redis 락이나 짧은 TTL 키는 경합을 줄이는 힌트일 뿐이고 DB 검사를 생략하는 근거가 아니다. 한 경로에서 기다리는 수단은 하나다 — 행이 있으면 row lock, 없으면 분산 락(`Lock`)이고 둘을 함께 기다리지 않는다. 한 aggregate를 여러 쿼리로 읽는 경로라면 READ COMMITTED에서 서로 다른 commit을 함께 읽을 수 있는지도 본다.

**반영: 마이그레이션이 락과 배포를 깨지 않는다.**
7. 이 DDL이 잡는 락과 대상 테이블의 크기는 어떤가.
   - nullable 컬럼이나 non-volatile 기본값(상수, `now()`)이 있는 컬럼의 추가는 메타데이터 변경이라 `ACCESS EXCLUSIVE`를 잡는 시간이 짧다. volatile 기본값(`gen_random_uuid()`, `clock_timestamp()`), stored generated 컬럼, identity 컬럼은 테이블과 인덱스를 전부 재작성한다.
   - 짧은 `ACCESS EXCLUSIVE`도 긴 트랜잭션 뒤에서 기다리는 동안 뒤따르는 모든 쿼리를 세운다. 마이그레이션 안에서 `SET LOCAL lock_timeout`을 두고, 시간 초과로 실패하면 다시 실행한다.
   - 일반 `CREATE INDEX`는 `SHARE` 락이라 빌드 동안 쓰기만 막는다. `SET NOT NULL`, 타입 변경, unique·PK 제약 추가는 `ACCESS EXCLUSIVE`라 스캔·재작성·인덱스 빌드 동안 읽기까지 막는다. 타입 변경은 binary coercible(`varchar` 길이 확장, `varchar`에서 `text`)이면 재작성이 없다.
   - 큰 테이블에서는 나눈다. `NOT NULL`은 nullable 추가, 배치 backfill, `NOT VALID` 제약 추가, `VALIDATE CONSTRAINT`(`SHARE UPDATE EXCLUSIVE`라 읽기와 쓰기를 막지 않는다) 순서다. unique는 `CREATE UNIQUE INDEX CONCURRENTLY` 뒤에 `ADD CONSTRAINT ... USING INDEX`로 붙인다. partial·expression 인덱스는 제약에 붙일 수 없다.
   - `CONCURRENTLY`는 트랜잭션 안에서 실행할 수 없다. Flyway는 이 문장을 감지해 그 마이그레이션을 트랜잭션 없이 실행하고 다른 문장과 섞이면 실패시키므로, 그 문장만 담은 별도 마이그레이션으로 둔다. 이 마이그레이션을 처음 넣는 PR에서 `spring.flyway.postgresql.transactional-lock=false`를 함께 설정한다. 기본값이면 Flyway 자신의 락 트랜잭션을 `CONCURRENTLY`가 기다려 끝나지 않을 수 있다(Flyway 문서의 경고이고 이 저장소에서 재현하지는 않았다). 실패하면 롤백되지 않고 INVALID 인덱스가 남는다. 이 인덱스는 쓰기 비용을 계속 내고 unique면 INSERT도 계속 거절하므로 다시 실행하기 전에 `DROP INDEX CONCURRENTLY IF EXISTS`로 지운다. 트랜잭션 밖에서 실패한 마이그레이션은 `flyway_schema_history`에 `success = false` 행을 남기고, 그 행이 있으면 다음 migrate가 멈춰 새 버전이 뜨지 않으므로 인덱스를 지운 뒤 그 행도 정리한다(`flyway repair` 또는 행 삭제). 마이그레이션에 `if not exists`를 쓰지 않는다 — INVALID 인덱스가 남아 있어도 건너뛴다. `CONCURRENTLY`는 진행 중인 쓰기 트랜잭션이 끝나기를 기다리므로 떠 있는 이전 버전 pod의 긴 트랜잭션이 기동을 늦춘다(상한은 트랜잭션 상한 30초). 트랜잭션 밖이라 `SET LOCAL lock_timeout`은 효과가 없다.
   - 제약을 더하기 전에 위반 행을 세는 쿼리와 그 결과, 위반 행의 처리 방침을 적는다. 위반 행이 있으면 마이그레이션이 실패해 새 버전이 기동하지 못한다.
8. 이전 버전 애플리케이션이 새 스키마에서 뜨고 쓰는가. 순서는 expand, 이중 읽기·쓰기, backfill, 전환, 정리다. JPA가 `validate`라서 엔티티에 없는 컬럼이 추가되는 것은 이전 버전의 기동을 막지 않는다. 기본값 없는 `NOT NULL` 컬럼은 이전 버전의 INSERT를 실패시킨다. 컬럼 삭제와 이름 변경은 이전 버전의 기동을 막고, Hibernate가 SELECT와 INSERT에 컬럼을 모두 명시하므로 이미 떠 있는 이전 버전 인스턴스의 조회와 쓰기도 즉시 실패시킨다. 삭제는 그 컬럼을 쓰는 코드가 배포에서 빠진 다음 PR에서 한다.
9. 이 값이 도메인 이벤트의 payload나 캐시되는 DTO에 실리는가. 실린다면 이벤트 schema의 하위 호환과 캐시 무효화를 함께 적는다. 하위 호환 규칙은 [이벤트 계약](event-contract.md)이다.

사례:
- `t_order.payload_hash`는 질문 1·3에서 걸려 추가하지 않았다. 대상 필드가 이미 `t_order`·`t_order_line`에 있고 line 변경 명령이 생기기 전까지는 현재 상태가 최초 요청과 같아서 직접 비교로 대체했다([order-idempotency-conflict](../spec/2026-09-20-order-idempotency-conflict.md)).
- `t_sync_watermark`(단말당 행 하나, `terminal_id`가 PK)와 `t_sync_operation`(`(terminal_id, operation_id)` unique)은 sync intake의 표다. watermark는 `max(sequence)`와 같지만 집계는 잠글 수 없어 행으로 둔다(질문 1). 항목마다 그 행을 잠그고 판정·적용·기록·전진을 한 커밋으로 하므로 `@Version`은 없다(질문 6). 접수 기록의 payload hash는 operation의 payload를 저장하지 않으므로 도출할 수 없고(질문 1) `(terminalId, operationId)` 재전송 판정의 근거이며, unique는 "같은 operation을 두 번 적용하지 않는다"의 마지막 방어선이라 soft delete된 행에도 걸린다(질문 4). `order_id`는 참조이고 FK는 없다(질문 5). Spring Modulith의 Event Publication Registry는 나가는 이벤트의 기록이라 들어오는 명령의 멱등·순번 추적을 대신하지 못한다([sync-intake](../spec/2026-09-30-sync-intake.md)). `t_sync_operation.kind`는 읽는 업무 코드가 없는데도 둔다(질문 2). 종류가 둘이 되는 시점에만 상수 기본값으로 기존 행을 정확히 채울 수 있고, 두 종류가 섞인 뒤에는 다른 컬럼에서 도출할 수 없기 때문이다(질문 3). 판정의 정본은 종류 접두어가 든 `payload_hash`이고 `kind`는 같은 INSERT로 쓰는 사람용 사본이다(질문 5)([sync-request-checkout](../spec/2026-09-30-sync-request-checkout.md)). 요청 항목의 선택 필드 `createdAt`(단말이 operation을 만든 시각)은 수렴 시간 metric에만 쓰고 컬럼을 두지 않는다. 필요해지면 그때부터 채울 수 있다(질문 1). payload hash에도 넣지 않아 시각만 다른 재전송은 `DUPLICATE`다([observability-alerts-tracing](../spec/2026-10-21-observability-alerts-tracing.md)). 배치의 선택 필드 `reconnectedAt`(단말이 끊긴 뒤 서버에 닿은 첫 요청의 전송 시각)도 같다. 수렴 시간의 기준점에만 쓰고 저장하지 않으며 컬럼을 두지 않는다([slo-alert-followups](../spec/2026-10-23-slo-alert-followups.md)).
- `t_order_checkout`은 통화 컬럼을 두지 않았다(질문 1, `t_order.currency`에서 읽는다). `amount`는 지금은 line 합계와 같아도 확정 시점에만 알 수 있는 값이라 둔다(질문 3·4). 읽고 판단한 뒤 쓰는 `RequestCheckout`의 경합은 주문 행 잠금(`PESSIMISTIC_WRITE`, PostgreSQL에서는 `for no key update`, 대기 3초 제한)이 막고, unique `(order_id, checkout_no)`와 `@Version`이 그 뒤의 방어선이다(질문 6). Hibernate가 INSERT를 UPDATE보다 먼저 flush해서 잠금이 없으면 `@Version`보다 unique 제약이 먼저 걸린다([order-request-checkout-persistence](../spec/2026-09-21-order-request-checkout-persistence.md)).
- `t_order_line.version`과 `t_order_checkout.version`은 질문 2·4에서 걸려 없앴다. 업무 코드가 읽지 않았고, 행 단위 version은 서로 다른 line을 고치는 두 트랜잭션을 막지 못해 aggregate의 방어선이 아니었다. 대신 같은 line 행을 동시에 고치는 경우의 충돌 감지는 포기했다. 지금 기존 주문의 line을 고치는 명령이 없다는 것이 그 전제이고, 명령을 넣는 PR이 루트 잠금이나 루트 version 증가를 함께 정한다. 방어선은 루트(`t_order`의 행 잠금과 `@Version`)와 unique `(order_id, checkout_no)`다. 배포된 환경이 없던 시점이라 질문 8의 순서를 밟지 않고 코드 제거와 컬럼 삭제를 한 PR로 했다([base-entity-explicit-version](../spec/2026-09-21-base-entity-explicit-version.md)).
- `t_order`의 unique `(terminal_id, client_order_id)`는 질문 4·6의 답이다. 같은 키의 생성이 동시에 오면 `Lock`이 줄 세워 늦은 요청이 기존 주문을 받고, 락이 통하지 않으면 이 제약이 막는다([shared-distributed-lock](../spec/2026-09-28-shared-distributed-lock.md)). 멱등 키는 삭제 뒤에도 재사용하면 안 되므로 partial unique로 바꾸지 않는다. 주문을 soft delete하는 명령이 생기면 `findByClientOrderId`가 삭제된 주문도 찾게 해야 한다. 지금은 주문을 삭제하는 코드가 없다.
- `t_terminal`·`t_terminal_credential`은 단말 인증의 표다. 토큰 평문은 저장하지 않고 SHA-256 hex(`token_hash`)만 둔다(질문 9). unique `ux_terminal_credential_token_hash`는 해시 하나가 두 단말을 가리키지 않게 한다. 인증 조회가 한 행을 전제하기 때문이다. `ux_terminal_credential_active`(`terminal_id`, `revoked_at is null`)는 "유효 credential은 단말당 하나"의 마지막 방어선이다. 평소에는 terminal 행 잠금(`PESSIMISTIC_WRITE`, 대기 3초)이 회전을 직렬화하므로 `@Version`은 두지 않는다(질문 4·6). 둘 다 soft delete된 행에도 걸린다. 이 제약은 커밋 때 검사하는 exclusion 제약이다(`DEFERRABLE INITIALLY DEFERRED`). Hibernate는 한 flush에서 INSERT를 UPDATE보다 먼저 보내지만, 회전이 폐기와 새 발급을 한 커밋에 넣어도 커밋 때 유효 행이 하나면 통과한다. partial unique 인덱스는 DEFERRABLE이 될 수 없고 unique 제약은 술어를 가질 수 없어서 exclusion 제약으로 두었다([contention-error-mapping](../spec/2026-10-20-contention-error-mapping.md)). 인증 결과는 캐시하지 않는다. 정본은 `revoked_at is null`인 행이고 Redis는 정본이 될 수 없다(질문 5)([terminal-authentication](../spec/2026-10-05-terminal-authentication.md)). 단말 코드 `terminal_code`는 점주가 단말을 고르는 목록 조회가 읽어서 들였다(질문 2). unique `ux_terminal_store_code`(`store_id`, `terminal_code`)가 매장 안 코드 유일의 유일한 방어선이고 사전 조회는 없다(질문 4·6). 지우는 명령이 없어 삭제 행에도 걸리게 두었다. 기존 행은 매장별 `LEGACY-순번`으로 채운 뒤 NOT NULL로 바꿨다(질문 3)([operator-authentication](../spec/2026-10-06-operator-authentication.md)).
- `t_owner`·`t_store`는 점주 계정과 매장의 표다. 로그인 실패 횟수와 세션은 업무 사실이 아니라 시한이 있는 장치라 Redis에 두고 컬럼을 만들지 않았다(질문 1). unique `ux_owner_email`이 이메일 중복 가입의 유일한 방어선이고, 이메일은 애플리케이션이 소문자로 정규화해 넣는다(질문 4). 매장과 점주의 소속은 `t_store.owner_id` 한 컬럼이다. 한 매장을 여러 계정이 관리하는 기능이 없어 소속 표를 두지 않았고, 세션에 매장 목록을 담지 않아 소속의 정본이 하나다(질문 5)([operator-authentication](../spec/2026-10-06-operator-authentication.md)).
- `t_dead_letter_redrive`는 DLT 재투입 기록이다. Kafka는 DLT 레코드를 다시 보낸 사실을 남기지 않고 로그는 정본이 아니라서 표로 둔다(질문 1). 원 토픽(`dlt_topic`에서 `.DLT`를 뺀 값)과 재투입 시각(`created_at`)은 도출할 수 있어 컬럼을 두지 않았다. 넣은 자리(`target_partition`·`target_offset`)는 다시 DLT로 간 메시지를 이 재투입에 잇는 유일한 값이다(질문 2). unique `ux_dead_letter_redrive_source(dlt_topic, dlt_partition, dlt_offset, dlt_timestamp)`가 "한 DLT 레코드의 기록은 하나"와 멱등 응답의 유일한 방어선이고, 지우는 명령이 없어 삭제 행에도 걸린다(질문 4). 레코드 시각(`dlt_timestamp`)을 넣은 것은 DLT 토픽을 다시 만들면 offset이 0부터 재사용되기 때문이다. 조회는 삭제 행을 보지 못하므로 이 표의 행은 SQL로도 soft delete하지 않는다. `reason`은 읽는 코드가 없는 감사 정본이고 나중에 채울 수 없어 둔다(질문 2·3). 전송은 트랜잭션 밖이라 같은 좌표가 동시에 오면 둘 다 보낼 수 있고 consumer 멱등이 견딘다(질문 6)([platform-operator-dlt-redrive](../spec/2026-10-21-platform-operator-dlt-redrive.md)).
- `t_dead_letter_dismissal`은 DLT 폐기 표시 기록이다. Kafka 레코드에는 표시를 남길 수 없어 표로 둔다(질문 1). 재투입 표에 넣지 않은 것은 그 표의 넣은 자리 컬럼이 not null이고 "기록이 있으면 브로커에 ack된 것이다"라는 불변식이 깨지기 때문이다. unique `ux_dead_letter_dismissal_source(dlt_topic, dlt_partition, dlt_offset, dlt_timestamp)`가 "한 DLT 레코드의 폐기 기록은 하나"와 멱등 응답의 유일한 방어선이고 삭제 행에도 걸린다(질문 4). 두 표에 걸친 배타는 두지 않는다. DB가 지킬 수 없고 미처리 수 gauge가 두 표의 합집합으로 세어 둘 다 있어도 틀리지 않는다. 합집합의 두 조회는 같은 시점을 읽지 않아, 폐기한 레코드의 재투입이 그 사이에 커밋되면 한 갱신 동안 많게 센다(질문 6). `reason`은 재투입 기록과 같은 판단으로 둔다(질문 2·3)([alert-state-gauges](../spec/2026-10-22-alert-state-gauges.md)).
- `t_fulfillment`의 unique는 청사진의 `(orderId, ticketType)`이 아니라 `(order_id)`다. 이행 방식이 하나뿐이고 `type`을 읽는 코드가 없어 질문 2에서 걸렸다. 방식이 늘면 지금의 유일한 종류를 뜻하는 상수 기본값 컬럼을 더하고 unique를 바꾼다(질문 3). "주문당 한 번"의 마지막 방어선이라 soft delete된 행에도 걸리는 전체 unique로 둔다(질문 4). 상태·매장·품목 snapshot도 읽는 명령·조회가 생길 때 더한다([fulfillment-kitchen-ticket](../spec/2026-09-24-fulfillment.md)).
- `t_menu`(매장당 한 행, `store_id`가 PK)는 메뉴의 정본이다. 메뉴는 PostgreSQL 어디에도 없고 `t_order_line`은 판매된 값의 기록이라 팔리지 않은 상품과 바뀐 가격을 모른다(질문 1). `version`은 `updated_at`으로 대신할 수 없다. `updated_at`은 JVM 시각이라 pod 사이에 단조가 아니다. `store_id`·`menu`·`version`은 두 조회 API와 ETag·`If-Match` 비교가 읽는다(질문 2). PK `t_menu_pkey`가 "매장당 메뉴 하나"와 생성 경합의 방어선이고 `@Version`이 수정 경합의 방어선이다. 지우는 명령이 없고 PK가 삭제 행에도 걸려, 삭제 행이 있으면 그 매장은 메뉴를 다시 만들지 못하므로 이 표의 행은 SQL로도 soft delete하지 않는다. 코드 중복과 항목 상한은 문서 하나를 통째로 검사하는 도메인 규칙이라 DB 제약이 없다(질문 4). 단말 localStorage는 사본이고 다음 받기(ETag가 다르면 200)가 복구 경로다. ETag에 매장 ID를 넣어 다른 매장 사본이 맞는 것으로 보이지 않게 한다(질문 5). PUT은 한 트랜잭션의 같은 관리 엔티티에서 version을 비교하고 쓰므로 조건부 UPDATE가 비교한 값을 지키고, 내용이 같아도 version을 올린다(질문 6). jsonb 문서의 필드 이름(`currency`, `items`, `code`, `name`, `price`, `category`)이 저장 형식이라 리터럴 JSON 테스트로 고정한다. 나중에 더하는 필드는 기본값을 둔다. 서버 캐시가 없고 version이 바뀌면 ETag가 바뀌어 무효화가 따로 없다(질문 9)([menu-catalog](../spec/2026-10-26-menu-catalog.md)).

기술 근거(2026-09-20 확인, PostgreSQL 18·Flyway 12.4.0·Hibernate 7.4.5): [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html), [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html), [Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html), [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [Flyway 트랜잭션 처리](https://documentation.red-gate.com/fd/migration-transaction-handling-273973399.html), [Flyway PostgreSQL 락](https://documentation.red-gate.com/fd/postgresql-database-277579325.html). Hibernate `validate`가 매핑된 컬럼만 검사한다는 점은 사용자 가이드에 없어서 `AbstractSchemaValidator` 소스로 확인했다.

## 5. 레이어 경계를 넘는 타입

접미사나 바깥 이름공간(`OrderCommand.`)만 보고 어느 레이어의 객체인지 읽혀야 한다. 표의 타입 이름은 §1과 같이 목표 모델이다.

| 경계 | 넘어가는 타입 | 넘어가지 않는 것 |
|---|---|---|
| HTTP ↔ Controller | `*Request` / `*Response` | Command, aggregate |
| Controller·이벤트 리스너·스케줄러 ↔ Facade | `OrderCommand.*`, `*Query`/`*Criteria` → `OrderCommand.*.Result`, `*View` | Request DTO, JPA 엔티티 |
| Facade ↔ Service·aggregate | `OrderCommand.*`, aggregate, Value Object, `*Policy`, `Transition`(`foundation`, §4.5) | `*Request`/`*Response`, `*View` |
| Facade ↔ Repository | aggregate, ID 값 타입 | Spring Data 타입, JPA 엔티티 |
| Repository 구현 ↔ JPA | `*Entity` — adapter 안에서만 | — |
| 모듈 ↔ 모듈 | 공개 Facade의 커맨드 이름공간(`OrderCommand.*`와 그 `Result`)과 `*Query`/`*Criteria`/`*View`, 도메인 이벤트, ID 값 타입 | `internal` 아래 전부, 테이블 |

## 6. 도식 규약

장기 스펙의 [DESIGN·flow 계층](development-workflow.md#장기-스펙-계층과-pr-spec)에 그림을 넣을 때 지킨다.

**컨텍스트 맵 (DESIGN)**
- 컨텍스트마다 상자 하나. 안에 aggregate 루트를 적는다. 자식 엔티티는 concern의 ERD가 맡는다.
- 컨텍스트 맵 안에서는 컨텍스트 사이에 화살표를 긋지 않는다. 이벤트 관계는 [청사진 §2.1](../references/05_Domain_Development_Blueprint.md)처럼 별도 목록이나 그림으로 적는다. 컨텍스트 맵에 동기 호출 화살표가 필요해지면 경계가 의심스럽다는 신호다(§4.6).

**유스케이스 시퀀스 (flow)**
- 참여자는 호출자, Facade, 관여 컨텍스트, DB, 이벤트 전달(EPR), 소비자 순으로 놓는다. 컨텍스트 lifeline에 닿는 메시지 하나가 그 컨텍스트가 제공해야 하는 공개 기능 하나다.
- 전제 조건 확인(조회)은 트랜잭션 상자 **앞에** 두고, 실패 분기는 그 자리에서 끝낸다.
- 트랜잭션 상자는 쓰기만 감싼다. 상자 안이 한 커밋으로 맞아야 하는 전부다. provider 호출·외부 전송은 상자 밖이다.
- 커밋 뒤에 발행되는 이벤트와 그 소비자(다른 컨텍스트의 후속 쓰기)를 같은 그림 아래쪽에 그린다. 호출자 응답은 커밋 직후이고 소비자보다 먼저다.
- 실패 시퀀스(중복·응답 유실·`UNKNOWN`·gap)는 flow 템플릿대로 같은 파일에 둔다.

## 7. 도메인 설계 체크리스트

grill 심문과 업무 기능 spec의 "소유 모듈 / Command·Query·Event / 불변식" 항목을 채울 때 순서대로 묻는다.

1. **소유** — 이 데이터를 소유하는 bounded context는 하나인가? 둘 이상이면 경계가 잘못됐거나 한쪽이 이벤트로 받아야 한다.
2. **루트와 트랜잭션** — aggregate 루트는 무엇이고, 한 트랜잭션에서 함께 맞아야 하는 것은 무엇인가? 그 밖은 ID로만 참조한다.
3. **유일한 진입점** — 이 기능을 다른 컨텍스트에서 수행할 수 있는가? 있다면 안 된다. 소유 컨텍스트의 Facade나 이벤트로만 한다.
4. **규칙의 위치** — 계산·검증이 데이터 가까이(Aggregate·Value Object·Policy) 있는가? Service에 `amount + discount`, `status = ...`, validation if-else가 늘면 옮긴다. 루트가 바뀔 때 남겨야 하는 이력은 자식 엔티티로 같은 트랜잭션에 있는가(§2)?
5. **단어** — 새 단어가 생겼는가? §3에 있는 단어인가, 같은 단어를 다른 뜻으로 쓰고 있지 않은가?
6. **사실** — 발행하는 이벤트는 과거형 한 가지 사실인가? "완료"처럼 여러 사실이 섞이면 나눈다.
7. **실패** — 중복 요청, 응답 유실, `UNKNOWN`, gap, 재처리가 상태 모델에 있는가? [README 완료 조건](../../README.md#engineering-principles)의 실패 시나리오와 맞춘다.

## 8. 참고 사례와 다르게 가는 결정

[카카오페이 사례](https://tech.kakaopay.com/post/backend-domain-driven-design/)에서 가져온 것: 용어 정의(§1), "도메인 기능은 그 도메인을 통해서만"(§7의 3번), 상태 변경과 이력을 한 aggregate에 두는 기준(§2), 경계마다 타입 접미사를 고정하는 레이어 도식(§5), 구현 전에 팀이 함께 보는 시퀀스(§6). 사례가 그렇게 한 이유는 "정책이 명확하고 복잡한 도메인을 견고하게 만들고, 여신 전문가·기획·개발이 같은 말을 쓰기 위해서"였다. 오프라인 정합성과 결제 모호성이 핵심인 이 프로젝트도 같은 조건이다. 구조는 다음에서 다르다.

| 사례 | 이 저장소 | 이유 |
|---|---|---|
| bounded context = Gradle 모듈 | Spring Modulith 패키지 모듈. Gradle 분할은 현재 상태(`docs/wiki/current-state.md`, 볼트)의 조건이 충족될 때만 | 모듈 9개가 비어 있는 지금 나누면 담길 코드보다 빌드 코드가 많다. 경계는 Modulith 검증이 이미 막는다 |
| Kotlin `internal` 가시성으로 JPA 엔티티를 숨김 | 목적은 같고 수단이 둘로 갈린다. 모듈 경계는 `internal` **패키지** + Modulith 검증, 엔티티를 밖에서 만들거나 바꾸지 못하게 하는 것은 `private` 생성자와 전 필드 `var … protected set`이고, `EntityVisibilityTest`가 그 형태를 고정한다([entity-property-visibility](../spec/2026-09-22-entity-property-visibility.md)) | 단일 Gradle 프로젝트에서 Kotlin `internal`은 전체에 보여 경계가 되지 않는다. 사례 스스로 배치용 JPA 엔티티를 중복 생성한 부작용을 기록했다. 생성·변경을 `from`·`apply`로 묶는 일은 키워드 없이 생성자와 setter 가시성만으로 된다. `private set`이 아닌 이유는 `allOpen`이 `@Entity`에 걸려 있어 멤버가 open이고 Kotlin이 open 프로퍼티의 `private set`을 금지하기 때문이다. 바뀌지 않는 필드를 `val`로 좁히지 않는 이유는 그것이 JVM final 영속 필드가 되어 Jakarta Persistence 3.2 §2.2 금지와 bytecode enhancement 비호환에 걸리기 때문이다 |
| Command를 aggregate 안의 중첩 클래스로, 상태는 `var … internal set` | Command는 Facade의 공개 입력, aggregate는 불변(§4.1) | CQRS 규약상 Command는 모듈 공개 계약이다. 불변 전이는 기존 Kotlin 규칙과 일치한다 |
| API·배치 공통 로직을 Biz-component 패키지로 | Controller·이벤트 리스너·스케줄러가 같은 Command Facade를 호출 | Facade가 이미 use case 단위의 공통 진입점이다. 별도 레이어를 두지 않는다 |
| 도메인 모듈에는 use case가 없고, 별도 `core_app`이 여러 도메인을 한 트랜잭션으로 조합(가입 = 회원 + 계좌 + 한도) | use case(Facade)는 컨텍스트 안에 있고, 컨텍스트를 넘는 변경은 이벤트가 기본이다. 동기 호출의 허용 조건과 트랜잭션 전파는 §4.6 | 컨텍스트별로 독립 배포로 뽑아내는 경로([시스템 설계 §6](../references/02_System_Design.md))를 열어 두려면 컨텍스트를 넘는 트랜잭션을 기본값으로 삼을 수 없다. 사례는 단일 배포 코어라 한 트랜잭션으로 묶을 수 있었다 |
| 자식 엔티티 이름에 `snapshot`(계좌 Snapshot, 연체 snapshot) | checkout 확정 금액에는 쓰지 않는다(§3) | 사례의 snapshot은 시점 복사본이라는 구현 사실이고, 우리의 checkout은 "N회차 확정 금액"이라는 업무 사실이다. 시점 복사본이 정말 필요해지면 그때 `snapshot`을 그 뜻으로만 쓴다 |
| [시스템 설계 §5](../references/02_System_Design.md)의 order 상태 `OFFLINE_CREATED → SYNCED → PAYMENT_PENDING` | `CreateOrder`의 첫 상태는 `OPEN`이다. 오프라인 생성·동기화 여부는 `sync`가 소유하는 사실이라 order 상태에 넣지 않는다. 상태 열거값은 각 명령 PR이 추가한다([order-domain-model](../spec/2026-09-16-order-domain-model.md)) | order 상태는 line·금액을 바꿀 수 있는지(§2 불변식)만 뜻해야 한다. 생성 경로를 상태에 섞으면 같은 주문이 경로에 따라 다른 lifecycle을 가진다 |
| [시스템 설계 §4.2](../references/02_System_Design.md)의 "독립 배포 consumer가 실제로 생긴 event만 externalize" | 소비자가 모두 같은 앱 안인데도 모듈 사이 이벤트를 모두 Kafka로 보내고 리스너를 consumer로 바꿨다([kafka-event-redelivery](../spec/2026-09-26-kafka-event-redelivery.md)) | 재전달만이면 주기 `resubmit`으로 풀리지만, 여러 pod로 돌리는 것을 전제하고 재시도·순서·DLT를 브로커의 표준 수단에 맡기며 앱 밖 consumer가 붙을 때 같은 토픽을 쓰려고 앞당겼다. 대가는 로컬 실행과 테스트에 브로커가 필요해진 것이다 |
